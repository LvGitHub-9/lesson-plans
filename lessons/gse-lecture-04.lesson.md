### V1 ★ 制品（artifact）与文件：目录树不够用

**原子性**：只考一件事 ✓（"文件是接口"与"目录树表达不了关系"是同一件事两面，不拆）

**【讲义原话】**
- 出处：§一堆文件，够不够表示一个项目
- 要点：
  - 「我们通常把软件项目看成各种文件的集合：**Intent 记录想做什么，Spec 说明具体应当满足什么要求，
    Code 给出实现，也就是 Impl**，再加上测试、配置、文档和生成的产物。
    这些开发过程中形成的对象，统称为**软件工程制品，也就是 artifact**。」
  - ⭐ 「**文件是一个非常成功的接口。**人可以用编辑器阅读和修改，程序可以搜索、比较、编译和打包，
    版本管理工具也能够接手。但**'放在文件里'首先是现有文件系统和工具生态提供的方便，
    项目本身并不天然就是一棵目录树。**」
  - ⭐⭐ 「**目录树尤其不擅长直接表达制品之间的关系。**
    比如个人助手的一项需求是'记住用户纠正过的偏好'。这项需求可能对应**一条规格、
    一个更新记忆的函数和几组测试**。现在用户又提出'有些偏好只在某段时间内有效'，
    **我们想知道的就不只是哪个文件变了，还包括哪些设计假设受到影响、
    哪些实现需要调整、哪些测试应该增加。**」
  - ⭐ 「从需求走到设计、实现和验证，再从一段代码反查它服务的需求，
    这类关系构成了 **traceability，可追踪性**……
    **把相关文件放进同一个目录，不会自动建立这些联系；
    保存每个文件的所有版本，也不会自动说明某项设计为什么存在。**」
  - ⚠️ 「这些关系**需要有人或工具维护**，否则**代码已经改了，原来的解释却可能还留在原地。**」

**【机制 / 为什么】** ✅ 材料给了完整机制，并指出"将错就错"的路径依赖。

**【前置】** L3 U3（快照）

**【标准范例】** —— 用他自己的项目
```
你的 FOC 工程里，"制品"和"文件"的关系：

    需求：空载下速度环稳态误差 < 1%
     ↓
    规格：采样 10kHz、PID 参数、限幅策略
     ↓
    实现：motor.c 里的 SpeedLoop()
     ↓
    验证：test_speed.py 或手工台架测试记录

⭐ 目录树只告诉你：
    Motor/
    ├── motor.c        ← 这些文件在哪
    ├── motor.h
    └── test_speed.py

⭐ 目录树**不告诉你**：
    这几条"需求→规格→实现→验证"的连线
    → 所以当需求改成"带载也要 <1% 误差"时，
      **你要自己想起来**：哪些规格要改、哪些实现要动、哪些测试要加
    ⚠️ 想不起来的那部分，就是讲义说的
       **"代码已经改了，原来的解释却可能还留在原地"**
```

**【常见误解】**
1. 「项目就是一堆文件」——讲义明确：**项目并不天然是一棵目录树**
2. 「文件放同一个目录里就有关系了」——❌ **不会自动建立这些联系**
3. 「有版本控制就够了」——❌ **保存每个文件的所有版本，也不会自动说明某项设计为什么存在**

**【适用边界】**
- 讲义把"文件"定性为**历史路径依赖的结果**（"将错就错"），并提了一个**面向未来的猜想**
  （Agent 成为主要生产者时，组织形式可能根本变化）→ ⚠️ **那是猜想，不是结论**

**【预考题】** ⭐ 用课堂原话
1. 【讲义原话·课堂提问】「如果今天重新设计一套版本管理系统，我们会把什么作为基本对象？」
2. 你的工程里，"需求→实现→验证"的对应关系记在哪里？

**【练习题 + 答案】**
- Q1（识别）：什么是 artifact（软件工程制品）？
  A1：**开发过程中形成的对象**：Intent（意图）、Spec（规格）、Code（实现）、
  以及测试、配置、文档、生成的产物。
- Q2（★ 应用）：为什么说"文件是一个非常成功的接口"，但"目录树尤其不擅长表达制品之间的关系"？
  A2：**成功**是因为人和工具都能读写、搜索、比较、编译、打包；
  **不擅长**是因为**目录树只有"位置"，没有"关系"**——
  一个需求对应哪条规格、哪个函数、哪组测试，目录里看不出来。
- Q3（应用）：用户提出"有些偏好只在某段时间内有效"，讲义说我们想知道什么？
  A3：**不只是哪个文件变了**，还包括：**哪些设计假设受到影响、哪些实现需要调整、
  哪些测试应该增加。**
- Q4（迁移）：你在 FOC 项目里把"需求→规格→实现→验证"的对应关系记在哪？
  如果没有记，当需求变化时会发生什么？
  A4（开放，引导）：通常只记在脑子里 → 需求一变就要**从头推一遍**。

**【迁移题】**
为你项目里的一条需求，画出它的"需求→规格→实现→验证"四条连线。

**【掌握判定】**
- 能说清：能说出 artifact 的构成、文件为什么"成功"、目录树为什么"不够"
- 能应用：能给一条需求画出制品间的连线
- 能回忆：隔一天能说出 traceability 指什么

### V2 快照 → 有向无环图；merge 与 rebase 的直观

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§从快照理解分叉与合并
- 要点：
  - 「Git 管理**文件内容、目录树，以及快照之间的历史关系**。一次 commit……
    除了指向文件状态，还记录**父提交、作者、说明**等信息。
    **父提交的连接把历史组织成一张有向无环图。**」
  - 「可以把一次开发理解成：**从状态 A 出发，完成一个功能，得到状态 B**；
    提交说明中的 `feat: ...` 帮助人理解这一步想推进什么。」
  - 「如果两个人都从 A 出发，一人修改输入方式，另一人修改结果展示，就会得到两条开发路线。
    **Merge 把两边的成果整合起来**；在通常的分叉合并中，新的提交会**同时连接两边的历史**。
    **Rebase 则把一条路线上的改动重新应用到另一个起点上**，
    让这些改动**好像是在新的基础上依次完成的**。」

**【机制 / 为什么】** ✅ 材料给了机制（父提交连成图）。⚠️ 引注 Git Objects 未核。

**【前置】** L3 U3、U5

**【标准范例】** —— 用他在 L3 学过的语言
```
Git 管三样东西：
    ① 文件内容
    ② 目录树
    ③ **快照之间的关系**（父提交连成的图）

"有向无环图"用你熟的话说：
    像一张"派生关系图"——每个版本从某个父版本派生出来，
    而且**不可能绕回自己**（所以叫无环）
    ⚠️ 这不是数据结构课上的图算法，只是"谁从谁来"的记录

    A ──► B ──► C
           └──► D     ← 两条线都从 B 出发

    merge：新提交同时连接 C 和 D（两个父提交）
    rebase：把 D 上的改动"重新放在 C 后面"，
            让它看起来像是先做了 C 才做的 D
```

**【常见误解】**
1. 「历史是一条直线」——❌ 是**有向无环图**（可以分叉再汇合）
2. 「merge 和 rebase 只是两种风格」——效果不同：**merge 保留分叉，rebase 改写基础**
3. 「提交说明只是形式」——讲义说它"**帮助人理解这一步想推进什么**"

**【适用边界】**
- ⚠️ 讲义只给了直观理解，**未展开对象模型细节**（引注 Git Objects 未核）

**【预考题】**
1. 两个人都从版本 A 出发各自改，最后会得到什么结构？
2. 为什么 Git 的历史不是一条直线？

**【练习题 + 答案】**
- Q1（识别）：一次 commit 除了文件状态，还记录什么？这些信息形成什么结构？
  A1：**父提交、作者、说明**等信息；**父提交的连接把历史组织成一张有向无环图**。
- Q2（应用）：两个人从同一个版本 A 出发，一个改输入方式、一个改结果展示，会怎样？
  A2：得到**两条开发路线**；merge 把两边成果整合（新提交同时连接两边历史），
  rebase 则把一条路线的改动**重放到另一个起点上**。
- Q3（迁移）：你从 v1.0 分出一个实验分支改算法，主干同时修了 bug。要合回来，用哪种方式？
  A3：看约定——**要保留"这是并行开发"的事实用 merge**；
  **要让历史看起来像线性地用 rebase**（但若别人已依赖你的实验分支，要慎重，见 L3 U5）。

**【迁移题】**
用你自己的项目画一次真实的"分叉与汇合"。

**【掌握判定】**
- 能说清：能说出 Git 管的三样、历史是 DAG、merge 与 rebase 的差别
- 能应用：能判断一个场景该 merge 还是 rebase
- 能回忆：隔一天能说出"父提交的连接把历史组织成一张有向无环图"

### V3 ★★ 冲突的本质

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§从快照理解分叉与合并
- 要点：
  - ⭐ 「**冲突来自两边对共同状态作出了不能直接兼容的修改。**
    例如同一个配置原来写着'立即保存'，一边改成'手动确认后保存'，
    另一边改成'每分钟自动保存'。**工具可以发现文本上的分歧，
    究竟要哪一种行为，却需要回到需求。**」
  - ⭐⭐ 「**即使改动位于不同文件，能够自动合并，组合起来也可能违背双方原来的假设。**」

⭐⭐ **这一句是 L3 U17（write skew）的另一个版本**，而且更狠：**没有文本冲突 ≠ 没有冲突**。

**【机制 / 为什么】** ✅ 材料给了机制和一条重要的边界。

**【前置】** L3 U6（冲突的可见形态）、L3 U17（write skew）

**【标准范例】** —— 直接复用他熟悉的中断竞态
```
⭐ 讲义这句话，用你的语言就是：

    两个中断各自改的是**不同的变量**（所以"文本上没有冲突"）
    但**组合起来可能违背一条共同假设**

    例：约束是"两个通道至少开一个"
    中断1 关掉 A     ← 只在 A 的文件里
    中断2 关掉 B     ← 只在 B 的文件里
    → 自动合并毫无问题 → **结果约束被破坏**

⭐ 讲义的判据：
    "工具可以发现**文本上的**分歧"  ← 工具能做的
    "究竟要哪一种行为，**却需要回到需求**"  ← 只能人做的
```

**【常见误解】**
1. 「没有冲突标记 = 合并没问题」——❌ **讲义明确否定**
2. 「冲突是文本问题」——❌ **冲突来自"对共同状态作出了不能直接兼容的修改"**，
   文本只是它的**表现形式之一**
3. 「工具能解决所有冲突」——⚠️ 工具只能发现**文本上的**分歧；
   **要哪种行为，要回到需求**

**【适用边界】**
- ⚠️ **缺口：讲义未给"如何发现跨文件的组合冲突"的方法**
  （L3 U17 给了方向：检查组合结果 / 更强的并发控制）

**【预考题】** ⭐ 用课堂原话
1. 两个人在不同文件里改动，能自动合并，就一定没问题吗？
2. 冲突的真正来源是什么？

**【练习题 + 答案】**
- Q1（★ 识别）：讲义说冲突来自什么？
  A1：**两边对共同状态作出了不能直接兼容的修改。**
- Q2（★ 关键）：为什么"改动位于不同文件、能够自动合并"仍可能出问题？
  A2：因为**组合起来可能违背双方原来的假设**。文本层面没有分歧，
  但两次修改合起来破坏了某个**共同约束**（这正是 L3 write skew 的形态）。
- Q3（应用）：配置从"立即保存"被一边改成"手动确认后保存"、另一边改成"每分钟自动保存"。

### V5 ★★★ change ID vs commit ID

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§把变化的身份纳入版本管理
- 要点：
  - ⭐ 「我们执行 cherry-pick 时，通常想搬走的是**某次提交引入的改动**；
    执行 rebase 时，通常也认为'**我做的还是那件事，只是换了一个基础**'。
    **但我们传给工具的主要标识，是 commit。**」
  - ⭐ 「**Commit 的身份与它的具体内容和元数据相联系。父提交一变，commit 的内容就变了；
    重写时会创建新的 commit 对象，得到不同的 ID。**
    于是，原来的 C 经过重写变成 C′：**人知道这仍然是在修改同一个功能，
    单靠 commit ID 却无法表达这种身份的延续。**
    ⭐⭐ 这里有两个值得区分的问题：**某个版本的准确状态是什么，
    以及某项改动随着反复修改经历了哪些版本。**」
  - 「如果把后一个问题直接纳入工具设计，就走到了 **Jujutsu** 的一个重要思路。
    它常简称为 **jj**，用 **change ID 追踪一项持续演化的改动**，
    同时保留 **commit ID 标识具体版本**。**重写时 commit ID 会改变，而 change ID 通常保持不变。**
    ……⚠️ 这里说的 change 是**随时间演化的提交**；
    **它的底层仍然保存快照，并不是把系统简单改成了补丁文件的集合。**」

⭐⭐⭐ **本讲最难也最重要的一点**：**"哪一版"和"哪件事"是两个不同的问题。**

**【机制 / 为什么】** ✅ 材料给了完整机制。

**【前置】** L3 U3（快照）、L3 U5（rebase 产生新标识）

**【标准范例】** —— 用他的项目管理方式
```
⭐ 两个问题，用你的场景分开：

    问题 A：**这个版本的准确状态是什么**
        → 对应 commit ID（像固件版本号 + 校验和）
        → 只要内容或父提交变了，它就**必须变**

    问题 B：**我在做的"这件事"经历了哪些版本**
        → 对应 change ID
        → 我一直在改"让速度环在低速下不抖"这件事，
          **改了 7 次** —— 这 7 个版本是同一件事的演化

⚠️ 讲义的关键提醒：
    "C 经过重写变成 C′：**人知道这仍然是在修改同一个功能，
     单靠 commit ID 却无法表达这种身份的延续**"

⭐ 所以 jj 用**两个 ID**：
    change ID  不变（标识"这件事"）
    commit ID  会变（标识"这一版"）

⚠️ 讲义主动澄清的边界：
    "**底层仍然保存快照**，并不是把系统简单改成了补丁文件的集合"
    → 别以为 jj 是"退回 diff 式系统"
```

**【常见误解】**
1. 「commit ID 就是"我在做的那件事"的标识」——❌ **rebase 之后就变了**
2. 「jj 是把快照改成补丁」——❌ 讲义明确否定
3. 「两个 ID 是重复设计」——它们回答**两个不同的问题**

**【适用边界】**
- ⚠️ 讲义引用了 Jujutsu 官方术语说明，**我未核对原文** → `【待查证·引注未核】`

**【预考题】** ⭐ 用课堂原话改写
1. 你 rebase 之后，那个"提交编号"会变吗？如果不希望它变，说明你关心的是什么？
2. "这是哪一版"和"我在做哪件事"——是同一个问题吗？

**【练习题 + 答案】**
- Q1（★ 识别）：讲义区分了两个什么问题？
  A1：**① 某个版本的准确状态是什么；② 某项改动随着反复修改经历了哪些版本。**
- Q2（应用）：为什么"人知道这仍然是同一个功能，单靠 commit ID 却无法表达"？
  A2：因为 **commit 的身份与它的内容和元数据相联系**；
  **父提交一变、内容一变，就会创建新的 commit 对象、得到不同的 ID**。
  于是"同一件事的第 3 版和第 7 版"在 commit ID 上**看不出是同一件事**。
- Q3（应用）：jj 用 change ID 解决了什么？
  A3：**追踪"一项持续演化的改动"**——重写时 **commit ID 会变，change ID 通常不变**，
  从而把"身份的延续"表达出来。
- Q4（★ 关键）：讲义为什么要专门澄清"底层仍然保存快照"？
  A4：因为容易误解成"放弃了快照、改成补丁集合"。
  实际上**快照仍是底层**，change ID 是**在快照之上**增加的一层身份表达。
- Q5（迁移）：你自己的项目里，"第 7 版 PID 参数"和"调试速度环这件事"，
  各自记录在哪里？两者能对上吗？
  A5（开放）：通常只在脑子里或注释里，**对不上**——这正是讲义说的问题。

**【迁移题】**
给你的一个"反复改了多次的改动"起一个 change ID（一句描述），再列出它经历的几个版本。

**【掌握判定】**
- 能说清：能说出两个问题的差别，并解释 change ID 的作用
- 能应用：能对一个场景判断"你关心的是哪一版还是哪件事"
- 能回忆：隔一天能复述"重写时 commit ID 会改变，而 change ID 通常保持不变"

### V6 ★ 把冲突变成「可保存的状态」

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§把变化的身份纳入版本管理
- 要点：
  - 「另一个很有吸引力的设计，是**把冲突作为可以保存的状态**。
    假设你正在把一串改动移到新的基础上，其中一处发生冲突。
    在 jj 中，**冲突可以直接记录在重写后的提交里，rebase 先完成，之后再处理这些冲突**。
    系统保存的是**冲突的逻辑表示**，仍然能够对它继续进行重写和合并。
    这样，'**调整历史结构**'和'**决定冲突处的最终内容**'就可以**分开安排**。」
  - ⭐⭐ 「这就是课堂所说的 **killer feature**：**冲突的存在不必把整个操作卡在半途中。**
    真正值得留意的是**抽象发生了什么变化**。
    **当一项过去被当作异常或临时过程的东西，可以被明确表示、保存和继续操作，
    许多流程就有机会统一起来。**」
  - 「老师拿自己开玩笑，说这就是 AI Native 能淘汰'老登'的原因：
    **Git 的肌肉记忆已经形成，即便理解新设计，也未必有足够时间重新训练一套习惯。**
    同学们反而可以倒过来学，**先理解更自然的抽象，再回望历史，理解旧设计为什么会出现。
    工具的熟练程度会过时，对设计前提的理解却可以带到下一套工具里。**」

⭐⭐ **"什么值得做成 first-class（一等公民）"** 是一条可迁移的设计判据。

jj 的方式：
    rebase 先完成 → **冲突作为状态被保存下来** → 你之后再处理

⭐ 讲义的判据（这是最值得学的一句）：
    "**当一项过去被当作异常或临时过程的东西，

    用你的经验对照：
    - 单片机里"错误码"从"直接停机"变成"一个可保存的状态"，

### V7 ★ Agent 并行：worktree 与"起个名字不会自动获得独立环境"

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§当开发者可以并行复制
- 要点：
  - ⭐ 「课堂把**人**戏称为 **single-threaded 生物**：我们只有一双手、一张嘴、一对眼睛。
    虽然能够同时惦记许多任务，**实际与开发环境交互的带宽相当有限**。
    对一个人来说，分支、stash 和工作区切换已经能支持不少场景。」
  - 「**Agent 改变了这个节奏。**一次范围合适的修改，可能在分钟级就推进到可以提交的程度；
    多个 Agent 还可以同时工作……**如果它们都操作同一份目录，某个 Agent 刚读过的文件
    可能被另一个改掉，测试正在运行时实现又发生了变化。**
    ⭐⭐ **给每个 Agent 起一个名字，并不会自动获得独立的开发环境。**」
  - 「一个自然的办法，是把每个 Agent 当成独立开发者，**各有一份仓库**，
    再把其他仓库配置为 remote，用来同步成果。Git 还提供了可以在本地使用的 **worktree**：
    **同一个仓库关联多个工作目录，各自拥有工作区、HEAD 和暂存区，
    同时共享仓库中的对象和大部分引用。**」
  - ⭐ 「这样，两个 Agent 可以分别在界面分支和记忆分支上开发，各自运行测试，再把成果整合起来。
    **新提交已经存在于共享的本地仓库中，无需互相 push、pull，
    修改仍然需要通过 merge 或 rebase 汇合。**
    ⚠️ 「**Worktree 减少了相互覆盖工作文件的问题，
    但任务之间的依赖仍然要管理**：界面等待什么数据格式，记忆模块什么时候能提供这个接口，
    双方是否采用了相同的错误处理约定，**都需要说明。**」

**【机制 / 为什么】** ✅ 材料给了机制和边界。

**【前置】** L3 U4（工作区/暂存区）、V2

**【标准范例】** —— 用他自己的经验
```
⭐ "single-threaded 生物"——你在调电机时就是这样：
    你只有一双手：改代码、编译、下载、看波形，**必须串行**
    同时"惦记"几件事 ≠ 同时做几件事

⭐ Agent 变了什么：
    它可以"分钟级"推进一个范围合适的修改
    → 于是"多个一起做"第一次变得可行

⚠️ 但讲义提醒的关键一句：
    "**给每个 Agent 起一个名字，并不会自动获得独立的开发环境**"
    → 三个 Agent 操作同一份目录 = 你刚读过的文件被别人改了

⭐ worktree 解决的问题：
    同一个仓库，**多个工作目录**（各自有工作区/HEAD/暂存区）
    共享对象和引用 → 各自跑测试，最后 merge/rebase 汇合
    ⚠️ 但**依赖仍要管理**：接口约定、什么时候能提供、错误处理约定
```

**【常见误解】**
1. 「多开几个 Agent 就等于并行开发环境」——❌ **起名字不等于隔离**
2. 「worktree 解决了并行问题」——只解决了**工作文件互相覆盖**；
   **任务之间的依赖仍要管理**
3. 「Agent 快所以人也能更快」——⚠️ 人仍是 single-threaded；
   **瓶颈在人这一侧**（对照 L2 T14）

**【适用边界】**
- ⚠️ 讲义说 worktree「共享仓库中的对象和大部分引用」——**"大部分"这个词背后有限制**，
  讲义未展开 → `【待查证】`

**【预考题】** ⭐ 用课堂原话
1. 【讲义原话·课堂提问】「如果主要使用者变成了能快速工作、还能并行复制的 Agent，
   原来的设计又有哪些前提需要重想？」
2. 让三个 Agent 同时改同一个目录，会出什么问题？

**【练习题 + 答案】**
- Q1（识别）：为什么说人是 single-threaded 生物？
  A1：**只有一双手、一张嘴、一对眼睛**；虽然能同时惦记许多任务，
  **实际与开发环境交互的带宽相当有限**。
- Q2（★ 关键）："给每个 Agent 起一个名字"为什么不够？
  A2：因为**起名字不会自动获得独立的开发环境**。
  若都操作同一份目录，**某个 Agent 刚读过的文件可能被另一个改掉**，
  **测试正在运行时实现又发生了变化**。
- Q3（应用）：worktree 解决了什么？没解决什么？
  A3：**解决**：同一仓库关联多个工作目录（各自有工作区/HEAD/暂存区），
  **减少相互覆盖工作文件的问题**。
  **没解决**：**任务之间的依赖仍然要管理**——接口何时可用、数据格式、错误处理约定。
- Q4（迁移）：你现在用 Keil 开两个工程副本改同一个模块，会遇到什么问题？和 one-repo-one-agent 像吗？
  A4（开放）：会互相覆盖、版本对不上——**和"多 Agent 同目录"是同一类问题**。

**【迁移题】**
如果你要同时做两件改动（改电流环 + 改上位机），怎么安排工作目录才不会互相干扰？

**【掌握判定】**
- 能说清：能说出 worktree 解决与未解决的问题，并复述"起个名字不会自动获得独立环境"
- 能应用：能安排一个"两个任务并行"的工作方式
- 能回忆：隔一天能说出 worktree 的隔离边界

### V8 ★★ 两种协调策略：先上锁 vs 先分开做

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§先分开做再合并，还是先上锁
- 要点：
  - 「回到最初的问题：**为什么需要版本控制？**人的生产速度有限，人和人之间沟通困难，
    沟通过后还会误解和出错。我们希望**保存可靠的状态，分小步前进，
    让不同方向可以独立探索，也让失败之后能够回查。**」
  - 「例如，**bisect** 可以利用一组可重现的好坏判断，**逐步缩小引入问题的提交范围**；
    **blame** 可以把当前代码行关联到相应的历史修改，帮助找到当时的上下文。
    **这些机制减少了对人的记忆的依赖。**」
  - ⭐ 「它们当然可以被用于找责任人，但在工程里，**更有用的问题往往是
    '这个决定当时为什么合理，现在什么前提变了'。**」
  - ⭐ 【课堂提问】「反正没有哪个 Agent 能被开除，**我们能不能再也不要 blame，
    只让它把事情推进、把问题修好？**……**如果执行者主要是可复制的 Agent，
    能不能减少围绕个人交接和事后协调的步骤，直接围绕项目状态组织工作？**」
  - ⭐⭐ **上锁方案**：「一种设计是由**主 Agent 负责规划**，把任务拆成边界明确的部分；
    **子 Agent 要修改某项共享资源时先取得互斥锁，读取最新状态，
    完成修改和必要检查，留下可恢复的快照，再释放锁。**
    **这里的锁是一套约定：同一时刻，只允许一个参与者修改约定范围内的状态。**」
  - ⭐⭐ **对照**：「这和版本管理中'**各自修改，汇合时再检查冲突**'的思路形成了有用的对照。
    课堂借数据库里的 **MVCC**……帮助理解后者：**保留多个版本，让工作先推进，
    再处理版本之间的关系。** ⚠️ **这是关于并发策略的类比；
    Git 的合并并不因此具有数据库事务的全部性质。**」
  - ⭐ 「'Agent 先上锁再干活'因此是一条**值得实验的设计路线**。它让我们看到，
    **协作可以在工作之前通过调度和互斥协调，也可以在工作之后通过版本和合并协调，
    还可以把两者结合起来。**
    ⚠️ **选择哪种机制，要看共享资源、冲突频率和返工代价，而不能只看参与者是不是 AI。**」

⭐⭐ **本讲最有价值的对照**：协调发生在**工作之前**还是**工作之后**。

**【机制 / 为什么】** ✅ 材料给了两种策略和选择依据。

**【前置】** V7、L3 U17（write skew）

**【标准范例】** —— ⭐ 用他一定做过的互斥
```
⭐ 你在单片机里做过这两种协调，只是没这么叫：

"工作之前协调"（互斥锁）：
    进临界区前 **关中断 / 拿信号量**
    → 确保同一时刻只有一个人在改
    → 完事再开中断 / 放信号量
    ⚠️ 代价：别人得等

"工作之后协调"（版本合并）：
    两个任务各自算，结果各放一份
    → 最后比较、取舍、合并
    → 谁也不用等谁
    ⚠️ 代价：最后可能冲突，要花时间处理

⭐ 讲义的关键提醒：
    主 Agent 规划 → 子 Agent **先取锁、读最新状态、改、留快照、放锁**
    ⭐ 注意"**读取最新状态**"这一步 —— 这正是防 write skew 的关键
       （L3 U17 的教训：基于旧快照决定，组合后破坏约束）
```

**【常见误解】**
1. 「应该用锁，因为更安全」——⚠️ 讲义明确：**要看共享资源、冲突频率、返工代价**，
   **不能只看参与者是不是 AI**
2. 「版本合并更好，因为不阻塞」——同样不能一概而论
3. 「blame 是用来找责任人的」——讲义说：**更有用的问题是"这个决定当时为什么合理，
   现在什么前提变了"**

**【适用边界】**
- ⚠️ 讲义明确：MVCC 只是**关于并发策略的类比**；
  **Git 的合并并不因此具有数据库事务的全部性质**
- ⭐ 讲义本人把"Agent 先上锁再干活"称为**"值得实验的设计路线"**，**不是结论**

**【预考题】** ⭐ 用课堂原话
1. 【讲义原话·课堂提问】「为什么需要版本控制？」
2. 让两个 Agent 都改同一份共享资源，你会让他们"抢锁"还是"各改各的再合并"？

**【练习题 + 答案】**
- Q1（识别）：为什么需要版本控制？（讲义给的四个理由）
  A1：**人的生产速度有限；人和人之间沟通困难，沟通过后还会误解和出错；
  我们希望保存可靠的状态、分小步前进、让不同方向独立探索、让失败之后能回查。**
- Q2（★ 应用）：两种协调策略分别发生在什么时候？
  A2：**"工作之前"通过调度和互斥协调**（先上锁）；
  **"工作之后"通过版本和合并协调**（先分开做再合并）。
  讲义说**还可以把两者结合起来**。
- Q3（★ 关键）：选择哪一种机制，依据是什么？
  A3：**要看共享资源、冲突频率和返工代价，而不能只看参与者是不是 AI。**
- Q4（★ 迁移）：你的速度环和电流环共享一个全局状态，两个中断都要改它。
  你会用哪种协调？为什么？
  A4：**工作之前协调**（关中断/信号量进临界区）——因为
  **冲突频率高**（每次控制周期都可能碰）、**返工代价高**（时序错会失控）。
  ⭐ 这正说明讲义那条依据的用处。

用"工作之前 / 工作之后"这个二分法，给你日常的两个协作场景各选一种策略并说明依据。

**【掌握判定】**
- 能说清：能说出两种策略的时机差别和选择依据
- 能应用：能依据"共享资源/冲突频率/返工代价"选一种
- 能回忆：隔一天能复述"协作可以在工作之前通过调度和互斥协调，也可以在工作之后通过版本和合并协调"

### V9 ★ 上锁的代价（★ 本讲唯一提到"操作系统课"的地方）

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§先分开做再合并，还是先上锁
- 要点：
  - ⭐ 「**上锁也有代价。锁住整个项目很简单，但可能把并行工作重新排成串行；
    只锁一个文件比较灵活，却未必覆盖跨文件的不变量。**
    例如**接口定义和调用方必须一起更新，只锁其中一个文件就不够。**」
  - ⭐⭐ 「**Agent 意外停止时，锁如何回收？一个任务同时需要两项资源时，怎样避免互相等待？
    后一个任务拿到锁后，有没有继续使用等待之前读到的旧内容？
    这些都是操作系统和数据库课里熟悉的问题。**」
  - 「**历史仍然有助于恢复和诊断，修好问题也仍然需要能够检验的结果。**」

**⚠️ 关键教学判断**：讲义说"这些都是**操作系统和数据库课**里熟悉的问题"——
**但他没上过这两门课。** 必须用单片机的临界区经验补上。

**【机制 / 为什么】**
- 材料给了三条代价（粒度、跨文件不变量、以及三个开放问题）
- ⚠️ **缺口：讲义把三个问题"抛"出来，没有给答案**（"这些都是……课里熟悉的问题"）

**【前置】** V8、L3 U17

**【标准范例】** —— ⭐ 用他一定踩过的坑
```
⭐ 讲义的三个问题，用单片机的语言就是：

① 锁的粒度
    "锁住整个项目"     ≈ **关总中断**（最简单，但实时性全毁）
    "只锁一个文件"     ≈ **只关某一个外设中断**（灵活，但保护不了跨外设的约束）
    ⚠️ "接口定义和调用方必须一起更新，只锁其中一个文件就不够"
       ≈ 你改了一个 .h 的接口签名，**所有调用方必须同时改**
         → 只保护 .h 没有用

② 锁如何回收（Agent 意外停止）
    ≈ **中断里拿了信号量却没释放，然后又死掉了**
      → 系统永久卡死
    ⚠️ 这是他一定遇到过的

③ 死锁（"同时需要两项资源，怎样避免互相等待"）
    ≈ 任务 A 拿了 UART 等 SPI，任务 B 拿了 SPI 等 UART
    ⚠️ 讲义明说这是**开放问题**，需要设计

④ 拿到锁后用旧读数
    ⭐ "**后一个任务拿到锁后，有没有继续使用等待之前读到的旧内容？**"
       ≈ 你在等锁之前读了变量的值，拿到锁后**没有重新读**就直接用
         → **这正是 L3 U17 的 write skew**

⚠️ 讲义把这三个问题列出来**但没有给答案**——
   因为它是在指出"这条设计路线还有哪些没解决"
```

**【常见误解】**
1. 「上锁就安全了」——❌ 有粒度、回收、死锁、旧读数四个问题
2. 「锁住整个项目最安全」——⚠️ **"可能把并行工作重新排成串行"**
3. 「只锁一个文件最灵活」——⚠️ **"未必覆盖跨文件的不变量"**

**【适用边界】**
- ⚠️ **缺口：讲义明确把三个问题留作开放问题，未给答案**
  （L3 U17 给了一条对策：**检查组合结果 / 更强的并发控制**）
- ⚠️ 讲义说这些是"操作系统和数据库课里熟悉的问题"——**本教案必须补上单片机语境的对照**，
  否则学习者无法接住（见【标准范例】）

**【预考题】** ⭐ 用课堂原话
1. 【讲义原话·课堂提问】「Agent 意外停止时，锁如何回收？」
2. 【讲义原话·课堂提问】「一个任务同时需要两项资源时，怎样避免互相等待？」
3. 【讲义原话·课堂提问】「后一个任务拿到锁后，有没有继续使用等待之前读到的旧内容？」

**【练习题 + 答案】**
- Q1（识别）：上锁的两条代价是什么？
  A1：**① 锁住整个项目 → 可能把并行工作重新排成串行；
  ② 只锁一个文件 → 未必覆盖跨文件的不变量**
  （例如接口定义和调用方必须一起更新）。
- Q2（★ 关键）："后一个任务拿到锁后，有没有继续使用等待之前读到的旧内容？"——
  这个问题对应你已经学过的什么？
  A2：对应 **L3 U17 的 write skew**：**各自依据旧快照作出的决定，组合后破坏了共同约束**。
  所以上锁方案里讲义特意写了"**读取最新状态**"这一步。
- Q3（应用）：你在中断里用信号量，如果中断里发生了异常没释放，会怎样？
  A3：**系统卡死**（锁无法回收）。所以实际工程里要小心：不在临界区做可能失败的操作、
  用超时/看门狗、或改用关中断等更简单的保护。
- Q4（迁移）：两个任务互相等待对方持有的资源，这种局面在单片机里怎么避免？
  A4（开放）：**统一加锁顺序**（所有任务按同一顺序申请资源）、
  减少同时持有的资源数、用超时机制。

**【迁移题】**
给你自己的中断/任务设计一套"加锁顺序"规则，避免死锁。

**【掌握判定】**
- 能说清：能说出上锁的两条代价和三个开放问题
- 能应用：能判断一个上锁方案会不会造成串行化或覆盖不了不变量
- 能回忆：隔一天能说出"历史仍然有助于恢复和诊断"

### V10 ★ 人多以后：沟通关系的平方级上升

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§人多以后，困难转移到了协作
- 要点：
  - ⭐ 「**版本管理终究只是工具。真正困难的，是团队怎样持续朝着同一个目标前进。**」
  - 「若 **n 个成员都可能需要两两沟通，潜在的沟通关系有 n(n−1)/2 条**：
    3 人是 3 条，6 人就有 15 条。这解释了'**平方级上升**'的直觉。
    ⚠️ **它数的是潜在关系，并不意味着每个团队的实际耗时都严格服从这个公式；
    清楚的接口和组织分工，正是在减少必须直接协调的关系。**」
  - ⭐ 「一个常见场景是，**每个人都觉得自己的部分很清楚**。
    界面已经能展示模拟数据，后端已经通过自己的测试，
    **但两边对字段含义和失败情况的理解不同。**
    另一个场景，大家都说任务'基本完成'，**有人指代码写完，有人指测试通过，
    有人则以为已经可以部署**。还有人**为了等待上游决定不断改计划，
    上游却不知道自己的延迟挡住了谁。**
    **代码量增长了，项目离可用状态的距离却没有按同样速度缩短。**」
  - ⭐ 「**分歧也可能出现在目标和责任上。**一个人要赶紧上线，另一个人要趁机重构，
    两个人都觉得自己在帮项目。**界面、接口、测试分别有人负责，
    跨模块的问题却可能落在分工的缝隙里。**
    **此时，再多几个提交也不能自动确定优先级，或者替团队找到愿意把整件事接起来的人。**」
  - ⭐ 「版本管理留给我们的启发，是**把项目看成一个持续演化的过程**：
    **保存当前状态，保留走到这里的历史和教训，允许多条探索路线存在，
    并设计它们重新汇合的办法。**」

**【机制 / 为什么】** ✅ 材料给了机制（潜在关系数）和四个具体失败场景。

**【前置】** V8、V9

**【标准范例】** —— 用一个团队协作的真实场景
```
⭐ 讲义的四个失败场景，你大概都见过：

① 字段含义不同：
   上位机以为 speed 是"目标转速"，下位机当成"实际转速"
   → 两边各自测试都通过，**合起来不对**

② "基本完成"的含义不同：
   你说"代码写完了"，硬件同事说"还没上板验证"
   ⭐ 这正是 L2 T4「写清楚完成是什么」在团队层面的版本

③ 上游延迟挡住下游却没人知道：
   你在等硬件确定引脚分配，硬件同事不知道你在等

④ 目标与责任分歧：
   你要先把功能跑通，同事要先重构
   ⭐ 讲义："**跨模块的问题却可能落在分工的缝隙里**"
```

**【常见误解】**
1. 「人多了加几个提交就行」——❌ 讲义明确：**"再多几个提交也不能自动确定优先级"**
2. 「n(n−1)/2 就是团队耗时的公式」——⚠️ 讲义明确：**"它数的是潜在关系"**，

### V11 Git 记录解题过程（识别现成工具能接住哪一部分）

### V12 ★ 空项目更难 + 早期 prompt 成为默认前提

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§从零开始，你就是包工头
- 要点：
  - ⭐ 「**从零开始做产品，有时比参与一个成熟开源项目更难。**
    成熟项目已经固定了许多选择：用户是谁，代码怎样分层，什么叫兼容，测试怎样运行……
    **空项目里的约束少，自由度大，Intent、Spec、Impl 之间的缺口
    也就有更多机会被默认选择填满。**」
  - ⭐ 【课堂提问】「'会成长的个人助手'至少留下了几个决定：
    **成长指记住事实、修正偏好，还是学会执行新任务？助手什么时候应该主动行动？
    记错了以后怎样纠正？**」
  - ⭐ 「如果一开始就把所有记忆都设计成永久有效，后来才发现大量信息有时间和场景限制，
    **早期那个看起来很确定的数据结构，就把一项需求误解固定进了实现。**」
  - ⭐⭐ 「**早期 prompt 对项目走向的影响尤其大。第一次描述里的'确定设计'，
    往往会成为以后代码和讨论的默认前提。接下来的 Agent 读到现有实现，
    又会顺着它继续生成。一个方便的临时选择，可能就这样逐渐变成 technical debt，
    也就是未来修改系统时必须额外偿还的技术债。**」
  - ⚠️ 「技术债也可能**来自认识的进步**。第一版的设计在当时有充分理由，
    真正做出来、用起来之后，团队才知道哪些概念应当分开、哪些接口应当重新组织。
    Martin Fowler 在 Technical Debt Quadrant 中讨论过这种情况：
    **即使团队认真设计，也可能在学习之后发现原来的结构已经落后于新的理解。**
    **值得关注的是怎样记录这个发现，以及何时调整结构。**」`【待查证·引注未核】`

    后来发现"有些偏好只在某段时间内有效"
    → **早期那个结构就把这个误解固定住了**

⭐⭐ 关于"早期 prompt"：

### V13 ★ "没有什么是不能变的" → 判据：能否承受需求变化

**【讲义原话】**
- 出处：§从零开始，你就是包工头
- 要点：
  - 「这不意味着应该先把所有未来需求都想清楚。课堂给出的准则很直接：
    ⭐ **没有什么是不能变的。**
    **所谓'以不变应万变'，落到软件上，就是它能否承受需求变化。**」
  - ⭐ 【课堂提问】「**能不能替换一项记忆策略，而不用重写全部界面？
    能不能增加一种输入方式，而不把核心行为复制一份？**」
  - 「我们可以**围绕已经看见的变化组织边界，再用实际反馈修正设计。**」

⭐⭐ **判据直接接上 L1 S15「修改的局部性」**——只是换了个问法。

**【机制 / 为什么】** ✅ 材料给了准则和两个具体问句。

**【前置】** V12、L1 S15（修改的局部性）

**【标准范例】** —— 直接对照他学过的
```

    → 换成你学过的说法：
      **改一处，会不会迫使整个系统重来？**
      **改动有没有局部性？**

⭐ 也用你可以直接验证的方式问：
    你换一种无感算法（SMO→EKF），要改多少地方？

```

**【常见误解】**
1. 「"没有什么是不能变的" = 所以不用设计」——不是。讲义说
   **"围绕已经看见的变化组织边界"**
2. 「要把所有未来需求都想清楚」——❌ 讲义明确否定
3. 「以不变应万变 = 设计一个万能架构」——❌ 讲义给了实用的解释：
   **能否承受需求变化**

**【适用边界】**
- ⚠️ 讲义说"围绕**已经看见的**变化组织边界"——**未看见的变化怎么办**，讲义未给方法

**【预考题】** ⭐ 用课堂原话
1. 【讲义原话·课堂提问】「能不能替换一项记忆策略，而不用重写全部界面？」
2. 【讲义原话·课堂提问】「能不能增加一种输入方式，而不把核心行为复制一份？」

**【练习题 + 答案】**
- Q1（识别）：讲义给的准则是什么？"以不变应万变"落到软件上指什么？

- Q2（★ 应用）：你换一种无感算法，需要改动哪些地方？这个"要改多少地方"说明了什么？
  A2：如果只换一个模块 → **局部性成立**；如果要动界面/电流环/上位机 →

  A3：**① 换掉其中一项，能不能不重写其他部分？
  ② 增加一种新的（输入/输出/策略），能不能不复制核心行为？**
  —— 本质上就是**改动有没有局部性**。

**【迁移题】**
用这两个问句评估你项目的一个模块，并给出改造方向。

**【掌握判定】**
- 能说清：能说出准则和它的实用解释
- 能应用：能用两个问句评估一个设计
- 能回忆：隔一天能说出"以不变应万变，落到软件上就是它能否承受需求变化"

### V14 ★★ MVP：开工前先写两个问题

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§用一个最小版本检验想法
- 要点：
  - ⭐ 「**任何时候，开始都比不开始强。**
    一个有用的开始方式是 **MVP，Minimum Viable Product，也就是最小可行产品**：
    **做出足够小、又能真正投入使用的版本，检验最关键的假设。**」
  - ⭐⭐ 【课堂提问】「**开工前可以先写下两个问题：这个版本要验证什么？
    出现什么结果，就说明我们想错了？**」
  - 「Eric Ries 对 MVP 的解释强调，**用尽可能少的投入获得经过验证的认识**。
    **只有事先说明需要什么证据，做出第一版之后，才更容易判断应该继续完善，
    还是改变方向。**」`【待查证·引注未核】`
  - ⭐ 「个人助手的第一版不必包揽邮件、日程、浏览器和所有长期记忆。
    比如，**可以先选择一个你每天都会遇到的场景：记录一项偏好，
    在下一次相关任务中使用它，并允许你纠正。**
    这个版本可以很粗糙，但**你能亲自观察它有没有帮忙、记忆有没有被正确利用、
    纠正之后是否真的改变了行为。**」
  - ⭐ 「一旦开始使用，**原先隐藏在形容词里的问题就会变得具体。**
    '**更主动一点**'可能意味着每天固定时间提醒，也可能意味着只在发现明确的遗漏时提示；
    '**更了解我**'可能需要记住长期偏好，也可能首先需要学会忘掉一次性的指令。
    **真实使用产生的这些分歧，会反过来检验早期的规格和架构。**」

⭐⭐ **"开工前写两个问题"是本讲最可操作的一点**，而且直接接上 L2 T4。

**【机制 / 为什么】** ✅ 材料给了机制（之前说明证据 → 之后才能判断该继续还是转向）。

**【前置】** L2 T4（写清"完成"是什么）、V12、V13

**【标准范例】** —— 用他做视频/做项目的经验
```
⭐ 讲义的两个问题，直接可用：

    "这个版本要验证什么？"
    "出现什么结果，就说明我们想错了？"

⭐ 例（个人助手）：
    要验证：**记忆被纠正后，行为是否真的改变**
    想错了的证据：纠正了但下次还是犯同一个错
        → ⚠️ 如果出现这个结果，说明方案有问题，**该换方向而不是继续完善**

⭐ 用你的经历对照（做视频）：
    "这期视频要验证什么？"  → 比如"这个选题有没有人看"
    "出现什么结果就说明想错了？" → 播放量低于 X 且完播率低
    ⚠️ **事先说清，才不会被"辛苦做完了"绑架**

⚠️ 讲义那句最重要的：
    "**只有事先说明需要什么证据，做出第一版之后，
     才更容易判断应该继续完善，还是改变方向。**"
    ← 这正是 L2 T4「写清楚完成是什么」的**另一个应用场景**
```

**【常见误解】**
1. 「MVP = 做的少」——❌ 是"**足够小、又能真正投入使用**"，
   目的是**检验最关键的假设**
2. 「先做出来再想验证标准」——❌ 讲义明确：**要事先说明需要什么证据**
3. 「MVP 就是一个粗糙版本」——关键是**能亲自观察**：
   有没有帮忙、有没有被正确利用、纠正后是否真的改变行为

**【适用边界】**
- ⚠️ Eric Ries 的 MVP 解释引注**未核对原文** → `【待查证·引注未核】`
- ⚠️ **缺口：讲义未给"如何选最关键假设"的方法**
  （只给了做法：选一个每天都会遇到的场景）

**【预考题】** ⭐ 用课堂原话
1. 【讲义原话·课堂提问】「这个版本要验证什么？」
2. 【讲义原话·课堂提问】「出现什么结果，就说明我们想错了？」

**【练习题 + 答案】**
- Q1（识别）：MVP 是什么？
  A1：**最小可行产品**——**做出足够小、又能真正投入使用的版本，检验最关键的假设**；
  强调**用尽可能少的投入获得经过验证的认识**。
- Q2（★ 关键）：为什么MVP 要"开工前先写两个问题"？
  A2：因为**只有事先说明需要什么证据，做出第一版之后，
  才更容易判断应该继续完善，还是改变方向**。
  ⚠️ 否则就会被"已经做了这么多"绑架，**分不清是该继续还是该转向**。
- Q3（应用）：为"会成长的个人助手"第一版写这两个问题。
  A3（示例）：**要验证**：记忆被纠正后行为是否真的改变。
  **想错了的证据**：纠正之后下次仍然犯同一个错。
- Q4（★ 应用）：为什么"更主动一点""更了解我"这类需求，**要先做出来才知道具体指什么**？
  A4：因为**一旦开始使用，原先隐藏在形容词里的问题就会变得具体**：
  "更主动"可能指固定时间提醒，也可能指发现明确遗漏时提示；
  "更了解我"可能需要记住长期偏好，也可能首先是**学会忘掉一次性指令**。
- Q5（迁移）：你下一个小项目的 MVP 是什么？写两个问题。
  A5（开放）。

**【迁移题】**
为你手上的一个项目写 MVP 的两个问题，并明确"继续"与"转向"的分界。

**【掌握判定】**
- 能说清：能说出 MVP 的定义和"先写两个问题"的理由
- 能应用：能为一个项目写出这两个问题
- 能回忆：隔一天能复述"只有事先说明需要什么证据，才更容易判断应该继续完善，还是改变方向"
