### U1 目录 ≠ 项目：为什么需要版本管理

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§一个目录，为什么还不算管好了项目
- 要点：
  - 「从最朴素的角度看，软件工程项目就是**一个目录**，目录里有文件：
    需求说明表达意图，接口文档和测试描述规格，源代码承担实现，构建脚本把它们组织起来。」
  - 「优盘坏了，代码也就没了。」
  - ⭐ 「即使优盘不坏，也还有别的问题。**昨天的版本能运行，今天改坏了，怎样回去？
    一个功能改了一半，突然需要修复另一处错误，怎样暂时放下它？
    你和同学从同一份代码出发，各自修改了一些文件，怎样把结果汇合起来？**」
  - 「这些需求自然引出了版本管理：**除了保存项目现在的样子，还要保存它经过哪些状态，
    以及这些状态之间的关系。**」

**【机制 / 为什么】** ✅ 材料给了三个具体需求（回退 / 暂存 / 汇合），没有停在"备份"上。

**【前置】** 无

**【标准范例】** —— 用他做硬件的经历
```
你调 FOC 时的真实情况：
    参数改到第 7 版终于跑通了 → 又想试第 8 版 → 结果第 8 版更差
    → "第 7 版是哪几个参数来着？"

你现在的做法大概是这样：
    motor_v1.c / motor_v2.c / motor_final.c / motor_final_真的final.c
    → 能找回文件，但"谁从哪份改来"要靠你记

⭐ 三个需求（讲义给的）：
    ① 回退    ：昨天能跑，今天改坏了，怎么回去？
    ② 暂存    ：功能改一半，突然要修别处，怎么放下？
    ③ 汇合    ：两个人从同一份代码各自改，怎么合并？
```

**【常见误解】**
1. 「版本管理 = 备份」——不够。还要保存**状态之间的关系**（谁从哪来）
2. 「我有网盘/优盘同步就够了」——解决不了②和③
3. 「小项目不需要」——讲义用的例子正是"只有 `hello.c`"的最小学生作业

**【适用边界】**
- ⚠️ 讲义**没有说"什么规模的项目才需要版本管理"**。但它举的失败案例是**大一的作业**，
  暗示门槛极低。

**【预考题】**
1. 你现在怎么管理单片机代码的版本？遇到过什么问题？
2. 除了"怕丢"，还有什么原因需要版本管理？

**【练习题 + 答案】**
- Q1（识别）：讲义说版本管理要保存哪两样东西？
  A1：**① 项目现在的样子；② 它经过哪些状态，以及这些状态之间的关系。**
- Q2（应用）：讲义列的三个问题分别是什么？各自对应你现在哪种做法？
  A2：**① 回退（改坏了怎么回去）② 暂存（改一半怎么放下）③ 汇合（各自改怎么合并）**。
  对应做法通常是：① 存多个副本 ② 靠记忆/注释掉 ③ 手工对照合并。
- Q3（迁移）：你 B站 视频工程文件（PR/AE 工程）遇到过类似问题吗？
  A3：（开放）版本多、素材变动、多人协作（封面/字幕）——**同一类问题**。

**【迁移题】**
说出你工作里一次"因为没有版本管理而损失时间"的具体经历。

**【掌握判定】**
- 能说清：能说出三个需求，并解释"保存状态之间的关系"指什么
- 能应用：能判断一个场景属于回退/暂存/汇合哪一类需求
- 能回忆：隔一天能说出这三个问题

### U2 学习变容易以后，"留意"变得更重要

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§学习变容易以后，留意变得更重要
- 要点：
  - 「看到很多项目，**不会自动把它们的设计变成自己的知识**。
    你可能打开过几十个仓库，却没有注意过它们如何组织目录，为什么保留某些文件，
    又为什么忽略另一些文件。」
  - ⭐ 「一个很有效的技巧是 **virtually implement：先在脑子里做一遍**。
    读论文时，看到作者提出的问题，先停下来想：**换成我，会怎样解决？需要哪些前提，
    可能在哪里失败？**然后再看作者的方案。**如果想法一致，就可以比较实现细节；
    如果不一致，就追问差异来自哪个约束、哪条自己不知道的经验。**」
  - 「**学习知识的门槛降低了，主动发现自己不知道什么的意识，就更重要了。**」

**【机制 / 为什么】** 材料给了方法（virtually implement）和判据（一致→比细节；不一致→追约束）。

**【前置】** L2 T3（AI 降低开始学习的成本）——本点是它的**配套方法**

**【标准范例】** —— 用他的领域
```
你在看一篇 FOC 无感控制的论文时：

❌ 直接读：
    "哦，他用 EKF 估计转速" → 读完还是不会用

✅ virtually implement（讲义的方法）：
    ① 先停下，问自己：换成我，怎么估转速？
       → 我会用反电动势 + 锁相环
    ② 再读作者方案 → 他用 EKF
    ③ 一致？→ 比细节（他的噪声模型怎么建的）
       不一致？→ 追问：差异来自哪个约束？
                  （是因为低速时反电动势太小？还是我需要辨识参数？）
```
> ⭐ 关键：**先预测，再看答案。** 这和你做预考题是同一个机制——
> 备课方法论 的第 2 步"预考"用的也是它（按 备课流程：先测后学优于学完再测）。

**【常见误解】**
1. 「看得多就会了」——讲义明确否定：**看过不等于变成自己的知识**
2. 「virtually implement 是浪费时间」——它**恰恰是让阅读有产出的那一步**
3. 「只要预测对了就说明我会了」——讲义说：**一致时要比实现细节**，不是结束

**【适用边界】**
- 讲义举的应用面很宽（读论文、读代码、看文档、**读 AI 生成的一段话**）
- ⚠️ **缺口：讲义未给"预测明显失败时该怎么办"的处理**（不一致时讲义说追问约束，但没给路径）

**【预考题】**
1. 你读过很多技术文章，哪些真正变成了你的能力？为什么？
2. 读别人的代码，怎么读才能学到设计？

**【练习题 + 答案】**
- Q1（识别）：virtually implement 是什么？
  A1：**先在脑子里做一遍**——看到作者提出的问题，先停下想"换成我会怎么解决、
  需要哪些前提、可能在哪里失败"，然后再看作者的方案。
- Q2（应用）：virtually implement 之后，"一致"和"不一致"分别该做什么？
  A2：**一致 → 比较实现细节**；**不一致 → 追问差异来自哪个约束、哪条自己不知道的经验**。
- Q3（迁移）：你准备一节视频课，怎么用这个方法检验自己？
  A3：先想"讲这个知识点我会怎么讲"，再对照别人的讲法；
  **一致的地方比细节，不一致的地方追问自己缺了什么**。

**【迁移题】**
挑一个你正在学的技术点，先写下你的预测，再去查资料对照。

**【掌握判定】**
- 能说清：能说出方法的两个步骤和两种结果的处理
- 能应用：能对一个材料实际做一次 virtually implement
- 能回忆：隔一天能复述"主动发现自己不知道什么的意识，就更重要了"

### U3 ★ Git 管理的是「项目快照」

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§从"我想撤销"推导出快照
- 要点：
  - ⭐ 「最需要建立的概念是：**Git 管理项目的快照。**
    快照描述**纳入版本管理的文件在某个状态下的内容和目录位置**。」
  - ⭐ 「**为什么要以项目为单位？因为源代码、接口和配置经常要一起变化。
    只恢复旧代码，却留下新配置，可能拼出一个历史上从未正常运行过的版本。**」
  - 「一次**提交（commit）**把这样的快照与**作者、说明、父提交**等信息联系起来。
    **父提交记录它从哪里来，于是一个个状态构成了历史。**」
  - 「你删除一个已经提交过的文件，再提交一次，新快照里虽然没有它，
    **仍被保留的旧快照里却还有**。编辑器里'存过盘'和 Git 里'提交过'，
    **保存的是不同层次的状态**。」
  - 「Git 也**不需要为每个快照机械复制全部文件**。它用对象保存内容和目录结构，
    未变化的部分可以复用；**逻辑上是完整快照，存储上可以共享数据**。」

**【机制 / 为什么】** ✅ 材料给了完整机制，包括"为什么以项目为单位"。

**【前置】** U1

**【标准范例】** —— 用单片机语言
```
快照 ≈ 一次把受管文件"打包存到 Flash"
    内容 = 文件的内容 + 目录结构
    commit ≈ 这次保存 + 是谁存的 + 一句说明 + 上一次保存的编号

"为什么以项目为单位"：
    你保存 FOC 参数时，如果只存了 PID 参数、没存采样频率，
    下次按这份参数跑，行为可能和当时完全不同
    → 讲义原文：**"只恢复旧代码，却留下新配置，
       可能拼出一个历史上从未正常运行过的版本"**

"存储上可以共享数据"：
    就像增量固件升级 —— 逻辑上是完整的一版，
    实际只传输/保存变化的部分
```

**【常见误解】**
1. 「Git 存的是"每次的差异」——⚠️ 讲义说的是**快照**；
   "逻辑上是完整快照，存储上可以共享数据"（这是 Git 与早期 diff 式系统的关键差别）
2. 「保存 = 提交」——讲义明确区分：**编辑器"存过盘"和 Git"提交过"是两个层次**
3. 「删了文件就没了」——**旧快照里还有**

**【适用边界】**
- ⚠️ **缺口：讲义未展开 Git 对象模型（blob/tree/commit 的具体关系）**，
  只在 §让工具把真实细节展开 里顺带提到。本讲不要求掌握对象层细节。

**【预考题】**
1. 你按 Ctrl+S 保存了文件，这件事和"提交"有什么区别？
2. 为什么 Git 要以"整个项目"为单位，而不是只保存单个文件的历史？

**【练习题 + 答案】**
- Q1（识别）：Git 管理的基本单位是什么？它包含什么？
  A1：**项目的快照**——受管文件在某个状态下的**内容和目录位置**。
- Q2（应用）：为什么"只恢复旧代码、留下新配置"是危险的？
  A2：因为**源代码、接口和配置经常要一起变化**，混搭可能拼出
  **历史上从未正常运行过的版本**。
- Q3（应用）：一次 commit 除了快照，还关联哪些信息？
  A3：**作者、说明、父提交**。父提交记录"它从哪里来"，一个个状态构成历史。
- Q4（迁移）：你如果把 FOC 的 C 代码存了版本、但 Keil 工程配置没存，
  会出现讲义说的哪种问题？
  A4：**内部代码和工程配置不一致**——可能编译不出当时的固件，或行为不同。

**【迁移题】**
回看你项目里"只换了一部分"的某个版本，说明它可能拼出什么"从未正常运行过的版本"。

**【掌握判定】**
- 能说清：能说出快照的含义、"为什么以项目为单位"、commit 的四个关联信息
- 能应用：能判断一个"混搭恢复"是否危险
- 能回忆：隔一天能说出"逻辑上是完整快照，存储上可以共享数据"

### U4 ★★ 工作区 / 暂存区 / 提交历史

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§从 init、add、commit 到分支与合并
- 要点：
  - ⭐ 「接下来要区分三个东西。**工作区**是你正在编辑的文件；
    **暂存区（Staging Area，也叫 Index）**保存下一次提交准备采用的内容；
    **提交历史**保存已经记录下来的快照。」
  - 「`git add hello.c` 会把**此刻** `hello.c` 的内容放入暂存区，
    普通的 `git commit` 再据此创建提交。」
  - ⭐⭐ 「因此有一个很值得亲手试的问题：**先修改 `hello.c`，执行 `git add hello.c`，
    然后又修改它，最后执行 `git commit`，提交的是哪个版本？**
    **答案是 add 时暂存的版本。**后续修改仍然在工作区，要再次 add 才会进入这次提交。」
  - 「可以用 `git diff` 观察尚未暂存的修改，用 `git diff --cached` 观察暂存区相对
    当前提交的变化。**暂存区让你能够组织一次提交的内容，
    而不是被迫把此刻所有编辑一并记录下来。**」

⭐⭐ **本讲最容易答错、也最能说明"三层结构"的一点。**

**【机制 / 为什么】** ✅ 材料给了完整机制，并给了"为什么要暂存区"（组织一次提交的内容）。

**【前置】** U3

**【标准范例】** —— 用单片机语言，一次讲清
```
你可以这样理解三层（不严格对应，但好记）：

    工作区      = 你正在改的 RAM 里的内容（还没确认）
    暂存区      = "准备写进这次保存"的缓冲区（你已经挑好要保存哪些改动）
    提交历史    = 已经写进 Flash 的各个版本

⭐ 讲义那个问题，换成你的场景：
    ① 把 PID 的 Kp 从 1.0 改成 1.2       ← 改工作区
    ② "记下这个改动"                      ← add（此刻的 Kp=1.2 进了暂存区）
    ③ 又把 Kp 改成 1.5                    ← 再改工作区
    ④ 提交
    → 提交进去的是 **1.2**，不是 1.5
    → 1.5 还在工作区里，没进这次提交
```

**【常见误解】**
1. 「commit 提交的是当前文件的样子」——❌ **提交的是 add 那一刻暂存的内容**
2. 「暂存区是多余的一步」——它让你**组织一次提交的内容**，而不是被迫把此刻所有编辑一并记录
3. 「`git diff` 看的是暂存区」——❌ `git diff` 看**尚未暂存**的修改；
   看暂存区要用 `git diff --cached`

**【适用边界】**
- ⚠️ 讲义给了"要区分三个东西"，但**没给三者的操作全景**（那属于工具手册）

**【预考题】**
1. `git add` 之后又改了文件，`git commit` 提交的是哪个版本？
2. 为什么要有"暂存区"这一步，不能直接提交工作区的内容吗？

**【练习题 + 答案】**
- Q1（识别）：三个东西分别是什么？
  A1：**工作区**（正在编辑的文件）/ **暂存区**（下一次提交准备采用的内容，也叫 Index）/
  **提交历史**（已经记录下来的快照）。
- Q2（★ 应用）：改 → add → 再改 → commit，提交的是哪个版本？
  A2：**add 时暂存的那个版本**。后续修改仍在工作区，要再次 add 才会进入这次提交。
- Q3（应用）：想看"还没暂存的修改"和"暂存区相对当前提交的变化"，分别用什么？
  A3：`git diff` 看**尚未暂存**的修改；`git diff --cached` 看**暂存区相对当前提交**的变化。
- Q4（★ 关键）：暂存区存在的价值是什么？
  A4：**让你能够组织一次提交的内容**，而不是被迫把此刻所有编辑一并记录下来。
  ——这直接连到 U15 的"原子变更"。

**【迁移题】**
用你自己的话解释："暂存区是为了让提交有边界。"这句话和 L1 的"修改的局部性"有什么共同点？

**【掌握判定】**
- 能说清：能说出三层的区别，并正确回答 add-modify-commit 那一题
- 能应用：能预测一次 add/commit 序列的结果
- 能回忆：隔一天能说出暂存区的作用

### U5 分支、合并、fast-forward、rebase

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§从 init、add、commit 到分支与合并
- 要点：
  - 「可以把**分支名理解为指向某个提交的可移动引用**；在通常的分支工作方式下，
    **`HEAD` 表示当前所在的分支**。你在这个分支上创建新提交，分支引用就向前移动。」
  - 「`git merge` 会**结合共同祖先和双方的变化**，尝试得到合并结果。
    双方已经分叉时，常见结果是创建一个**有两个父提交的合并提交**；
    如果一方只是另一方的后续，Git 也可能只把分支引用向前移动，这叫 **fast-forward**。」
  - 「`git rebase` 则**把一串提交所代表的改动，依次重放到新的起点上**……
    **重放得到的提交通常有新的标识**，过程中也可能冲突。
    它适合在**约定允许的范围内**整理工作；
    **如果别人已经依赖原来的提交，你再改写它们，就会增加协作成本。**」

**【机制 / 为什么】** ✅ 材料给了机制（引用移动 / 结合共同祖先 / 重放）。

**【前置】** U4

**【标准范例】** —— 用他自己的场景
```
分支 = 指向某个提交的"可移动标签"

    main:    A─B─C
                       ↘ 你在改界面
    feature-ui:          D─E

"可移动"的意思：你在 feature-ui 上提交一次，这个引用就往前走一格

merge：把两条线的变化结合
    - 分叉了 → 产生一个**有两个父提交**的合并提交
    - 只是后续 → 直接前移，叫 **fast-forward**

rebase：把你那两次改动**重新放到新起点上**
    ⚠️ 会产生**新的提交标识**（等于换了个历史）
    ⚠️ 别人已经依赖旧提交时，你再改写 → 增加协作成本
```

**【常见误解】**
1. 「分支是复制一份代码」——不是。**分支只是一个指向提交的可移动引用**
2. 「merge 和 rebase 效果一样」——不一样：**merge 保留分叉，rebase 重写历史**
3. 「rebase 更干净所以应该总是用」——讲义明确指出**协作成本**风险

**【适用边界】**
- 讲义说 rebase「适合在**约定允许的范围内**整理工作」——**取决于团队约定，不是技术优劣**

**【预考题】**
1. 分支到底是什么？（是复制代码吗？）
2. rebase 之后，提交标识（那个编号）会变吗？这对别人有什么影响？

**【练习题 + 答案】**
- Q1（识别）：分支名在 Git 里是什么？
  A1：**指向某个提交的可移动引用**；`HEAD` 表示当前所在的分支。
- Q2（应用）：什么情况下 merge 会产生一个"有两个父提交的合并提交"？什么情况只前移？
  A2：**双方已经分叉** → 产生合并提交；**一方只是另一方的后续** → 只把分支引用向前移动
  （fast-forward）。
- Q3（应用）：`git rebase` 做了什么？为什么要小心？
  A3：**把一串提交代表的改动依次重放到新起点**。重放后的提交**有新的标识**；
  若**别人已经依赖原来的提交**，改写它们会**增加协作成本**。
- Q4（迁移）：你如果在自己机器上 rebase 了已经推到公司仓库的分支，同事会遇到什么？
  A4：他们本地的历史与远端**对不上了**——同一个改动变成了两个不同的提交，
  合并时会产生大量无意义的冲突。**这就是"协作成本"。**

**【迁移题】**
说出"合并（保留分叉）"和"重放（改写历史）"各自适合的场景。

**【掌握判定】**
- 能说清：能说出分支是引用、merge 与 rebase 的差别
- 能应用：能预测一次 merge 会前移还是产生合并提交
- 能回忆：隔一天能说出 rebase 的协作成本

### U6 ★ 合并冲突：看到什么、怎么解决

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§从"我想撤销"推导出快照 / §从 init、add、commit 到分支与合并
- 要点（⚠️ **讲义课前调查发现多数同学答不出**）：
  - 「`git merge` 发生冲突以后，你会观察到什么？……**合并冲突时，
    也没有人主动说出：常见文本冲突的双方内容和冲突标记，会直接出现在工作区文件里。**」
  - ⭐ 「当双方对同一段文本做了无法自动协调的修改，Git 通常会在**工作区文件里**写入
    `<<<<<<<`、`=======`、`>>>>>>>` 等标记，展示需要人工决定的内容，
    同时在 `git status` 中报告例如 **`both modified`** 的状态。」
  - 「解决冲突，就是**阅读上下文，把文件编辑成最终应有的内容，移除标记，
    再用 `git add` 标记已解决并完成合并**。」
  - ⚠️ 「**二进制文件、删除与修改冲突等情况不一定呈现同样的文本标记，
    所以关键是同时检查状态和文件。**」

**【机制 / 为什么】** ✅ 材料给了完整机制，且给了边界（非文本冲突）。

**【前置】** U5

**【标准范例】** —— 用最熟悉的场景
```
你和同学改同一个 .h 的同一行：

    工作区文件里会直接出现：
        <<<<<<< HEAD
        #define MAX_RPM  3000
        =======
        #define MAX_RPM  5000
        >>>>>>> feature-speed

    → 上下两段是"双方的内容"，中间是分隔
    → **你要做的是把文件编辑成最终该有的样子**，然后把标记删掉

    git status 会显示：both modified

⭐ 注意讲义给的边界警告：
   二进制文件（比如 .xlsx、.pdf、固件 .bin）、删除与修改冲突，
   **不一定有这种文本标记**
   → 所以"关键是同时检查状态和文件"
```

**【常见误解】**
1. 「冲突会弹一个界面让你点按钮」——⚠️ 讲义强调的是**冲突标记直接写进了工作区文件**
2. 「解决冲突 = 选一边」——不完全是，**你要把文件编辑成最终应有的内容**（可能是两边都不是）
3. 「看 `git status` 就够了」——❌ 二进制冲突**可能没有文本标记**，必须**同时看文件**

**【适用边界】**
- ⚠️ 讲义明确：**二进制文件、删除与修改冲突不一定呈现文本标记**

**【预考题】**
1. merge 冲突时，你会在哪里看到冲突？（提示：不是“看报错”）
2. 解决冲突的最后一步是什么？
3. ⭐【讲义原话·课堂提问】「**`git merge` 发生冲突以后，你会观察到什么？**」
   ——为什么“知道 Git 是版本管理工具”和“能够预测下一条命令的后果”之间，
   会一直隔着很远？

**【练习题 + 答案】**
- Q1（★ 识别）：merge 冲突时"会观察到什么"？
  A1：**双方内容和冲突标记（`<<<<<<<`、`=======`、`>>>>>>>`）直接出现在工作区文件里**；
  同时 `git status` 报告 **`both modified`** 之类的状态。
- Q2（应用）：解决冲突的步骤是什么？
  A2：**阅读上下文 → 把文件编辑成最终应有的内容 → 移除标记 → `git add` 标记已解决
  → 完成合并。**
- Q3（应用）：为什么说"关键是同时检查状态和文件"？
  A3：因为**二进制文件、删除与修改冲突不一定呈现同样的文本标记**，
  只看状态或只看文件都可能漏掉。
- Q4（迁移）：你更换 FOC 工程里的某个外设驱动（.c/.h），和同事的改动冲突时，
  为什么比文本冲突更麻烦？
  A4：如果涉及二进制（如工程配置、库文件），**没有文本标记可以人工取舍**，
  需要靠人来判断保留哪一份、或重新生成。

**【迁移题】**
解释为什么"知道 Git 是版本管理工具"和"能预测下一条命令的后果"之间差很远。

**【掌握判定】**
- 能说清：能说出冲突在工作区文件里长什么样、解决步骤、以及非文本冲突的边界
- 能应用：能预测一次冲突后 `git status` 会说什么
- 能回忆：隔一天能复述解决冲突的四步

### U7 ★ 预测命令后果的四个问题

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§从 init、add、commit 到分支与合并
- 要点：
  - 「这不只是少背了几个术语。**真正使用过一个工具，也需要留意眼前发生的变化。
    否则，'知道 Git 是版本管理工具'和'能够预测下一条命令的后果'之间，会一直隔着很远。**」
  - ⭐⭐ 「理解这些操作后，再回头看命令，就不再只是记住'输入什么'。
    **你可以在操作前预测：工作区会变吗？下一次提交包含什么？哪个引用会移动？
    历史里会增加什么关系？这才是可以继续外推的知识。**」

⭐⭐ **这是本讲给出的"可迁移的知识判据"**：能预测，才算懂。

**【机制 / 为什么】** ✅ 材料给了一组可操作的预测问题。

**【前置】** U4、U5、U6

**【标准范例】** —— 用这四个问题分析一条命令
```
命令：git commit -m "fix: xxx"

① 工作区会变吗？        → 不会（commit 读的是暂存区）
② 下一次提交包含什么？  → 暂存区现在的内容
③ 哪个引用会移动？      → 当前分支引用（HEAD 指向的那个）向前移一格
④ 历史里增加什么关系？  → 新增一个提交，父提交是原来的分支顶端

⭐ 这和在单片机里"执行这条指令前知道寄存器会怎么变"是同一层能力
   —— 讲义原文叫"可以继续外推的知识"
```

**【常见误解】**
1. 「背下命令和参数就算会了」——讲义明确否定
2. 「能跑通就行，不用知道为什么」——**预测不出来，换一个场景就废**
3. 「这四个问题是给初学者的」——这是**判断"是否真懂一个工具"的通用尺子**

**【适用边界】**
- ⚠️ 讲义把这四个问题用于 Git，**但它显然可推广到其他工具/命令**——这是【外部补充】的推广

**【预考题】**
⭐⭐ 本点直接用讲义里**保研面试的三个真实问题**（讲义记录：十位同学没有一个答出 rebase，
也没有人主动说出冲突标记会出现在工作区文件里）：

1. 【讲义原话·课堂提问】「**什么是 Git？**」（多数人还能说上几句）
2. 【讲义原话·课堂提问】「**什么是 `git rebase`？**」（十位同学没有一个答出来）
3. 【讲义原话·课堂提问】「**`git merge` 发生冲突以后，你会观察到什么？**」
   （没有人主动说出：**双方内容和冲突标记会直接出现在工作区文件里**）

> ⭐ 讲义对这三题的判断：「**这不只是少背了几个术语。真正使用过一个工具，
> 也需要留意眼前发生的变化。**」

**【练习题 + 答案】**
- Q1（识别）：讲义给的四个预测问题是什么？
  A1：**① 工作区会变吗？② 下一次提交包含什么？③ 哪个引用会移动？
  ④ 历史里会增加什么关系？**
- Q2（应用）：用这四个问题分析 `git add hello.c`。
  A2：① 工作区不变；② **下一次提交会包含** `hello.c` 此刻的内容；
  ③ **引用不移动**（add 不动分支）；④ 历史里**不增加任何关系**。
- Q3（应用）：用这四个问题分析 `git checkout -b dev`（新建并切到分支 dev）。
  A3：① 工作区不变；② 下一次提交的内容按暂存区来，暂存区不变；
  ③ **HEAD 移动**到新分支 `dev`；④ 历史不新增提交，但**新增了一个指向当前提交的分支引用**。
- Q4（迁移）：把这四个问题改造一下，用来判断"你懂不懂一条单片机指令"。
  A4（开放，示例）：① 哪些寄存器会变？② 哪些标志位会变？③ 内存/外设状态会变吗？
  ④ 下一个指令取哪里的？

**【迁移题】**
挑一条你"会用但说不清后果"的命令/操作，用这四个问题考自己一次。

**【掌握判定】**
- 能说清：能复述四个问题，并用它们分析一条 Git 命令
- 能应用：能对未见过的命令做预测（哪怕预测错，也要能说出错在哪一步）
- 能回忆：隔一天能说出"这才是可以继续外推的知识"

### U8 ★ 该提交什么

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§哪怕只有 hello.c，也需要工程判断
- 要点：
  - ⭐ 「目录里同时有 `hello.c` 和编译得到的 `hello`，要不要一起提交？
    如果两者都保存，**下一次只改了源码却忘记重新编译，仓库就会出现两份不一致的状态。
    别人到底该相信哪份？**如果只保存源码，也还要说明怎样构建，让其他人有条件重建结果。
    **'我的目录里有什么'和'项目需要共同保存什么'，是两个问题。**」
  - 「老师反复提醒新生的几类问题」：
    - 「**构建产物和运行日志通常不提交**，例如 `dist/`、编译得到的程序和调试日志；
      **应让源码、依赖和构建方法能够重建所需结果。**」
    - 「**个人配置通常不提交**，尤其是包含自己机器上的绝对路径、私人偏好的设置；
      **团队共享、可移植的编辑器配置则可以有意保留。**」
    - 「**密钥不能提交。源码需要共享，并不意味着访问服务的凭据也应一起共享。**」
    - 「`.DS_Store` 等临时文件不提交，它们既不表达项目意图，也不参与项目构建。」
  - ⭐ 「**这些不是按文件名机械执行的禁令。**依赖锁文件虽然由工具生成，
    却常常用于固定依赖版本；有些项目也有意保存生成的头文件或静态发布产物。
    **需要解释的是，这个文件为何构成共同维护的项目状态，以及怎样保证它与其他文件一致。**」

**【机制 / 为什么】** ✅ 材料给了判据（"为什么构成共同维护的项目状态"），而不是文件名清单。

**【前置】** U3（快照以项目为单位）

**【标准范例】** —— 他一定遇到过
```
你 Keil 工程里有哪些文件？

    main.c / motor.c / motor.h        → ✅ 提交（源码）
    Project.uvprojx                    → ✅ 通常提交（工程配置，团队共享）
    Objects/main.o / main.axf          → ❌ 不提交（构建产物）
    Objects/xxx.d                      → ❌ 不提交（中间产物）
    DebugConfig/                       → ❓ 看情况（个人调试配置）
    .vscode/settings.json (含个人路径)  → ❌ 个人配置
    某个 api_key.h                     → ❌❌ 密钥，绝对不能提交

⭐ 判据（讲义给的）：**它是否构成"共同维护的项目状态"？**
   并且能保证和别的文件一致？

⚠️ 反例（讲义特别提醒）：**依赖锁文件**虽然由工具生成，却常常要提交
   —— 因为它是"保证一致"的关键
```

**【常见误解】**
1. 「编译产物提交了更省事」——讲义指出风险：**源码改了忘重编译，仓库里出现两份不一致的状态**
2. 「不提交产物就行了」——不够，**还要说明怎样构建**（让别人能重建）
3. 「这是文件名清单，背下来就行」——❌ 讲义明确否定：**不是机械禁令**，
   要解释"为何构成共同维护的项目状态"

**【适用边界】**
- 讲义明确保留例外：**依赖锁文件、生成的头文件、静态发布产物**
- ⚠️ **缺口：讲义未给"如何判断某个例外是否该提交"的通用流程**

**【预考题】**
1. 你的单片机工程里，哪些文件提交、哪些不提交？为什么？
2. 编译出来的 `.hex` / `.axf` 要不要提交？

**【练习题 + 答案】**
- Q1（识别）：「我的目录里有什么」和「项目需要共同保存什么」，为什么是两个问题？
  A1：因为目录里有些文件是**个人的、临时的、可重建的**（构建产物、个人配置、临时文件），
  它们**不构成"共同维护的项目状态"**；而有些是团队必须共享的。
- Q2（应用）：判断下列该不该提交，并说理由：
  (a) 编译得到的可执行文件 (b) 密钥文件 (c) 依赖锁文件 (d) `.DS_Store`
  A2：**(a) 不提交**（可重建，且会出现不一致的两份状态）；**(b) 绝对不能**
  （源码共享 ≠ 凭据共享）；**(c) 通常提交**（它正是用来保证一致性的）；
  **(d) 不提交**（不表达项目意图，也不参与构建）。
- Q3（★ 关键）：讲义为什么说"这些不是按文件名机械执行的禁令"？
  A3：因为**判据不是文件名，而是"这个文件为何构成共同维护的项目状态，
  以及怎样保证它与其他文件一致"**。同样是生成的文件，
  依赖锁文件要提交、编译产物不提交，**区别在于对一致性的作用不同**。
- Q4（迁移）：你 B站 视频的工程文件，哪些该进版本管理、哪些不该？
  A4（开放）：剪辑工程文件、字幕文本、封面源文件 → 提交；
  渲染出的成品视频、缓存/代理文件 → 不提交。

**【迁移题】**
给你自己的一个项目写一份"提交/不提交"清单，每条都附上一句**理由**（不是"因为都是这样"）。

**【掌握判定】**
- 能说清：能说出判据（为什么构成共同维护的项目状态），并说出四类通常不提交的东西
- 能应用：给定一个文件，能判断并**说出理由**（而不只是"应该/不应该"）
- 能回忆：隔一天能说出"源码需要共享，并不意味着凭据也应一起共享"

### U9 ★ .gitignore 的边界与密钥泄漏

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§哪怕只有 hello.c，也需要工程判断
- 要点：
  - 「`.gitignore` 可以把这些约定落实为忽略规则，但**它不会让已经被跟踪的文件自动
    退出版本管理，更不会抹掉历史**。」
  - ⭐ 「这也解释了为什么**误提交密钥后，仅仅删除当前文件不够**：
    **旧提交可能仍保留它，别人也可能已经取得副本。**
    **版本管理帮助我们记住过去；不该公开的东西一旦进入过去，就不能假装它从未发生。**」

**【机制 / 为什么】** ✅ 材料给了机制（旧提交仍在）。

**【前置】** U8、U3（旧快照仍保留）

**【标准范例】**
```
你误把 api_key.h 提交了，然后：
    ① 删掉文件，再提交一次     → 当前版本没有了 ✅
                                但旧提交里还有 ❌
    ② 加进 .gitignore          → 以后再提交时会被忽略
                                但已经跟踪的文件**不会被移除** ❌

⭐ 讲义的话：
   "不该公开的东西一旦进入过去，就不能假装它从未发生"
   → 正确做法是**立刻作废那个密钥**（换一个新的），
     而不是只想着"从历史里删掉"（历史可能已被别人克隆）
```

**【常见误解】**
1. 「加进 .gitignore 就安全了」——❌ **不会让已跟踪文件自动退出**，也不抹历史
2. 「删掉当前文件就行了」——❌ 旧提交可能仍保留，别人可能已取得副本
3. 「用工具重写历史就能彻底解决」——⚠️ 讲义强调的是**"不能假装它从未发生"**；
   真正的止损是**作废凭据**

**【适用边界】**
- ⚠️ **缺口：讲义未给"误提交密钥后的完整处置流程"**（只说"仅仅删除当前文件不够"）
- 【外部补充】业界通行做法是**立即作废并轮换密钥**，其次是清理历史——标记为外部补充

**【预考题】**
1. 把文件加进 `.gitignore`，它就安全了吗？
2. 不小心把密钥提交上去了，删掉文件再提交一次，问题解决了吗？

**【练习题 + 答案】**
- Q1（识别）：`.gitignore` 做不到哪两件事？
  A1：**① 不会让已经被跟踪的文件自动退出版本管理；② 不会抹掉历史。**
- Q2（应用）：误提交密钥后，为什么"仅仅删除当前文件不够"？
  A2：因为**旧提交可能仍保留它，别人也可能已经取得副本**。
- Q3（★ 关键）：解释讲义那句话——"不该公开的东西一旦进入过去，就不能假装它从未发生"。
  A3：版本管理的作用就是**记住过去**；一旦写进历史，它就成了可被复现的事实。
  所以处置的重点不是"让历史看起来干净"，而是**承认它已泄漏并作废凭据**。
- Q4（迁移）：你如果误把自己的私人手机号写进一个公开仓库，会怎么处理？
  A4：（开放）**先假设已泄漏**（改号/换联系方式），再考虑清理历史。

**【迁移题】**
列出你项目里"一旦泄漏就无法挽回"的东西，并写出各自的止损动作。

**【掌握判定】**
- 能说清：能说出 `.gitignore` 的两个做不到，并解释"不能假装它从未发生"
- 能应用：能给出误提交密钥的正确处置顺序
- 能回忆：隔一天能复述那句话

### U10 命名细节也值得追问

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§大写还是小写，也值得追问
- 要点：
  - 例子：`[TYPO-CHECK]` vs `[typo-check]`，同一条文档检查规则的两种写法。
  - 「老师的直觉是'大写似乎更好，**但不是极强**'，一时又说不清原因。
    **这样的犹豫很有价值：它提示我们，直觉背后可能有可以讨论的设计理由。**」
  - 「方括号里的名字是**固定的规则标识**，后面则是**解释规则的自然语言**。
    **大写让两者更容易在视觉上区分**；讨论'违反了 `TYPO-CHECK`'时，
    它也更像**一个明确的引用**。」
  - ⭐ 「不过，**如果整个项目已经使用小写标识，或处理规则的工具要求小写，

    而是**理解了这个选择涉及的角色区分、可引用性和一致性**。」

**【机制 / 为什么】** ✅ 材料给了完整的推理过程（三个考量：角色区分 / 可引用性 / 一致性）。

**【前置】** L1 S12（Spec 的精确化）

**【标准范例】** —— 用他自己的代码
```
你的代码里也有这种选择，只是你可能没停下来想过：

    #define MAX_RPM       3000      ← 全大写：常量
    int target_rpm;                 ← 小写：变量

    为什么常量用大写？→ **和变量的角色区分开**，一眼能看出

⭐ 讲义想教的不是"大写更好"，而是：
   **停下来问一句为什么，然后发现背后的判据（角色区分、可引用性、一致性）**
```

**【常见误解】**
1. 「大写更好」——讲义明确**没有**给出这个结论
2. 「这种小事不值得讨论」——讲义恰恰说：**"这样的犹豫很有价值"**
3. 「风格问题没有对错」——讲义给了**三个可以讨论的判据**

**【适用边界】**
- 讲义明确：**"保持一致可能比局部的醒目更重要"** —— 结论依赖项目现状

**【预考题】**
1. 你的代码里为什么常量用大写、变量用小写？（说不出理由也没关系）

**【练习题 + 答案】**
- Q1（识别）：讲义从哪三个角度解释这个选择？
  A1：**① 角色区分**（固定标识 vs 自然语言解释）**② 可引用性**（像明确的引用）

  A2：**不是**。结论是**理解了这个选择涉及角色区分、可引用性和一致性**；

- Q3（迁移）：你的单片机代码里，`static` 变量和全局变量怎么区分？为什么？
  A3：通常用**命名前缀或放置位置**（如 `s_` 前缀、或放在 .c 内部）。
  理由是**角色区分**——一眼看出它的作用域。

**【迁移题】**

**【掌握判定】**

### U12 ★ 提交说明要留下「为什么」

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§提交要留下可以理解的变化
- 要点：
  - 「`update` 当然能成为提交说明，但**几个月后翻历史，它几乎不能帮助任何人**。」
  - 例子：`fix(parser): accept repeated spaces between arguments`
    —— 「这是 **Conventional Commits** 风格的示例：**`fix` 表示修复，`parser` 标示范围，
    后面说明行为变化**。固定结构**既方便人浏览，也方便工具分类和生成更新记录**。
    具体项目可以采用不同约定，**关键在于形成稳定、可理解的表达**。」
  - ⭐⭐ 「标题之后，还可以解释：**旧解析器把连续空格当成空参数，导致复制来的命令失败；
    现在忽略参数之间的多余空格，但保留引号内部的空格。**
    **代码 diff 展示怎样改，提交说明补上为什么改、想保留什么。**
    将来有人想删除这段逻辑，就能**找到判断依据，而不必重新猜一遍**。」

**【机制 / 为什么】** ✅ 材料给了机制（diff 说"怎样改"，说明说"为什么改"）。

**【前置】** U8（该提交什么）

**【标准范例】** —— 用他的工作
```
❌ "update"  /  "改了一下"  /  "修复bug"
   → 三个月后你自己也不知道改了什么

⚠️ 半好："修复了转速抖动"
   → 知道改了什么，但不知道**为什么**这么改

✅ 完整：
    fix(speed-loop): 低速时改用滑动平均滤波

    原因：低速时编码器分辨率不足，单周期差分得到的速度噪声大，
          导致速度环在 100rpm 以下抖动明显。
    做法：改用 8 点滑动平均，代价是约 2ms 的额外延迟，可接受。
    保留：原本的限幅逻辑不动。

    ⭐ 这样，将来有人想删掉这个滤波，他能**看到当时的判断依据**
```

**【常见误解】**
1. 「写清楚"改了什么"就够了」——讲义要的是**为什么改、想保留什么**
2. 「团队约定很烦」——讲义说它**既方便人浏览，也方便工具分类和生成更新记录**
3. 「diff 已经说明一切了」——❌ diff 只说**怎样改**，不说**为什么**

**【适用边界】**
- 讲义明确：**"具体项目可以采用不同约定"**（Conventional Commits 只是例子）
- ⚠️ **缺口：讲义未给"说明应该写到多详细"的判据**

**【预考题】**
1. 你写提交说明会写什么？（大概率是"改了什么"）
2. diff 已经能看到改动，为什么还要写说明？

**【练习题 + 答案】**
- Q1（识别）：diff 和提交说明各承担什么？
  A1：**diff 展示"怎样改"；提交说明补上"为什么改、想保留什么"。**
- Q2（应用）：为什么 `update` 这样的说明"几个月后几乎不能帮助任何人"？
  A2：因为它**没有提供可据以判断的信息**——看不出改了什么范围、为什么改，

### U14 ★★ 一行修复背后是一整套工程工作

**原子性**：只考一件事 ✓

    修改实现，再验证修复及已有行为。**评测中的 **`FAIL_TO_PASS` 测试应从失败变成通过，
    `PASS_TO_PASS` 测试应继续通过**。这两个名字说明了**修复的双重要求：

  - **Astropy 案例**（`【待查证·引注未核】`）：「它的建模工具用一个**布尔矩阵表示输出对输入的依赖**：

### U15 ★★★ 原子变更（本讲核心）

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§用原子变更推进项目
- 要点：
  - ⭐⭐⭐ 「可以把这一讲的核心概括为：**项目是由原子变更推进的快照，可以分支，可以合并。**
    **原子变更（atomic change）在这里指围绕一个明确意图组织的完整修改，
    它应当能够被解释、验证，并在需要时单独撤销。**
    **它不一定只改一个文件，也不一定只有几行。**」
  - ⭐ 「为什么强调这一点？因为**人很难处理'一团混沌'**。
    一次改了接口、重写了实现、更新了依赖、调整了格式，最后测试失败，**应该从哪里找起？**
    **如果这些变化有清楚的边界，就可以分别理解、审查和处理冲突。**」
  - ⭐ 「**历史还可以成为调试工具。**`git bisect` 在已知好版本与坏版本之间，
    通过不断测试中间提交**缩小范围，帮助定位引入问题的变化**；
    `git revert` 可以**记录撤销某次变化的新提交**。
    它们好不好用，**与历史中的变化是否完整、是否可验证密切相关。**」
  - ⚠️ 「有些项目要求**线性历史**（linear history）……不过，**线性只是组织形式。
    每一步都意义不明、不能运行，排成一条直线也不会自动变成好历史。**」
  - ⭐ 「在模型能力还有限时，AI 参与开发同样需要避免'一团混沌'。
    一次交给它一个**有边界的目标**，保留**可以检验的状态**，发现偏差后**及时反馈**，
    这些仍然是有效的工程方法。**代码生成速度提高了，并没有自动消除理解和集成的难度。**」

⭐⭐⭐ **本讲的核心概念**，而且**直接接上 L1 的"修改的局部性"**。

**【机制 / 为什么】** ✅ 材料给了定义、理由、用途、和边界。

**【前置】** U4（暂存区就是为了组织提交）、L1 S15（局部性）

**【标准范例】** —— 用他自己的项目
```
❌ 一团混沌：
    一次改完：换了无感算法（SMO→EKF）+ 重写了电流环 + 更新了 HAL 库
             + 顺手统一了代码格式
    → 结果：转速不对
    → **应该从哪里找起？**

✅ 原子变更（每次围绕一个明确意图）：
    提交 1：把电流环的 PI 参数抽成配置项       ← 可解释、可验证、可单独撤销
    提交 2：接入 EKF，但先不启用（开关控制）    ← 同上
    提交 3：启用 EKF                            ← 出问题直接 revert 这一次
    提交 4：统一代码格式（单独一次）             ← 不淹没真正改动

⭐ 讲义的定义里三个要件，逐一对上：
    "能够被解释"   → 提交 1 的意图一句话说清
    "验证"         → 每次都能编译 + 跑一次台架
    "单独撤销"     → 提交 3 出问题，revert 它，回到提交 2 的状态

⭐ 讲义的判据（+ L1 S15）：
    "一次改了接口、重写了实现、更新了依赖、调整了格式，最后测试失败，应该从哪里找起？"
    ← **这正是"修改的局部性"在"历史"这一层的表现**
```

**【常见误解】**
1. 「原子变更 = 只改一个文件」——❌ 讲义明确：**不一定只改一个文件，也不一定只有几行**
2. 「提交越小越好」——判断标准是**是否围绕一个明确意图**，不是行数
3. 「线性历史 = 好历史」——❌ 讲义明确：**线性只是组织形式**
4. 「格式化和修复一起提交更省事」——❌ 讲义明确：**顺手格式化整个项目通常应该分开**

**【适用边界】**
- 讲义给了"原子变更"的定义和理由，但 ⚠️ **未给"如何判断一次修改是否构成原子变更"的操作流程**
- 【外部补充】可用 L1 S15 的判据反推：**若能单独撤销且不影响其他意图，就是原子**——标注为外部推得

**【预考题】**
1. 什么叫"原子变更"？是不是"改得少"？
2. 为什么"一次改了一大堆东西"会让调试变难？

**【练习题 + 答案】**
- Q1（★ 识别）：原子变更的定义是什么？（三个要件）
  A1：**围绕一个明确意图组织的完整修改**，它应当**能够被解释、验证，并在需要时单独撤销**。
  它**不一定只改一个文件，也不一定只有几行**。
- Q2（应用）：下面哪些应该拆成独立的提交？
  (a) 修复一个 bug (b) 更新第三方库 (c) 统一代码格式 (d) 该 bug 的测试
  A2：**(a)+(d) 一次**；**(b) 单独一次**；**(c) 单独一次**。
  理由：各自围绕**不同的意图**，(c) 会淹没 (a) 的真实改动。
- Q3（★ 应用）：为什么讲义说"历史还可以成为调试工具"？它和原子变更是怎么联系起来的？
  A3：因为 `git bisect` 靠**不断测试中间提交来缩小范围**、`git revert` 靠**记录撤销**。
  **它们好不好用，取决于历史中的变化是否完整、是否可验证** ——
  而这正是原子变更提供的性质。**历史质量决定调试手段可用性。**
- Q4（★ 关键串联）：用 L1 的"修改的局部性"解释"为什么要原子变更"。
  A4：因为**一次改了一大堆互相纠缠的改动，等于把多个意图的依赖混在一起**：
  出问题时无法定位到哪一处，也无法单独撤销一处——
  **改动放大**。原子变更就是**在"历史"这一层把改动切开，让每一处都可独立理解和回退**。
- Q5（迁移）：你如果一次给 AI 一个"改十个地方"的任务，出问题时要怎么查？
  A5：只能整体回退或逐个排查，**失去了"定位单位"**。
  讲义的说法的对策是：**一次给一个有边界的目标 + 保留可检验的状态 + 及时反馈。**

把你现在手上的一个待办，拆成 3-4 个原子变更，每个写一句意图。

**【掌握判定】**
- 能说清：能说出定义三要件，并解释"为什么强调这一点"
- 能应用：能把一次混杂的修改拆成原子变更

- 出处：§Agent 能力之内的项目，怎样协作
- 要点：
  - ⭐ 「老师的实践是，**架构阶段先'单线程'：与能力强的模型反复讨论，
    直到接口、约束和总体设计逐渐收敛，再把结果写成文档、规则和示例，
    包括测试要做到什么程度。**」
  - 「这个阶段仍然需要人的知识。**为什么还要学习操作系统、编译原理和数据库？
    因为这些领域积累了大量好设计：怎样划分职责，怎样表达不变量，怎样隔离变化，
    怎样协调并发。**知道这些，才能在讨论中**提出有效问题**，
    判断模型给出的方案是否值得继续。」
  - ⭐ 「进入实现阶段后，可以**打开少量终端并行工作。老师给出的实践范围是不超过三个终端**，
    通过 `AGENTS.md` 说明协作规则，例如历史如何整理、任务怎样集成，
    再由人脑承担一部分并发控制：**尽量安排相互不冲突的任务**。
    ⚠️ **这个数量是个人工作方式，不是并发 Agent 的普遍上限。**」
  - ⭐ 「**每一轮产出都应尽快检查**；有界面的项目，立即打开看看，给出视觉验收反馈。
    **无论你觉得模型这一次的质量高不高，都不要让未确认的设计选择积累太久。**
    架构讨论收敛共同前提，有限并发推进独立工作，快速反馈纠正理解偏差，**三者需要配合起来。**」

**【机制 / 为什么】** ✅ 材料给了完整的三段式实践。

**【前置】** U15、L2 T14（人应该盯住哪些地方）

**【标准范例】** —— 用他的项目经验
```
讲义给的三段式，和你在嵌入式项目里的做法对照：

① 架构阶段（单线程）：
   定接口、定约束、定"测试做到什么程度"
   ⭐ 相当于你在做 FOC 之前先把"电流环/速度环怎么分、谁调谁"想清楚，
      而不是边写边定

② 实现阶段（少量并行，≤3 终端）：
   用 AGENTS.md 说明规则；**人脑做并发控制：安排互不冲突的任务**
   ⭐ 相当于"一个改电流环、一个改上位机界面"——碰不到一起

③ 每轮尽快检查：
   ⚠️ "无论你觉得模型这一次的质量高不高，都不要让未确认的设计选择积累太久"
   ⭐ 相当于你调参：**每改一处就看一次波形**，而不是改十处再看
```

**【常见误解】**
1. 「并行越多越快」——讲义给的是**个人工作方式（≤3）**，
   且明确**"不是并发 Agent 的普遍上限"**；关键是**安排互不冲突的任务**
2. 「质量高就可以不检查」——⚠️ 讲义明确：**无论质量高低，都不要让未确认的设计选择积累太久**
3. 「架构阶段可以让 AI 定」——讲义说这个阶段**仍然需要人的知识**（提问、判断方案）

**【适用边界】**
- ⚠️ **"不超过三个终端"是老师的个人实践，不是普遍上限** —— 讲义主动声明了这一点，**不能当规范背**

**【预考题】**
1. 让多个 AI 同时干活，怎么安排才不出乱子？
2. 为什么"架构阶段"要先单线程？

**【练习题 + 答案】**
- Q1（识别）：讲义给的三段式实践是什么？
  A1：**① 架构阶段单线程**（与强模型反复讨论，直到接口/约束/总体设计收敛，
  并写成文档、规则、示例，含测试要求）；**② 实现阶段少量并行**（≤3 终端，
  用 `AGENTS.md` 说明规则，人脑安排互不冲突的任务）；**③ 每轮尽快检查**（含视觉验收）。
- Q2（应用）：为什么"不要让未确认的设计选择积累太久"？
  A2：因为**后续工作会建立在那些未确认的选择之上**，一旦发现不对，
  返工范围会随积累而扩大——这正是 L1 的**改动放大**。
- Q3（★ 关键）："为什么还要学习操作系统、编译原理和数据库"——讲义给的理由是什么？
  A3：因为这些领域积累了大量**好设计**（怎样划分职责、表达不变量、隔离变化、协调并发），
  知道这些才能在讨论中**提出有效问题**，判断模型方案是否值得继续。
- Q4（迁移）：你现在的工作里，"架构阶段"和"实现阶段"分别是什么？你会怎么安排并行？
  A4（开放）。

**【迁移题】**

### U17 ★★ 一千倍思想实验

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§如果代码产能再提高一千倍
- 要点：
  - 「'一千倍'在这里用来**放大矛盾，并非一次测量结果**。
    ⭐ **生成一分钟，人工理解和验收一小时，积压的就会是等待判断的变更。**
    Git 本身还能保存它们，但**围绕人工提交、审查和协调组织起来的工作方式，可能成为瓶颈。**」
  - ⭐ 「如果从零开始为 Agent 设计版本控制系统，也许应该把**快照、变更以及变更如何组合**
    放到中心。所谓 **change algebra**，可以理解为**描述变更组合规则的一套运算**：
    **两项变化能否独立应用？能否交换顺序？是否依赖某个前置变化？冲突以后应当重做哪一部分？**」
  - 「这与数据库中的**多版本并发控制（MVCC）**有相通之处……
    ⚠️ **但两者并不是同一个概念。**」
  - ⭐⭐ **write skew 例子**：「项目要求**至少有一名值班员在岗**，初始状态是甲、乙都在岗。
    **Agent A 看到乙在岗，就把甲改为离岗；Agent B 看到甲在岗，就把乙改为离岗。
    两项修改可以写在不同文件里，文本合并没有任何冲突，结果却是无人值班。**
    ……类似数据库中的 write skew：**各自依据旧快照作出的决定，组合后破坏了共同约束。**
    **快照和局部检查之外，还需要检查组合结果或采用更强的并发控制。**」
  - ⭐ 「一种可能的设计是，让 Agent 在独立快照上生成变更，系统把变更与当前主线组合，
    **验证候选结果，再原子地发布这个确切版本**……
    **锁可以只保护短暂的版本读取或发布过程，耗时的生成和测试在锁外完成。
    否则，把整个开发过程锁住，只是把并发工作重新排成了长队。**」`【待查证·引注未核】`
  - 「老师用'反正没有 Agent 能被开除、能坐牢，出什么问题修好就行'挑战以追责为中心的审计习惯……
    **这仍然取决于错误能否及时发现、后果是否可恢复，以及验收标准能覆盖多少真实要求。**
    **测试全绿说明已有检查通过了；如果'至少一人值班'从未写进要求或检查，
    就不能指望文件合并替我们保证它。**」
  - ⭐ 「**人的责任会更多落在定义意图、不变量和完成标准上**，系统则需要解释：
    **它凭什么接受这次变化？**」

⭐⭐ **本讲把 L1 的"一千倍"推到了并发层面**，并且 write skew 的例子**可以直接用中断竞态解释**。

**【机制 / 为什么】** ✅ 材料给了完整的思想实验和一个具体的失败模式。

**【前置】** L1 S19（生产变便宜后瓶颈转移）、U15（原子变更）

**【标准范例】** —— ⭐ **用中断竞态讲 write skew，一次讲透**
```
⭐ 讲义的值班员例子，换成你最熟的场景（两个中断改共享状态）：

    约束：系统里**至少有一个通道处于开启状态**
    当前：通道 A 开、通道 B 开

    中断 1 执行：读到"B 是开的" → 于是把 A 关掉
    中断 2 执行：读到"A 是开的" → 于是把 B 关掉

    → 两次操作各自都"看了状态、做了合理判断"
    → 两次修改没有冲突（改的不是同一个变量）
    → **结果：两个通道都关了，约束被破坏**

⭐ 讲义的原话：
   "各自依据旧快照作出的决定，组合后破坏了共同约束"
   "文本合并没有任何冲突，结果却是无人值班"

⚠️ 讲义明确说**这不是数据库的 MVCC**，只是"有相通之处"

⭐ 对策（讲义给的）：
   ① **检查组合结果**（不只检查各自的修改）
   ② 或**采用更强的并发控制**
   ③ 锁只保护**短暂的读取/发布**，耗时的生成和测试放在锁外
      —— "否则只是把并发工作重新排成了长队"
```

**【常见误解】**
1. 「各自的修改都对、合起来就对」——❌ **write skew 正好是反例**
2. 「文件合并没有冲突 = 没有问题」——❌ 讲义明确："文本合并没有任何冲突，结果却是无人值班"
3. 「把整个开发过程锁住最安全」——⚠️ 讲义明确：**"只是把并发工作重新排成了长队"**
4. 「测试全绿就说明约束被保证了」——⚠️ 讲义明确：**如果约束从未写进要求或检查，就指望不上**

**【适用边界】**
- ⚠️ **`change algebra`、Jujutsu 机制、MVCC 的联系均为讲义的设想/引注，未经验证或未核对**
  → 标 `【待查证·引注未核】`
- 一千倍是**假设，用来放大矛盾，不是测量结果**

**【预考题】**
1. 两个人（或两个 AI）各自做了"看起来正确"的修改，合起来会不会出错？
2. 你现在写的单片机代码里，"至少有一个条件必须成立"这类约束，是靠什么保证的？

**【练习题 + 答案】**
- Q1（识别）：一千倍思想实验想放大的矛盾是什么？
  A1：**"生成一分钟，人工理解和验收一小时"** —— 积压的会是**等待判断的变更**；
  **围绕人工提交、审查和协调组织的工作方式可能成为瓶颈。**
- Q2（★ 应用）：值班员例子里，两次修改有冲突吗？为什么结果错了？
  A2：**没有文本冲突**（改的是不同文件/不同变量）。结果错是因为
  **各自依据旧快照作出决定，组合后破坏了共同约束**——即 write skew。
- Q3（★ 迁移）：用中断竞态复述一遍 write skew（不要用值班员的例子）。
  A3：见上面【标准范例】：两个中断各自读到"另一个通道是开的"就关掉自己那个，
  结果两个都关了，破坏了"至少一个开启"的约束。
- Q4（应用）：讲义给的对策有哪几条？
  A4：**① 检查组合结果**（不只检查各自的修改）；**② 采用更强的并发控制**；
  **③ 锁只保护短暂的版本读取/发布，耗时的生成与测试在锁外完成。**
- Q5（★ 关键）：为什么"测试全绿"不能保证约束成立？
  A5：因为**"测试全绿说明已有检查通过了"**；
  **如果约束从未写进要求或检查，就不能指望文件合并替我们保证它。**
  所以**人的责任更多落在"定义意图、不变量和完成标准"上**（接 L2 T4）。

**【迁移题】**
找出你系统里一条"多个部分共同保证"的约束（像"至少一个开启"），
说明它现在靠什么保证，会不会出现 write skew。

**【掌握判定】**
- 能说清：能说出瓶颈转移、write skew 的机制、以及三条对策
- 能应用：能识别一个场景是否构成 write skew
- 能回忆：隔一天能说出"人的责任会更多落在定义意图、不变量和完成标准上"
