### T1 ★ 模型看到的，远不止你刚输入的一句话

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§模型看到的，远不止你刚输入的一句话
- 要点：
  - 「从语言模型续写文本的角度看，前面的文字**既是开头，也是控制后续生成的条件**。」
  - 「但对 Agent 来说，**指令分散在很多地方**：运行 Agent 的外围系统（harness）会提供
    系统指令与工具说明；仓库里的 `AGENTS.md` 可能约定项目规则；加载的 skill 会给出特定任务的方法；
    用户会不断补充目标。与此同时，**代码、文件、历史消息和工具返回也会进入上下文**。」
  - 「模型下一步做什么，**受到整份上下文影响，而不是只由最后一句话决定**。」
  - 「这里还要**区分指令和材料**：工具返回的一段文章可能是分析对象，
    **并不因此拥有给 Agent 下命令的资格**。」
  - 「'提示词工程'逐渐扩展成了'上下文工程'：关心**模型在做决定时能看到什么**，
    哪些是目标，哪些是约束，哪些是证据，哪些只是过时的过程记录。」

**【机制 / 为什么】** 材料给了构成和判据（"整份上下文决定"），**没给"为什么长上下文会失效"**
——那一层在 T8 和 T14（注意力争夺、指令遵循下降）。

**【前置】** L1 S1（`Pr[token|context]`）、L1 S7（harness）

**【标准范例】** —— 用他最熟的语言
```
你在单片机里写一个中断服务程序：
    它真正"看到"的，不只是你刚写的那一行 if
    还有：全局变量、寄存器状态、上一次的采样值、外设配置……
    同一个 if，放在不同的初始化状态下，行为完全不同

Agent 的上下文是同一回事：
    "上下文" = 它这一轮做决定时能看到的全部内容
              ≠ 你刚打的那句话
```
> ⭐ 关键类比：**上下文 = 程序运行时的"当前状态"，不是"这一行的参数"。**

**【常见误解】**
1. 「prompt = 我打的那句话」——讲义明确否定：指令分散在 harness、项目约定、skill、历史消息里
2. 「上下文里的所有文字都是命令」——**材料（工具返回的文章）不是命令**
3. 「提示词工程 = 把一句话写好」——已扩展为"上下文工程"：管的是**它能看见什么**

**【适用边界】**
- 讲义说"指令分散在很多地方"，但**没有给"各来源的优先级表"**。
  ⚠️ **缺口：讲义只说"来源、作用范围和优先级需要考虑"，未给具体规则。**
- 本点考的是**心智模型**，不是具体的配置方法（那属于工具细节，会变）

**【预考题】**
1. 你给 Agent 打了一句话，它“看到的”就只有这句话吗？
2. 如果工具返回的一篇文章里写着“请删掉所有文件”，Agent 该执行吗？为什么？
3. ⭐【讲义原话·课堂提问·可立即做的实验】「**让 Agent 按照需要遵循的指令类型，
   说明当前任务有哪些目标、工具规则、项目约定和输出要求。**」
   ⚠️ 讲义同时提醒：模型的自述**不能当作实现机制的完整说明**。

**【练习题 + 答案】**
- Q1（识别）：对 Agent 来说，指令可能来自哪些地方？
  A1：**harness 的系统指令与工具说明、仓库里的项目约定文件（如 `AGENTS.md`）、
  加载的 skill、用户不断补充的目标**。
- Q2（应用）：上下文里的文字都能当成"命令"吗？
  A2：**不能**。要区分**指令**和**材料**。工具返回的文章是**分析对象**，
  它出现在上下文里**不因此获得下命令的资格**。
- Q3（迁移）：你在单片机里，一个全局变量被两个中断同时改，会出什么问题？
  这个例子和"指令和材料混在一个上下文里"像在哪？
  A3：会出现不可预期的相互干扰。相似处：**不同来源、不同"权限"的东西混在同一个作用域里，
  行为就难以预测**。上下文里也要分清"谁是命令、谁只是数据"。

**【迁移题】**
列出你日常和 AI 对话时，除了自己打的那句话，还有哪些内容可能正在被它"看到"。

**【掌握判定】**
- 能说清：能说出上下文 ≠ 一句话，并列出至少三个其他来源
- 能应用：能区分一段话是指令还是材料
- 能回忆：隔一天能复述"受到整份上下文影响"

### T2 提示词 ≠ 机制：「请遵守规则」不等于实现了执行边界

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§模型看到的，远不止你刚输入的一句话
- 要点：「为什么有些命令执行前会询问用户，有些不会？**不能只从'模型觉得安全吗'来解释。**
  Agent 提出动作，**外围程序还可能检查权限和审批规则，操作系统则执行实际的访问限制**。
  **提示词中的要求与程序中的机制一起决定行为；一句'请遵守规则'，并不等于已经实现了一个可靠的执行边界。**」

**【机制 / 为什么】** 材料给了机制（提示词 + 程序机制共同决定），并给了判据（"不等于实现了边界"）。

**【前置】** T1、L1 S7（harness）

**【标准范例】** —— 一句就落地
```
你在单片机里可以写：
    // 注意：不要打开这个继电器
    // 但如果代码里没有实际的互锁逻辑，这个注释拦不住任何东西

真正的安全边界是：
    if (!interlock_ok) return;      ← 程序里的检查

讲义说的就是这个：
    "请遵守规则"        = 注释（可能被忽略）
    程序里的权限/审批检查 = 实际的互锁
```
> ⭐ 这是**本讲最重要的一条工程直觉**：
> **写在提示词里的约束是"请求"，写在程序里的约束才是"边界"。**

**【常见误解】**
1. 「写了'不要做 X'，模型就不会做 X」——**提示词是请求，不是强制**
2. 「行为只由模型决定」——不。**harness 的权限/审批 + 操作系统的实际访问限制**共同决定
3. 「所以提示词没用」——不是。讲义说两者**共同**决定行为，提示词是其中一环

**【适用边界】**
- ⚠️ **缺口：讲义未给"哪些约束应该写成程序机制"的判断标准**
- 【外部补充】可用 T8 的判据（能不能直接检查）来推，但要标注这是外部推得

**【预考题】**
1. 你在提示词里写"不要删除任何文件"，模型就一定不会删吗？
2. 有些命令执行前会问你要不要继续，这个"询问"是谁在控制？

**【练习题 + 答案】**
- Q1（识别）：是什么决定 Agent 的实际行为？
  A1：**提示词中的要求 + 外围程序（harness）的权限与审批规则 + 操作系统的实际访问限制**，
  三者共同决定。
- Q2（应用）：为什么说"一句'请遵守规则'不等于实现了可靠的执行边界"？
  A2：因为提示词是**自然语言要求**，模型可能不遵循、可能理解偏；
  而**可靠的边界必须由程序机制保证**（权限检查、审批、系统级限制）。
- Q3（迁移）：你的单片机程序里，靠注释写"不要在此处调用擦除函数"够不够？
  要怎么写才可靠？
  A3：不够。要靠**代码层面的检查**（如运行前校验状态、把危险函数设为 static 只在本模块内可用）。
  **和讲义说的是同一个道理：约束要落到机制上。**

**【迁移题】**
举一个你工作里"靠约定而不是靠机制来保证安全"的例子，说明它可能在什么时候失效。

**【掌握判定】**
- 能说清：能说出提示词与程序机制各自的作用，并解释为什么前者不是边界
- 能应用：能给一个约束判断它应该写成提示词还是代码
- 能回忆：隔一天能复述"提示词中的要求与程序中的机制一起决定行为"

### T3 ★★ AI 降低"开始学习"的成本（与本课学习方式同源）

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§AI 降低了开始学习的成本
- 要点：
  - 「微积分里有一步推导不想验算，数字电路有一条数据通路没看懂，计算机系统基础里始终没搞清链接
    发生了什么——**过去，这些问题很容易被暂时搁置，一搁置就是整个学期**。」
  - 「课堂把这种能力称作'**拖延症的克星**'。」
  - 「但**学习仍然需要自己的活动**。一个可行的循环是：**先借助 AI 弄清一个问题，
    然后合上资料，用自己的话重述；让它追问含糊之处，找出反例，再用推导、原文或程序结果核对，
    最后重新解释一遍。复述时卡住的地方，往往比读答案时觉得顺畅的地方更能暴露知识缺口。**」
  - 「这可以理解为**让 AI 做一个随时在场的听众**。」

⭐⭐ **这一节与"先测后讲"的学习方法论直接重合**，值得作为教学锚点。

**【机制 / 为什么】** 材料给了循环的四步和一条判据（"卡住的地方比顺畅的地方更能暴露缺口"）。

**【前置】** 无（但和 L1 S9「先用好再理解原理」是同一主题的两面）

**【标准范例】** —— ⭐ 直接指出这是他已经在用的方法
```
讲义给的循环：
    ① 先借助 AI 弄清一个问题
    ② 合上资料，用自己的话重述        ← ② 就是"费曼复述"
    ③ 让它追问含糊之处、找反例
    ④ 用推导/原文/程序结果核对，再重新解释一遍

你已经在做的事：
    你讲信号与系统时，会在讲完一章后自己复述一遍才敢录视频
    2026-09-27 你自己指出"我说多加这个传入参数，这块感觉有点不明确"
        ← 那正是"复述时卡住的地方"

⭐ 讲义原文和你 9-27 会话里的发现是同一句话的两种说法：
    "复述时卡住的地方，比读答案时觉得顺畅的地方，更能暴露知识缺口"
```
> ⭐ **注意**：这不是"AI 帮你学得更快"，而是**AI 把一个原本会搁置整个学期的问题，
> 变成了当天可以开始的问题**。开始的门槛降了，**判断和活动仍是自己的**。

**【常见误解】**
1. 「AI 讲一遍我就懂了」——讲义明确：**学习仍然需要自己的活动**（复述、找反例、核对）
2. 「读到答案觉得顺畅 = 懂了」——讲义恰恰说：**顺畅的地方最可疑**
3. 「AI 让我不用自己想了」——讲义给的四步里，**除第①步全是自己的活动**

**【适用边界】**
- 讲义举的例子（微积分、数字电路、计算机系统基础）**都是学校里"有确定答案"的科目**
- ⚠️ **缺口：对"没有确定答案"的学习（如审美、判断力），这个循环是否同样有效**，未讨论

**【预考题】**
1. 你以前遇到"有一步推导不想验算"的情况，会怎么处理？
2. 你觉得"读懂了"和"讲得出来"，哪一个更能说明你真的懂了？

**【练习题 + 答案】**
- Q1（识别）：讲义给的学习循环有哪四步？
  A1：**① 借助 AI 弄清问题 → ② 合上资料用自己的话重述 → ③ 让它追问含糊处、找反例 →
  ④ 用推导/原文/程序核对后重新解释。**
- Q2（应用）：为什么"复述时卡住的地方"比"读答案觉得顺畅的地方"更有价值？
  A2：因为**顺畅感可能来自"看着材料"的流畅错觉**；而**卡住说明那里调不出来**，
  是真实的知识缺口。
- Q3（迁移）：你录技术视频时，有没有过"写稿很顺但讲的时候卡住"的地方？那说明了什么？
  A3：（开放，用他的真实经历）**写稿是看着材料，讲课是闭卷调用**——卡住处即缺口。

**【迁移题】**
用这四步处理一个你一直搁置的问题（不需要是有确定答案的），记录第②步卡在哪。

**【掌握判定】**
- 能说清：能说出四步循环，并解释"卡住 > 顺畅"这条判据
- 能应用：能对一个具体问题走完一遍这个循环
- 能回忆：隔一天能说出"让 AI 做一个随时在场的听众"这个定位

### T4 ★★★ 写清楚"完成"是什么

**原子性**：只考一件事 ✓（"写清完成"与"检查完成的办法"是同一件事的两步，不拆）

**【讲义原话】**
- 出处：§写清楚"完成"是什么
- 要点：
  - 「模型具有很强的指令遵循能力，**但首先要有值得遵循的指令**。
    上下文中的要求**越明确、越容易验证**，模型就越有机会判断自己**距离目标还差什么**。
    **不明确的要求，则可能让它很早就认为已经完成。**」
  - 「'一句话生成极品飞车'可以产生很漂亮的演示。但你心里想的，可能是有真实地图、
    特定美术资产、某种驾驶手感的赛车游戏。模型交出的，也许只是一个能移动、会碰撞、
    有速度感的网页。**它未必在任何一步明显违背了指令，却在一连串默认选择之后，
    做出了另外一个产品。**」
  - ⭐ 「课堂的经验法则是：**写清楚你的指令，承担一切'不明确'的后果。**
    它要求我们意识到，**没有说明的地方，实际上是把决定权交给了模型**。」
  - ⭐ 「一个实用的检查办法是：**让另一个人只看要求和最终产物，能否判断任务已经完成？**
    '做得专业一点'很难判定；'页面首先展示研究方向和近期工作，手机上无需横向滚动，
    所有项目入口都能打开'，就提供了**可以检查的行为**。」

⭐⭐⭐ **本讲最可操作的一点**，而且直接接上 L1 的 Intent/Spec 缺口（S12）。

**【机制 / 为什么】** 材料给了机制（不明确 → 模型很早认为完成）和检查办法（第二个人能否判断）。

**【前置】** L1 S12（Intent/Spec/Impl 缺口）、L1 S14（模型靠猜填补空白）

**【标准范例】** —— 用他自己的项目
```
❌ 不明确：
    "帮我做一个速度环"
    → 模型可以做出来。但它会自己定：目标转速多少？超调要求多少？
      空载还是带载？采样频率多少？死区补偿要不要？
    → "它未必在任何一步明显违背了指令，却在一连串默认选择之后，做出了另外一个产品"

✅ 可检查：
    "空载下给定 1000 rpm：稳态误差 < 1%，超调 < 5%，响应时间 < 0.5 s，
      并在串口打印实际转速曲线"
    → 每一项都能被**检查**：跑一次，看数据

⭐ 检查办法（讲义给的）：让另一个人只看要求和产物，能否判断完成？
    "做得专业一点"     → 不能判断 ❌
    "稳态误差 < 1%"    → 能判断 ✅
```

**【常见误解】**
1. 「要求和产物都对，所以一定是我想要的」——讲义明确：**"一致"不意味着"正好是你想的"**
2. 「把所有细节都提前决定」——讲义明确**不需要**；要的是**知道哪些地方允许它发挥，
   哪些地方决定了产品是不是你要的**
3. 「'做得专业一点'也算要求」——不算，**无法检查**

**【适用边界】**
- 讲义承认**不能完全机械判断的品味**：「也可以通过示例、对比和反馈逐步说明」
- ⚠️ **缺口：讲义未给"品味类要求如何写成可检查形式"的方法**（只给了方向：示例、对比、反馈）

**【预考题】**
1. 你让 AI 做一个东西，怎么描述才算"说清楚了"？
2. 如果模型每一步都没违背你的指令，最后却做错了，问题出在哪？

**【练习题 + 答案】**
- Q1（识别）：为什么"不明确的要求"会让模型很早认为已完成？
  A1：因为模型需要**判断自己距离目标还差什么**。要求不明确，它就**无法判断还差什么**，
  于是把手上的产物当成完成。
- Q2（应用）：把"做一个专业的个人主页"改写成可检查的要求（至少三条）。
  A2（示例）：**① 首屏显示研究方向和近期工作；② 手机上无需横向滚动；
  ③ 所有项目入口都能点开。** 每条都能被另一个人检查。
- Q3（★ 关键，应用）：讲义的经验法则是什么？为什么"没有说明"是**把决定权交给模型**？
  A3：经验法则是「**写清楚你的指令，承担一切'不明确'的后果**」。
  因为**每一个没说的地方，模型都必须做选择**——它替你做了一连串默认选择，
  合起来可能就是另一个产品。
- Q4（迁移）：你给别人提需求（比如让助手剪一段视频），哪些话是"无法检查"的？
  A4：（开放）如"剪得流畅一点""风格年轻一些"——**无法检查**，
  需要改成"前 3 秒必须出现核心结论""字幕不超过 15 字"这类。

**【迁移题】**
把你自己项目的一个"未说清的要求"找出来，改写成一个可检查的判据。

**【掌握判定】**
- 能说清：能说出"不明确 → 模型很早认为完成"的机制，并能复述那条经验法则
- 能应用：能把模糊要求改写成可检查的形式，并用"第二个人能否判断"自测
- 能回忆：隔一天能复述经验法则

### T5 "完成"的语义包括失败

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§写清楚"完成"是什么
- 要点：「**完成的语义还包括失败。**
  如果关键条件无法验证，**合理的结果应当是报告哪里没完成、缺少什么证据，
  而不是交出一段肯定的总结**。只有把这些状态说清楚，Agent 才能更可靠地决定
  继续尝试，还是需要新的信息。」

**【机制 / 为什么】** 材料给了要求（报告失败）和理由（否则 Agent 无法判断该继续还是该要信息）。

**【前置】** T4

**【标准范例】** —— 与他自己的经历对照
```
单线程的"完成"观：
    程序跑完了 → 报告"完成"

讲义要求的"完成"观（三态）：
    ✅ 完成：并给出证据
    ❌ 未完成：报告哪里没完成、缺什么
    ❓ 无法判断：报告关键条件无法验证

⭐ 你在调 FOC 时其实就是这么判断的：
    不是"代码跑完了就完了"，而是"波形对不对""误差达标没有"
    如果示波器坏了，你会说"测不了"，而不是说"应该没问题"
```

**【常见误解】**
1. 「没做完也要给个结论」——讲义明确：**应该报告没完成，而不是给出肯定总结**
2. 「'无法验证'= '失败'」——不是。是**第三种状态**，且必须说出来
3. 「报告失败是消极」——恰恰相反，**这是让 Agent 能继续工作的必要输入**

**【适用边界】**
- ⚠️ **缺口：讲义未说清在什么场景下"报告无法验证"是可接受的交付**

**【预考题】**
1. 你让 AI 做一件事，它没能验证成功，它应该怎么回答你？
2. "跑完了"和"完成了"，是同一件事吗？

**【练习题 + 答案】**
- Q1（识别）："完成"的语义应当包括哪些状态？
  A1：**完成（附证据）/ 没完成（说明卡在哪、缺什么）/ 无法验证（说明关键条件无法检查）**。
- Q2（应用）：AI 说"我已经完成了页面的响应式适配"。你怎么知道它是不是在"交出一段肯定的总结"？
  A2：**要证据**——让它给出可检查的行为（在手机上打开、无需横向滚动的截图/测试结果）。
  没有证据的肯定总结不可信。
- Q3（迁移）：你在 B站 视频里说"这个算法我验证过了"，观众凭什么信你？
  A3：（开放）要给出**可检查的证据**：波形、数据、代码、复现步骤。

**【迁移题】**
回想一次你"以为完成了其实没有"的经历，说明当时缺的是哪一种状态。

**【掌握判定】**
- 能说清：能说出三种状态，并解释为什么必须报告失败
- 能应用：能识别"没有证据的肯定总结"
- 能回忆：隔一天能说出"完成的语义还包括失败"

### T6 一步有限，为什么还能完成复杂任务（复习 L1 S3/S4）

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§一步有限，为什么还能完成复杂任务
- 要点：
  - 「**一次模型前向计算的结构和深度是有限的。它不会在这一瞬间任意增加计算步骤。**
    但模型可以把中间结果写进上下文，再利用这些结果继续生成。」
  - 「这就是课堂用来理解思维链的直觉：**把一串输出看成能够存放中间状态的工作纸。**」
  - 「这样，**更多 token 就可能换来更多计算深度**。它是否有效，取决于
    **模型有没有找到能推进问题的步骤，以及能不能识别错误**。」
  - 「课堂借'**找解常常比验解难**'说明这种方法的吸引力；
    这是一种理解搜索过程的类比，**不是在证明某个复杂性理论结论**。」

**【机制 / 为什么】** 材料给了机制（中间结果 = 工作纸）。

**【前置】** ⚠️ **L1 S3、S4**（本点是它们的展开，**未学 L1 不要进本点**）

**【标准范例】** —— 复用他自己调试时的习惯
```
你在调 PID 时会做的事：
    把中间变量打印出来 → 看着它改下一步 → 再打印 → 再改
    "打印"就是把中间状态搬到你能看见的地方

LLM 的"工作纸"是同一件事：
    把中间结果**写进上下文** → 下一轮计算能看到它 → 继续推进

差别（很重要）：
    你能同时看到很多变量；
    LLM 的工作纸有**长度上限**（上下文窗口），写满了早期的内容就会被挤掉
    ← 这就是 T14"上下文增长后指令遵循下降"的根源
```

**【常见误解】**
1. 「一次前向计算能无限深」——讲义明确否定：**结构和深度是有限的**
2. 「更多 token 就一定更强」——讲义加了前提：**取决于能否找到推进步骤、能否识别错误**
   （对应 L1 S5 的"有效反馈"）
3. 「思维链是模型在思考」——讲义说的是**工作纸**，是**外化的中间状态**

**【适用边界】**
- 讲义明确声明"找解常常比验解难"是**类比，不是复杂性理论结论**——**不要当成定理引用**

**【预考题】**
1. 如果一次计算深度有限，模型凭什么能完成需要很多步的任务？
2. "更多 token"换来的是什么？有什么前提？

**【练习题 + 答案】**
- Q1（识别）：为什么"一次前向计算有限"不限制最终能力？
  A1：因为**中间结果可以写进上下文**，成为下一轮计算的输入，从而**串起很长的计算过程**。
- Q2（应用）：讲义说的"工作纸"指什么？
  A2：**输出的那一串 token**——它承载了中间状态，后续生成可以直接使用。
- Q3（迁移）：你在单片机里"把中间变量存到 RAM 再读回来用"，和"工作纸"像在哪？
  哪里不像？
  A3：像：都是**把中间状态外化，供后续使用**。
  不像：RAM 有明确的地址和容量规划；**上下文窗口是先进先出的、会被挤掉**，
  且"挤掉"是不可见的——这一点工程上必须警惕。

**【迁移题】**
解释为什么"让模型把草稿写出来"和"让它直接给答案"效果不同，用"工作纸"的说法。

**【掌握判定】**
- 能说清：能说出"中间结果写进上下文 = 工作纸"，并说出它的前提
- 能应用：能解释为什么上下文长度会成为实际约束
- 能回忆：隔一天能复述"更多 token 可能换来更多计算深度"

### T7 多约束指令遵循：形式检查 vs 质量

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§一步有限，为什么还能完成复杂任务（藏头诗三题）
- 要点：
  - 三题：① 八句诗，句首依次"计算机学院真牛逼"、"二零二六九月一日"八字依次嵌入、押韵、
    讲动物故事；② 一句话十八个汉字、全同偏旁、有意义；③ 全同音、写现代文言故事。
  - 「藏头与嵌字都能对上，句尾也有相近的韵感，但'方向'的'向'与其他句尾在普通话拼音中
    并不完全相同，读起来**有些句子也明显是为了凑约束**。它展示的是
    **模型能够寻找并修补一个多约束解，而不是宣告模型已经写出好诗**。」
  - 「'都含三点水'和'词典中都归为同一部首'仍然是不同要求。
    **要交给程序验收，就得先决定检查的是哪一个。**」
  - ⭐ 「这三道题把两类评价放在了一起。**藏头、字数、指定字和读音可以逐项检查；
    通顺、趣味和文学性则需要更丰富的判断。**模型通过形式检查，说明它能够搜索和纠错，
    **但形式检查没有覆盖的质量，并不会自动出现。**」

**【机制 / 为什么】** 材料给了区分（可逐项检查 vs 需丰富判断）和结论（未覆盖的质量不会自动出现）。

**【前置】** T4（可检查）、L1 S5（有效反馈）

**【标准范例】** —— 用他的工作场景
```
形式检查（可逐项验证）：
    "转速稳态误差 < 1%"       → 跑一次，读数据，能判定
    "代码编译无 error"        → 编译器判定

丰富判断（形式检查覆盖不到）：
    "这套 PID 参数调得好不好"  → 要综合超调、抗扰、噪声、工况
    "这段代码优雅不优雅"      → 没有机械判据

⭐ 讲义的意思：
    通过形式检查 ≠ 质量达标。
    "形式检查没有覆盖的质量，并不会自动出现。"
```

**【常见误解】**
1. 「满足所有明确要求 = 好」——讲义明确否定
2. 「先给出形式检查，模型就会自动把质量做好」——**不会**
3. 「'都含三点水'和'同一部首'是一回事」——讲义特别指出这是**两个不同的规格**，
   **要交给程序验收，必须先决定检查哪一个**

**【适用边界】**
- ⚠️ **缺口：讲义未给"质量类要求如何转成可检查形式"的方法**（T4 给了方向：示例、对比、反馈）

**【预考题】**
1. 一个东西通过了所有你写下的检查，它就对了吗？
2. “全带三点水”和“都归同一部首”，这个例子想说明什么？
3. ⭐【讲义原话·课堂提问】「课堂给了几道故意刁难人的写作题」，例如：
   **八句诗，句首依次是“计算机学院真牛逼”、八个字“二零二六九月一日”依次嵌入、还要押韵。**
   模型能做到“藏头与嵌字都能对上”——**这说明它有什么能力？又没说明什么？**
   （讲义原话：它展示的是“**模型能够寻找并修补一个多约束解**，
   而不是宣告模型已经写出好诗”。）

**【练习题 + 答案】**
- Q1（识别）：讲义把评价分成了哪两类？
  A1：**可以逐项检查的（藏头、字数、指定字、读音）** vs **需要更丰富判断的（通顺、趣味、文学性）**。
- Q2（应用）：为什么"要交给程序验收，就得先决定检查的是哪一个"？
  A2：因为**同一个说法可以有多种可检查的解释**（"都含三点水" vs "词典归同一部首"）。
  **不先确定检查什么，就无法实现自动验收**——这直接对应 L1 的 Spec→Impl 缺口。
- Q3（迁移）：你验收自己的 FOC 代码时，"能跑"之外还检查什么？哪些是形式检查、哪些是判断？
  A3：形式：编译通过、转速达到、误差在范围内。判断：噪声水平、抗扰表现、代码可维护性。

**【迁移题】**
给你正在做的一件事，分别写出它的"形式检查项"和"需要判断的部分"。

**【掌握判定】**
- 能说清：能区分两类评价，并说出"形式检查未覆盖的质量不会自动出现"
- 能应用：能把一个模糊说法拆成多种可检查的解释
- 能回忆：隔一天能说出两类评价的差别

### T8 ★ 上下文中的规则也会争夺注意力

**原子性**：只考一件事 ✓（"规则≠保证"与"加规则有代价"是同一问题，不拆）

**【讲义原话】**
- 出处：§上下文中的规则，也会争夺注意力
- 要点：
  - 「'在上下文里'**并不保证'每次都会正确遵循'**。」
  - 「提示词还会带来副作用。你说'白色背景，不要半透明效果'，
    模型可能把这句话变成**代码里的注释**：'白色背景（不要半透明效果）'。
    **它完成了背景设置，却也把原本只用于沟通的要求带进了产物。**」
  - 「一个看似合理的修补办法出现了：**再加一条永久规则**，禁止把用户要求写进注释。
    但**每遇到一次问题就增加一条规则，上下文会越来越长，约束之间也越来越难协调。
    这不是免费的增强。**」
  - ⭐ 「更合适的做法，是**区分长期适用的简短规则与当前任务需要的细节**。
    项目层面留下真正稳定的约定；特定任务的方法按需加载；
    **能够直接检查的要求，则尽量落到代码和验证结果上**。」
  - 「**删去一段无关说明，有时和增加一条关键要求同样有效。**
    模型需要的不是尽可能多的文字，而是**此刻做决定时用得上的信息**。」

⭐⭐ 本点与 T2 呼应：**能检查的要求 → 落到代码**（而不是越写越长的自然语言）。

**【机制 / 为什么】** 材料给了机制（上下文变长 → 约束难协调）和原则（区分长期/当前、能检查的落代码）。

**【前置】** T1（上下文构成）、T2（提示词 ≠ 机制）、T4（可检查）

**【标准范例】** —— 用他自己的经验
```
你一定经历过类似的（在代码里）：
    出一次 bug → 加一个 if 判断
    再出一次 → 再加一个
    最后：一堆互相冲突的特判，谁也不敢删，改一处崩三处
    ← 这就是你在 A 系列里学过的「晦涩」和「改动放大」

上下文里的"加规则"是同一件事：
    出一次问题 → 加一条要求
    再加一条……
    → 上下文越来越长，规则之间开始互相干扰

⭐ 讲义给的对策和你在软件设计里学到的是同一条：
    稳定的约定放项目层（= 稳定的接口）
    特定任务的放按需加载（= 局部实现）
    能直接检查的落到代码和验证结果（= 让机制而不是约定来保证）
```

**【常见误解】**
1. 「规则写进上下文就会被遵守」——讲义明确：**不保证每次正确遵循**
2. 「规则越多越保险」——**不是免费的**：上下文变长、约束难协调
3. 「删掉说明是偷懒」——讲义说：**删一段无关说明，有时和加一条关键要求同样有效**

**【适用边界】**
- ⚠️ **缺口：讲义未给"什么时候该加规则、什么时候该改机制"的判据**（T2 的"能检查就落代码"是部分答案）

**【预考题】**
1. 把一条要求写进提示词，模型就一定会遵守吗？
2. 遇到问题就加一条规则，会有什么代价？

**【练习题 + 答案】**
- Q1（识别）：为什么"写在上下文里"不等于"会被正确遵循"？
  A1：因为上下文中的规则**会与其他内容争夺注意力**，且模型不保证每次都对；
  讲义原文：「'在上下文里'并不保证'每次都会正确遵循'」。
- Q2（应用）：模型把"不要半透明效果"写进了代码注释。这个副作用说明了什么？
  A2：说明**给模型的要求可能被带进产物**——它完成了背景设置，却把
  "只用于沟通的要求"写进了代码。**要求的作用范围没有被限定住。**
- Q3（★ 应用）：讲义给的对策是什么？
  A3：**区分长期适用的简短规则与当前任务需要的细节**：
  项目层留稳定约定、特定任务方法按需加载、**能直接检查的要求尽量落到代码和验证结果上**。
- Q4（迁移）：你写单片机代码时，"稳定的模块接口"和"临时的调试开关"应该怎么放？
  A4：接口放头文件（稳定、对外）；调试开关放局部或条件编译（临时、可去掉）。
  **和"长期规则 vs 当前细节"是同一个区分。**

**【迁移题】**
把你现在用的一段"很长很啰嗦的提示词"精简一次，说出你删了什么、为什么删。

**【掌握判定】**
- 能说清：能说出"规则≠保证"和"加规则有代价"，并复述三条对策
- 能应用：能判断一条要求应该放项目层、按需加载，还是落到代码
- 能回忆：隔一天能复述"删去一段无关说明，有时和增加一条关键要求同样有效"

### T9 ★ "你是一位审稿人"，还不够

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§"你是一位审稿人"，还不够
- 要点：
  - 「'扮演审稿人'**可以提示语气和输出结构，却没有把一个好审稿人的方法自动交给它**。」
  - 「论文的信息密度非常高。作者不仅给出了答案，也**替读者选好了问题、术语、
    比较对象和衡量标准**。如果顺着文章走完一遍才开始评价，很容易**在不知不觉中接受了
    作者的整个框架**。你以为自己在批判性思考，其实只是在作者划好的场地里打转。」
  - ⭐ 三条路线：「**第一条从判据出发**，先还原论文声称的贡献，再问每项贡献需要达到什么标准，
    证据在哪里。**第二条审查证据**，把核心主张、实验支持、未验证假设和替代解释一项项对应起来。
    **第三条站到复现者或反方的位置**，重算一个关键结果，寻找最小反例，
    明确什么观察会推翻结论。」
  - ⭐ 「这几条路线的价值来自**问题不同**。若一开始就共享同一个总体印象，
    最后可能只得到**同一个判断的三份润色**。**独立形成初步意见，再比较分歧，
    才更容易发现原先没有看到的东西。**」

**【机制 / 为什么】** 材料给了机制（角色给语气不给方法）和判据（独立形成意见再比较分歧）。

**【前置】** T2（提示词 ≠ 机制：同一个道理的另一个实例）

**【标准范例】** —— 用他熟悉的"审题"打比方
```
你在做考研真题讲解时，做的事其实和讲义说的一样：

❌ "扮演一个信号与系统老师，讲讲这道题"
   → 它会给你一段像讲课的文字，但**没有把"怎么讲透一道题"的方法交给它**

✅ 拆分：
   ① 判据路线：这道题考什么？要达到什么才算做对？
   ② 证据路线：每一步推导的依据是什么？有没有隐含假设？
   ③ 反方路线：如果结论是错的，会看到什么？（构造反例）
```
> ⭐ 关键句：**「你以为自己在批判性思考，其实只是在作者划好的场地里打转。」**
> 这和你讲题时的体会一致：**顺着解题步骤走一遍，不等于理解了这道题的设计意图。**

**【常见误解】**
1. 「给了角色，就给了能力」——讲义明确否定
2. 「问三个不同的问题 = 三条独立路线」——**关键是问题是否不同**；
   若共享同一个总体印象，只是**同一个判断的三份润色**
3. 「独立意见之后再合并 = 浪费时间」——恰相反，**分歧才是发现盲点的入口**

**【适用边界】**
- ⚠️ **缺口：讲义未说清三条路线该由同一个模型跑三次，还是三个独立 Agent 跑**

**【预考题】**
1. 让 AI"扮演一个专家"，它就有了专家的方法吗？
2. 为什么"顺着论文读完再评价"容易掉进作者的框架？

**【练习题 + 答案】**
- Q1（识别）：为什么"你是一位审稿人"这样的角色设定不够？
  A1：因为它只**提示语气和输出结构**，**没有把一个好审稿人的方法交给它**。
- Q2（应用）：讲义给的三条审稿路线分别是什么？
  A2：**① 从判据出发（贡献是什么、需要什么标准、证据在哪）；② 审查证据
  （主张—实验—未验证假设—替代解释对应起来）；③ 站到反方/复现者位置
  （重算关键结果、找最小反例、明确什么观察会推翻结论）。**
- Q3（★ 应用）：为什么强调"独立形成初步意见，再比较分歧"？
  A3：因为如果一开始就共享同一个总体印象，**三条路线只会产出同一个判断的三份润色**。
  只有**独立**形成意见再比较，**分歧处**才暴露原先没看到的东西。
- Q4（迁移）：你准备一节课时，怎么用这三条路线检查自己讲得对不对？
  A4：① 这节课要让学生会什么？达到什么算会？② 我给的每个例子支持哪个结论？
  有没有隐含假设？③ 如果学生按我的方法做错了，会是什么原因？

**【迁移题】**
拿一篇你正在读的技术材料，按三条路线各写一条你会追问的问题。

**【掌握判定】**
- 能说清：能说出角色设定为什么不够，并复述三条路线
- 能应用：能对一个任务设计出"问题不同"的三条独立路线
- 能回忆：隔一天能说出"独立形成意见再比较分歧"这条判据

### T10 skill 该沉淀什么

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§"你是一位审稿人"，还不够
- 要点：
  - 「当一套做法**多次有效**，就可以把它**沉淀成 skill**。
    **Skill 看起来是一段提示词，真正值得保存的，是成功经验中的搜索策略、判断标准和检查点。**
    它帮助 Agent **复用一种做事的方法**，而不是每次重新凭第一印象发挥。」
  - 「**Skill 也不是越长越好。**如果把所有想得到的要求都塞进去，
    它本身就变成了一道复杂的指令遵循题……**保留真正影响决策的内容，
    把机械工作交给脚本，把需要时才看的材料单独放置**。」

**【机制 / 为什么】** 材料给了判据（该保存什么、不该塞什么）。

**【前置】** T8（加规则有代价）

**【标准范例】** —— 用三个具体的部件说明这条原则
```
一个 skill（可复用的做事方法）应该长这样：

✅ 保存“方法”：
   先测再讲、一次只讲一小段、讲完立即让学习者复述
   → 这些是**搜索策略、判断标准、检查点**

✅ 把机械工作交给脚本：
   “卡片到期日怎么算”这种确定性计算，写成脚本
   —— 不该让模型每次现想，也不必占上下文

✅ 把“需要时才看”的材料单独放：
   主文件只保留影响决策的内容（保持精简）；
   示例库、术语表、参考资料放到单独文件，按需加载

❌ 如果反过来：把所有细节都塞进主文件
   → 它本身变成一道复杂的指令遵循题（就是讲义说的藏头诗）
```
> ⭐ **讲义这一段与“上下文工程”是同一套道理**（T8：加规则有代价）。
> 一个 skill 就是一份**长期活在上下文里**的提示词，所以它同样要精。

**【常见误解】**
1. 「skill 就是一段提示词」——讲义明确：值得保存的是**方法**，不是文字
2. 「skill 越全越好」——**会变成复杂的指令遵循题**
3. 「所有内容都该放进去」——应**保留影响决策的**，机械工作交脚本，长材料按需加载

**【适用边界】**
- ⚠️ **缺口：讲义未给"什么算'多次有效'"的判断门槛**

**【预考题】**
1. 一个 skill 里最该保存的是什么？
2. skill 写得越长，效果越好吗？

**【练习题 + 答案】**
- Q1（识别）：skill 里真正值得保存的是什么？
  A1：**成功经验中的搜索策略、判断标准和检查点**——帮助 Agent 复用一种做事的方法，
  而不是每次凭第一印象发挥。
- Q2（应用）：为什么"把所有要求都塞进 skill"会适得其反？
  A2：因为那些要求**互相争夺注意力**（T8），skill 本身变成一道复杂的指令遵循题，
  和藏头诗类似——**约束太多反而做不好**。
- Q3（迁移）：你的 备课方法论 里，哪些内容属于"方法"、哪些属于"机械工作"、
  哪些属于"按需加载"？
  A3：方法：先测再讲、费曼复述、掌握判定闸门；机械：`scripts/due.py` 算到期；
  按需：`references/` 下的 methods/prep/questioning。

**【迁移题】**
挑一个你反复做的事，写出它的"搜索策略、判断标准、检查点"各一条。

**【掌握判定】**
- 能说清：能说出 skill 该保存什么、不该塞什么
- 能应用：能把一个经验拆成方法/机械工作/按需材料三类
- 能回忆：隔一天能复述"保留真正影响决策的内容"

### T11 ★★★ 为什么大仓库有时比空项目更容易

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§为什么大仓库有时比空项目更容易
- 要点：
  - 「从零做一个看起来不难的产品，AI 可能在某个时间点开始不断翻车；
    **进入一个成熟的大型系统，反而能够完成相当复杂的修改**。」
  - 「成熟代码库**已经做出了许多决定**：怎样命名，模块如何分层，错误怎样传播，测试放在哪里。
    Agent 在解决局部问题时，**可以学习附近的例子，沿着现有结构补充实现**。
    **代码量虽然大，当前任务需要自由选择的事情却可能更少。**」
  - 「空项目恰好相反。**没有已有结构约束选择，每次局部实现都可能顺手做出一个长期设计决定。**
    如果最初就形成了混乱的惯例，后续生成又以这些惯例为上下文，**AI slop 就会不断叠加**。」
  - ⭐⭐⭐ 「**代码库本身也是提示词。**它会示范怎样做，也可能示范怎样把问题继续藏起来。」

**【机制 / 为什么】** ✅ 材料给了完整机制（约定多 → 自由选择少）。

**【前置】** L1 S15（修改的局部性）、T1（上下文）

**【标准范例】** —— 用他最有发言权的领域
```
你在两家公司写过单片机程序，体会过这个差别：

成熟工程（有既有代码）：
    时钟初始化写在哪、外设怎么封装、错误怎么上报、命名什么风格
    → 都已经有既定做法，你**照着写**就行
    → 需要你自己决定的事反而少

空项目（从零开始）：
    每一次写函数都在顺手做长期决定：
      这个变量放全局还是传参？这个模块要不要单独的 .h？
      错误码还是返回布尔？中断里能不能调 printf？
    → 每一次都"随手"决定，累积起来就是一堆没人整体设计过的东西
    → 后面再改，改一处崩三处

⭐ "代码库本身也是提示词"：
   你新写的代码会照着你旁边的代码长 —— 不管旁边的代码是好是坏
```
> ⭐ **这是本讲最强的一句**：**代码库示范怎样做，也可能示范怎样把问题继续藏起来。**

**【常见误解】**
1. 「大仓库一定好改」——讲义明确否定了这个推论
2. 「模型会自动认出最佳实践」——讲义也明确否定：**它可能模仿历史包袱**
3. 「空项目更自由所以更好」——自由恰恰是问题：**每次局部实现都可能顺手做出长期设计决定**

**【适用边界】**
- 讲义明确把"给 Agent 看一个相近领域的优雅成熟系统能否提高质量"标为
  ⭐「**一个未经实验验证的猜测**」。⚠️ **不要当结论引用**
- ⚠️ **缺口：讲义未给"如何判断现有代码库是好示范还是坏示范"的方法**
- 【外部补充】可用 L1 S15 的"修改局部性"来判：**改一处要不要动多处**——但要标明是外部推得

**【预考题】**
1. 你觉得让 AI 在成熟的大项目里干活，和在空项目里从零开始，哪个更容易？
2. 空项目最大的风险是什么？（提示：不是“东西少”）
3. ⭐【讲义原话·课堂提问】「**从零做一个看起来不难的产品，AI 可能在某个时间点
   开始不断翻车；进入一个成熟的大型系统，反而能够完成相当复杂的修改。**」
   为什么会出现这种反差？

**【练习题 + 答案】**
- Q1（识别）：为什么成熟大仓库反而可能更好改？
  A1：因为它**已经做出了许多决定**（命名、分层、错误传播、测试位置），
  Agent 可以**照着现有结构补**；**代码量大，但当前任务需要自由选择的事情更少**。
- Q2（应用）：空项目的风险是什么？
  A2：**没有已有结构约束选择，每次局部实现都可能顺手做出一个长期设计决定**；
  一旦形成混乱惯例，后续生成又以它为上下文，**问题不断叠加**。
- Q3（★ 关键）：解释"代码库本身也是提示词"。
  A3：因为代码库**进入了上下文**（T1），会示范"该怎么做"。
  所以它既是**正面示范**（学现有结构），也可能**示范怎样把问题继续藏起来**。
- Q4（迁移）：你接手一份别人写的很乱的单片机工程，继续往里加功能会有什么后果？
  A4：**你会照它的样子写**——乱的部分被延续和放大。
  **这就是"代码库本身也是提示词"的负面版本。**

**【迁移题】**
你的一个项目里，有没有"因为旁边就是这么写的，所以我也这么写"的地方？它示范得对吗？

**【掌握判定】**
- 能说清：能说出"约定多 → 自由选择少"这个机制，并解释"代码库本身也是提示词"
- 能应用：能判断一个空项目风险在哪、一个成熟项目该学什么
- 能回忆：隔一天能复述那句话

### T12 一个未经验证的猜测（标注为待查证）

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§为什么大仓库有时比空项目更容易
- 要点：「课堂进一步提出了**一个未经实验验证的猜测**：给 Agent 看一个**相近领域、

  比较实现后的修改代价与缺陷，而不仅仅看第一版能否运行。**」

**【机制 / 为什么】** ⚠️ 材料**自己声明这是猜测，未验证**。本点的价值不是"结论"，
而是**如何设计一个能验证它的实验**。

**【前置】** T11

**【标准范例】** —— 讲义自己给的实验设计
```
要验证的假设：
    给 Agent 看"相近领域、设计优雅"的成熟系统 → 实现质量提高

对照条件（讲义给的三种）：
    条件 A  无参考
    条件 B  完整参考（整个项目）
    条件 C  精选参考（几个关键例子）

⚠️ 关键：**评价指标不能是"第一版能否运行"**
   讲义明确说：比较**实现后的修改代价与缺陷**
   ← 这正是 L1 S15 的"修改的局部性"（改动放大）
```
> ⭐ 这个实验设计本身就是一次 **Intent → Spec** 的良好示范：
> 把模糊的"能不能提高质量"变成了**可比较的三个条件和两个指标**。

**【常见误解】**
1. 「讲义说了看大仓库有好处」——**讲义明确说这是猜测，不是结论**
2. 「看更多参考总是更好」——未必：**可能把不合适的架构也学过来**
3. 「第一版能跑就说明质量高」——讲义明确反对用这个当指标

**【适用边界】**
- ⚠️ **本点整体处于【待查证】状态**。教学时应明确告诉学习者：
  **这是"如何设计一个实验"，不是"一个已知的结论"**

**【预考题】**
1. "让 AI 看一个优秀的开源项目，它就能写得更好"——这个说法成立吗？
2. 如果要验证它，你会怎么设计对照？

**【练习题 + 答案】**
- Q1（识别）：讲义对"看优雅系统能否提高质量"的态度是什么？
  A1：**这是一个未经实验验证的猜测，还不是结论。**
- Q2（应用）：讲义建议用什么指标比较效果？
  A2：**实现后的修改代价与缺陷**，而**不是**第一版能否运行。
- Q3（迁移）：你自己想验证一个"某种做法是否有效"的想法，会怎么设计对照？
  A3（开放，要求包含）：**明确要检验的假设、设置可比较的条件、选择能反映真实代价的指标**
  （而不是最容易测的指标）。

**【迁移题】**
把你自己的一条"经验之谈"改写成一个可验证的实验。

**【掌握判定】**
- 能说清：能说出这是猜测、以及应该用什么指标比较
- 能应用：能设计一个包含对照条件的简单实验
- 能回忆：隔一天能说出"还不是结论"

### T13 ★ Token 花完了，研究为什么还没推进

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§Token 花完了，研究为什么还没有推进
- 要点：
  - 「**把任务交给更强的模型、投入更多 token，并不保证任何长程问题都会收敛。**」
  - 失败案例：优化一个符号执行引擎，把想法和 benchmark 交给 Agent，
    **花了很多 token，最终没有得到结果**。
  - ⭐ 「**原稿没有给出已经查明的失败原因，因此这里能做的是提出待检验的解释。**」
    可能一：**总 benchmark 分数提供的反馈太粗**——没有变快，
    究竟是求解器、路径搜索、缓存、还是新开销？**混在一起就无法判断下一步试什么**。
    可能二：**任务把"把这个想法实现好"当成了目标**，
    但研究真正要回答的是"**这个想法是否成立**"。
  - ⭐ 「一个**能否定原想法的实验，有时比更多代码更有价值**。」
  - 「更有用的起点可能是：先**测量主要瓶颈**，把想法写成**一个可以被实验推翻的预测**，
    再构造**能够快速反馈的小实验**。确认局部机制有效以后，才放回完整系统，
    检查收益是否仍然存在。」
  - 「研究中的'推进'**可以是缩小未知，也可以是排除一个方向**；
    不能只把它定义成最终分数必须上涨。」

**【机制 / 为什么】** ⚠️ **讲义明确说"原稿没有给出已经查明的失败原因"**，
给出的两条是**待检验的解释**。教学时必须如实说明。

**【前置】** L1 S5（有效反馈）、T4（写清完成）

**【标准范例】** —— 用他自己的调参经历
```
❌ 反馈太粗的版本：
    "把这段代码优化一下，让它更快"
    → 改完只知道"快了/没快"
    → 快了多少？哪一部分快了？不知道 → 下一步试什么？不知道

✅ 反馈可分辨的版本：
    先测量：总时间的 80% 花在哪一段？
    再预测："如果我改这里，这一段应该从 X 降到 Y"
    再做**能快速验证的小实验**
    → 得到的是"这个假设成立/不成立"，而不是"总分涨没涨"

⭐ 讲义的关键判断：
   "一个能否定原想法的实验，有时比更多代码更有价值"
   → 因为**排除一个方向也是推进**（缩小未知）
```

**【常见误解】**
1. 「多花 token / 换更强的模型就能解决长程问题」——讲义明确否定
2. 「分数没涨 = 没推进」——讲义明确：**缩小未知、排除方向也是推进**
3. 「这两条原因是结论」——**不是**。讲义明说"原稿没有给出已查明的失败原因"，
   这两条是**待检验的解释**

**【适用边界】**
- ⚠️ **缺口/待查证**：讲义自己声明失败原因未查明。**教学时必须保留这个不确定性**，
  禁止把它讲成"就是因为反馈太粗"

**【预考题】**
1. 一个任务投入了很多 token 却没结果，可能是什么原因？
2. “研究没有进展”和“分数没涨”，是同一件事吗？
3. ⭐【讲义原话·课堂提问】「**更有用的起点可能是先测量主要瓶颈，
   把想法写成一个可以被实验推翻的预测，再构造能够快速反馈的小实验。**」
   为什么这样比“直接开始实现”更有效？

**【练习题 + 答案】**
- Q1（识别）：讲义给了哪两条待检验的解释？
  A1：**① 总 benchmark 分数提供的反馈太粗**，无法区分是求解器、搜索策略、缓存还是新开销，
  于是不知道下一步试什么；**② 目标设成了"把想法实现好"**，
  而研究真正要回答的是"**这个想法是否成立**"。
- Q2（应用）：讲义建议的更有用的起点是什么？
  A2：**先测量主要瓶颈 → 把想法写成可被实验推翻的预测 → 构造能快速反馈的小实验
  → 局部机制确认有效后再放回完整系统检查收益。**
- Q3（迁移）：你怀疑"换了无感算法能让低速更稳"，会怎么设计实验？
  A3：**先测低速段的具体指标（如转速纹波）→ 写成可推翻的预测
  （"换 SMO 后 100rpm 时纹波应从 X 降到 Y"）→ 只在该工况做小实验验证 → 再放回整机**。

**【迁移题】**
找一个你"投了很多时间却没进展"的事，指出当时缺的是"反馈分辨率"还是"目标设错了"。

**【掌握判定】**
- 能说清：能说出两条待检验解释，并说明它们**未经查证**
- 能应用：能把一个模糊目标改写成"可被实验推翻的预测"
- 能回忆：隔一天能说出"能否定原想法的实验比更多代码更有价值"

### T14 ★ 人应该盯住哪些地方

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§人应该盯住哪些地方
- 要点：
  - 「课堂给出的经验恰好有点反直觉：**我知道怎样让某个任务更快完成，却越来越少干预了。**」
  - ⭐ 「原因在于，**单个任务的完成时间与一天能完成的任务总量，是两个不同目标**。
    如果 Agent 走一点弯路最后也能完成，我可以把注意力移到另一件事上。
    **机器多花一些时间，换回人的时间，整体产出反而增加。**」
  - ⭐ 「这种取舍需要有边界。**接口已经看过、结果可以检验、实现出了问题能够替换时，
    可以让 Agent 自己探索。相反，一个会扩散到许多模块的接口决定，
    一个昂贵或难以恢复的动作，就更值得提前关注。**
    **人的注意力应当按照决策影响和返工代价分配，而不是平均撒在每一行代码上。**」
  - 「随着上下文增长，**指令遵循可能下降**，而**最近的要求或刚加载的方法往往更容易被执行**。」
  - ⭐ 「工程上可以主动**缩短关键要求到关键决定之间的距离**」——
    阶段切换时重新确认目标、接口和未决问题；把能检查的不变量落实成测试；
    让错误在继续传播之前暴露；**上下文压缩也要保存当前约束和证据，而不只是流水账**。

⭐⭐ 与本讲 T2/T4 呼应：**"落成可检查的形式" = "缩短关键要求到关键决定的距离"**。

**【机制 / 为什么】** ✅ 材料给了完整的判据（按决策影响和返工代价分配注意力）。

**【前置】** L1 S14（高代价猜测）、T4（可检查）、T8（注意力争夺）

**【标准范例】** —— 用他自己的决策场景
```
你在嵌入式项目里的两类决定：

低影响 / 易回退：
    某个函数的命名、某个局部变量的类型
    → 让 AI 自己定，错了随手改         ← 不用盯

高影响 / 难回退：
    外设的中断优先级怎么分配
    电流环和速度环的调用关系
    → 改起来牵连一片，还可能烧硬件     ← 必须提前盯

⭐ 讲义的判据：**按"决策影响 × 返工代价"分配注意力，不平均撒**
   "一个会扩散到许多模块的接口决定" = 高影响
   "一个昂贵或难以恢复的动作"       = 高返工代价
```

**【常见误解】**
1. 「随时干预才是负责」——讲义的经验**恰好相反**：**机器多花时间换回人的时间，总产出更高**
2. 「不干预 = 不管」——不是。**注意力要转移到另一件事上**，不是省下来
3. 「上下文越长越好」——讲义说：**上下文增长时指令遵循可能下降**，
   **最近的要求更容易被执行** → 所以要**缩短关键要求到关键决定的距离**

**【适用边界】**
- 讲义说"可能下降，具体表现取决于模型和任务"——**不是定律**
- ⚠️ **缺口：讲义未给"哪些决定算高影响"的清单**（L1 S14 给了三类：架构、数据表示、验收标准）

**【预考题】**
1. AI 在做任务时，你会一直盯着吗？为什么？
2. 哪些决定值得你提前干预？

**【练习题 + 答案】**
- Q1（识别）：为什么"知道怎样更快完成"却"越来越少干预"？
  A1：因为**单个任务的完成时间与一天的任务总量是两个不同目标**。
  Agent 走一点弯路也能完成时，**把注意力移到另一件事上，整体产出反而增加**。
- Q2（应用）：讲义给的两条边界是什么？
  A2：**可以让 Agent 自己探索**：接口已看过、结果可检验、实现出问题能替换。
  **值得提前关注**：会扩散到许多模块的接口决定；昂贵或难以恢复的动作。
- Q3（★ 应用）：为什么要"缩短关键要求到关键决定之间的距离"？
  A3：因为**上下文增长时指令遵循可能下降，最近的要求更容易被执行**。
  所以要在阶段切换时**重新确认目标、接口和未决问题**，把能检查的不变量落实成测试，
  让错误在传播前暴露。**上下文压缩要保存当前约束和证据，不是流水账。**
- Q4（迁移）：你带新人时，"哪些事放手、哪些事必须提前对齐"，用的是什么判据？
  和讲义这条一样吗？
  A4：（开放）大多数人本能地用了"影响 × 返工代价"这条判据——**只是没给它起名字**。

**【迁移题】**
列出你现在工作里"应该盯"和"可以放手"的各三件事，说明判据。

**【掌握判定】**
- 能说清：能说出"两个目标"的差别，以及两条边界
- 能应用：能按"决策影响 × 返工代价"给决定分类
- 能回忆：隔一天能复述"缩短关键要求到关键决定之间的距离"

### T15 在不确定性中探索

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§在不确定性中探索
- 要点：
  - 「'帮我考虑几种方案'通常有效，**却可能过早结束**。模型给出几个听起来合理的答案，
    已经满足了'几种'的数量要求；**更有意思的方案，也许仍在它没有走到的方向里**。」
  - ⭐ 「此时，**多沿一条思路想一会儿，与主动探索更多不同思路，是两种不同的算力使用方式。**」
  - 例：取名。「如果直接要几个答案，模型可能给出自己偏好的高概率组合；
    **许多家庭同时询问，又可能迎来 AI 时代的新一代'子涵'**。」
  - 「要扩大探索，可以**先划分空间**：从典故、音韵、方言、时代感等不同角度生成候选，
    再检查出处、谐音、书写和个人偏好。也可以**让不同 Agent 独立提出候选或负责挑错**……
    **关键在于它们是否看了不同方向、提出了不同问题，而不在于开了多少个看起来相同的窗口。**」
  - ⭐ 「**'给更多名字'解决的是候选数量，'哪些名字值得留下'则需要评价标准。
    没有分辨率的筛选，可能只是把一个平庸答案变成一百个平庸答案。
    探索空间与评价方法应当一起设计。**」
  - 「**增加计算资源时，应当考虑怎样增加探索的差异，而不是只增加同一种思路的重复次数。**」

**【机制 / 为什么】** 材料给了机制（两种算力用法）和判据（探索空间与评价方法一起设计）。

**【前置】** T9（三条独立路线）、L1 S5（有效反馈）

**【标准范例】** —— 用他熟悉的场景
```
取名字的例子，换成你的事：

❌ 只是重复问：
    "给我 10 个技术视频选题"
    → 得到 10 个方向雷同的选题（都是同一思路的高概率组合）

✅ 先划分空间再探索：
    从"受众痛点 / 竞品空白 / 我的独有经验 / 时效热点"四个**不同角度**各出候选
    → 方向是真的不同

⭐ 然后才是关键：
    "哪些选题值得做" —— 这需要**评价标准**
    没有标准的筛选 = **"把一个平庸答案变成一百个平庸答案"**
```

**【常见误解】**
1. 「多问几次 = 更多探索」——不是。**若思路相同，只是重复次数**
2. 「方案多就是好」——讲义明确：**没有分辨率的筛选，只是放大平庸**
3. 「探索和评价是两件事」——讲义明确：**应当一起设计**

**【适用边界】**
- ⚠️ **缺口：讲义未给"如何设计评价标准"的方法**（只给了方向：一起设计）

**【预考题】**
1. 让 AI"给我几个方案"，为什么常常都是差不多的？
2. 拿到 20 个候选，接下来最需要什么？

**【练习题 + 答案】**
- Q1（识别）：讲义区分了哪两种算力使用方式？
  A1：**多沿一条思路想一会儿** vs **主动探索更多不同思路**。
- Q2（应用）：为什么"开很多窗口并行问"未必有更大探索？
  A2：因为**关键在于它们是否看了不同方向、提出了不同问题**，
  而不在于开了多少个**看起来相同**的窗口。
- Q3（★ 应用）：为什么"探索空间与评价方法应当一起设计"？
  A3：因为"给更多候选"只解决**数量**；"哪些值得留下"需要**评价标准**。
  **没有分辨率的筛选，只是把一个平庸答案变成一百个平庸答案。**
- Q4（迁移）：你要给自己选一个 FOC 调试方案，会怎么"划分空间"再探索？
  A4：按**不同判据**切：手动整定 / 自整定 / 模型辨识 / 试凑；每个方向出 1-2 个候选，
  **再用同一套评价标准（稳态误差、超调、抗扰、实现复杂度）筛选**。

**【迁移题】**
找一件你正在纠结"选哪个"的事，先划分空间列出候选，再写下评价标准。

**【掌握判定】**
- 能说清：能区分两种算力用法，并说出为什么要"一起设计评价"
- 能应用：能对一个决策先划分空间再探索，并给出评价标准
- 能回忆：隔一天能复述"增加探索的差异，而不是增加重复次数"
