### S1 LLM 的接口：`Pr[token | context]`

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§从语言模型到能够行动的 Agent
- 要点：「从使用者的角度，可以先把自回归语言模型理解为一个**条件概率分布**：给定已有上下文，
  预测下一个 token，即 `Pr[token | context]`。」

**【机制 / 为什么】** 讲义给出了这个接口的定义，但**没解释自回归为什么能产生"看起来在思考"的效果**——
那一层放在 S3。

**【前置】** 无（本讲真正的起点）

**【标准范例】** —— 用你熟的语言重写
```
输入（上下文）：  "今天天气真"
模型要算的是：    P(下一个 token = "好" | "今天天气真")  = ?
                 P(下一个 token = "冷" | "今天天气真")  = ?
选一个，接到后面 → 新的上下文 = "今天天气真好" → 重复
```
> ⚠️ 这和你在单片机里写的**查表 + 状态机**在形式上是一回事：
> **输出接到输入上，一步步往下走**。区别只是"表"不是写死的，而是一个概率分布。

**【常见误解】**
1. 「模型是在数据库里检索答案」——不是，它是**算下一个 token 的概率**，没有"查答案"这一步
2. 「`context` 就是你这次输入的那一句话」——不只。上下文是**这一轮对话里模型能看到的全部内容**
   （含它自己先前吐出来的、以及被塞进去的文件内容）
3. 「概率分布 = 不确定性 = 不可靠」——形式上是概率，但**解码策略**（选哪个）另有一套规则

**【适用边界】**
- 讲义明确说这是「**从使用者的角度**」的简化理解。它是**够用的心智模型，不是模型的完整实现**
- 讲义也提示这只是当前主流形态：「模型未来是否仍以逐 token 生成作为主要计算方式，课堂也提出了开放的设想」
  —— 所以这是**当下的界面，不是永恒的真理**

**【预考题】**（学之前问，此时他答不出）
1. 如果模型只是"预测下一个 token"，它凭什么能写出一整段有逻辑的代码？
2. `context` 里除了你打的那句话，还可能有什么？

**【练习题 + 答案】**
- Q1（识别）：`Pr[token | context]` 里，符号 `|` 读作什么？含义是什么？
  A1：读作"在……条件下"。含义是**给定 context 这个条件下，某个 token 出现的概率**。
  ⚠️ 这个词他的母语领域有：**条件概率**，信号与系统里处处在用。可直接用。
- Q2（应用）：模型输出"我今天"之后，下一轮计算的条件是什么？
  A2：`context` 变成了原来的上下文 + "我今天"，模型算的是 `Pr[token | 原上下文 + "我今天"]`。
  **关键：输出成了下一轮的输入。** 这就是"自回归"。
- Q3（迁移）：单片机的状态机里，当前状态决定下一个状态；LLM 里"当前状态"是什么？
  A3：当前状态 = **上下文**（含已生成的内容）；"状态转移" = 采样出下一个 token 并接上去。
  差别：状态机的转移表是**你写死**的；LLM 的"转移"是**算出来**的。

**【迁移题】**
用你自己的话解释：为什么说 LLM 的输出"既是结果，又是下一步的输入"？

**【掌握判定】**
- 能说清：不看材料能解释 `Pr[token|context]` 里两部分的角色，并说出输出如何变成下一轮输入
- 能应用：给一段对话，指出下一轮的条件是什么
- 能回忆：隔一天能凭记忆写出这个式子并解释

### S2 token 是什么

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§从语言模型到能够行动的 Agent
- 要点：「Token 是模型处理文本的**基本单位**，**不必恰好对应一个汉字或一个单词**。」

**【机制 / 为什么】**
- 材料给了断言"不必对应"，但**没给 token 是怎么切出来的**（分词算法、词表大小、为什么这样设计）。
- ⚠️ **缺口：讲义未给出 tokenization 的机制。** 本讲不需要展开；若学习者追问，
  只答"按统计规律切、常见片段整块保留"，并标注为【外部补充】。

**【前置】** S1

**【标准范例】** —— 用一个反例让"不是汉字也不是单词"落地
```
"生成式软件工程"  可能被切成： ["生成", "式", "软件", "工程"]        ← 4 个 token
"ChatGPT"        可能被切成： ["Chat", "G", "PT"]                  ← 3 个 token，不是 1 个"词"
"2026"           可能被切成： ["20", "26"]                        ← 数字也可能被切开
```
⚠️ 具体切法**随模型而异**，上例是**示意**，不是某个模型的真实词表。
**这不影响理解，但不要当成事实引用。**（标记：【待查证】具体切法）

**【常见误解】**
1. 「一个汉字 = 一个 token」——讲义明确否定了
2. 「一个单词 = 一个 token」——同样否定
3. 「token 是字符」——不是。它是**统计上常一起出现的片段**

**【适用边界】**
- token 的边界**取决于模型的词表**，不同模型不同
- 因此"同一句话在不同模型里占多少 token"**不能直接比较**——这一点讲义没提，但影响实际使用（计费、上下文长度）

**【预考题】**
1. "你好世界" 是几个 token？（他大概率会答 4）
2. 为什么模型不直接按"字"处理，而要发明 token 这个单位？（他答不出）

**【练习题 + 答案】**
- Q1（识别）：token 和"汉字""单词"是什么关系？
  A1：**没有固定的一一对应关系**。token 是模型处理文本的基本单位，可能是一个字、
  半个词、一个常用词，也可能是几个字符的片段。
- Q2（应用）：为什么说"上下文窗口 128K token"不等于"能读 128K 个汉字"？
  A2：因为 1 个汉字可能占多个 token（也可能若干个汉字合成 1 个）。**token 数和字数不成固定比例。**
- Q3（迁移）：这和信号里的"采样"有什么像的地方？
  A3：都是**把连续的东西离散成基本单元**再处理。差别：采样是按时间等间隔切；
  tokenization 是按统计规律切，切点不均匀。

**【迁移题】**
如果两个模型都声称"支持 100 万 token 上下文"，能直接比较谁读的文本更多吗？为什么？

**【掌握判定】**
- 能说清：不看材料能说出 token 与字/词的关系，并说明"为什么不能按字数换算"
- 能应用：解释为什么"上下文长度用 token 计"会导致不同模型不可直接比较
- 能回忆：隔一天能说出"token 是基本单位，不对应字或词"

### S3 为什么"预测下一个 token"不能判定能力上限

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§从语言模型到能够行动的 Agent
- 要点：「"预测下一个 token"描述的是**计算怎样展开**，**不能直接拿来判定能力上限**。
  模型输出的文字会进入后续上下文：先写下一个中间结果，再基于它继续计算；发现矛盾，再尝试修正。
  一个看似静态的概率分布，由此可以**展开成很长的计算过程**。」

**【机制 / 为什么】**
材料**给了机制**：输出 → 进入上下文 → 基于它继续算 → 可以自我修正。
⭐ 这正是"接口简单 ≠ 能力有限"的原因。**这是本讲最反直觉的一步。**

**【前置】** S1

**【标准范例】** —— 用他自己写代码的经验
```
你在单片机里写"先采样，再判断，再输出"：
    采样(ADC) → 判断(比较) → 输出(PWM) → 下一轮采样
每一步的输出都进入下一步。你能做出速度环，不是因为单个步骤"聪明"，
而是因为步骤被串起来了、中间结果被保留了。

LLM：
    生成"让我算一下 12×13" → 这串字进入上下文 → 基于它生成"12×10=120"
    → 120 进入上下文 → 生成"12×3=36" → ... → "156"
它"算"出了结果，是因为中间结果被留在了上下文里。
```
> ⭐ 这个类比的关键点：**中间结果的可见性是能力的来源。**
> 你在 FOC 里也见过类似的东西——积分环节之所以能消除稳态误差，靠的就是"记住"了历史。

**【常见误解】**
1. 「它只是统计续写，所以不可能真的推理」——**这是本讲要打破的第一个直觉**。
   统计续写描述的是**单步计算怎么展开**，不是**整条链能达到什么**
2. 「模型内部一定有个'思考过程'」——讲义的说法克制：能力来自**输出进入后续上下文**，
   而不是假设内部有隐藏的推理模块
3. 「能自我修正 = 一定正确」——修正只是**有了修正的机会**（S5 会补上"需要有效反馈"这个前提）

**【适用边界】**
- 讲义说"可以展开成很长的计算过程"，但**没说这个过程多长、什么时候会失效**
- ⚠️ **缺口：讲义未给出"长链何时崩溃"的边界**。这直接关系到 S5 的"有效反馈"

**【预考题】**
1. 如果模型只是"根据前文猜下一个词"，它为什么能算对你没见过的乘法？
2. "先写一个中间结果，再基于它继续算"——这句话里，关键动作是什么？

**【练习题 + 答案】**
- Q1（识别）：为什么"预测下一个 token"这个描述不能推出能力上限？
  A1：因为它描述的是**单步怎么算**；而多步串联后，模型可以把中间结果留在上下文里，
  在很长的链条上逐步推进甚至自我修正。**单步的简单性推不出链条的能力上限。**
- Q2（应用）：模型写"我先列出方程……"。这句话对后面的计算有什么作用？
  A2：它**变成了上下文的一部分**，后面每一步都基于它。它相当于一个可以回看的草稿纸。
- Q3（迁移）：你在 FOC 里，为什么积分项能消除稳态误差？
  A3：因为它**累积/保留了历史信息**。和"中间结果进入上下文"是同一种机制：
  **把先前的结果存下来，让后面的计算能用到。**
  ⚠️ 差别要说清：FOC 的积分是数学累积；LLM 是文本进入上下文窗口，有长度上限。

**【迁移题】**
有人说"它就是个高级的输入法联想"。你用什么证据反驳？（提示：从"中间结果能否被后续使用"入手）

**【掌握判定】**
- 能说清：能解释"输出成为下一轮输入"如何把静态分布展开成长计算过程
- 能应用：给一个模型自我修正的例子，指出"中间结果"在哪一步被保留
- 能回忆：隔一天能说出"接口简单 ≠ 能力上限"

### S4 思维链：把中间步骤留在上下文里

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§从语言模型到能够行动的 Agent
- 要点：「推理型模型让"先尝试、再检查、再修正"变得更有效。**Chain-of-thought，也就是思维链，
  把中间步骤留在上下文中**。」

**【机制 / 为什么】** 讲义给了定义（中间步骤留在上下文），**没给"为什么留中间步骤有用"的机制**。
⚠️ **缺口：未解释机制。**（S3 已给出"中间结果可见性是能力来源"这一层，可作为可接受的解释，
但**要标注这是从 S3 推出来的，不是讲义直说**。）

**【前置】** S3

**【标准范例】**
```
没有中间步骤：
    问："23 × 17 = ?"        →  直接吐出答案（容易错）

有中间步骤（思维链）：
    问："23 × 17 = ?"
    答："23×17 = 23×(10+7) = 230+161 = 391"
       ↑ 每一步都写出来了 —— 都在上下文里，下一步能看见上一步
```
> ⚠️ 注意：**写出中间步骤不是"给人看的解释"，而是"给模型自己用的草稿"。**
> 这一点很关键，它解释了为什么"让它一步步想"比"让它直接答"更准。

**【常见误解】**
1. 「思维链是模型的内心活动」——不是。它是**当成文本输出来的内容**，是可以看见的
2. 「思维链是事后解释」——恰恰相反，**它是计算过程本身的一部分**（先写，后算）
3. 「只要让它一步步想就一定对」——不保证。**前提是每一步能被检查**（接到 S5）

**【适用边界】**
- 讲义把它归到"推理型模型"的行为，**并非所有模型/所有任务都从思维链同等受益**
- ⚠️ **缺口：讲义未说明什么任务上思维链无效**

**【预考题】**
1. "让它一步步想会更容易对"——这个现象的解释是什么？（他大概率答"因为更清楚"）
2. 思维链里的步骤，是模型"先说给你听"，还是"先说给自己用"？

**【练习题 + 答案】**
- Q1（识别）：什么是思维链？
  A1：**把中间步骤作为文本留在上下文里**，让后续计算能看见并使用它们。
- Q2（应用）：为什么"写出中间步骤"能提高正确率？
  A2：因为中间结果**进入了上下文**，后续每一步都能基于它继续算，而不是一次性地凭一次计算
  给出终局答案。相当于**有了草稿纸**。
- Q3（迁移）：你调试单片机时，为什么习惯把中间变量打出来看？
  A3：因为**把不可见的中间状态变成可见的**，你才能检查、才能定位错误。
  思维链对模型做的是同一件事：**把中间状态外化**。

**【迁移题】**
为什么"要求模型先说思路再给答案"和"要求模型只给答案"效果不同？用"可见性"解释。

**【掌握判定】**
- 能说清：能说出思维链是"中间步骤留在上下文"，并解释它为何有用
- 能应用：能举一个自己领域里"外化中间状态帮助定位问题"的例子并对照
- 能回忆：隔一天能复述定义 + 一句机制

### S5 推理时多花计算（前提是反馈有效）

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§从语言模型到能够行动的 Agent
- 要点：「**test-time scaling** 则是在使用模型时投入更多计算，换取更深入的尝试。
  **多花计算是否值得，要看这些尝试能不能得到有效反馈。**」

⭐ **后半句是本讲给出的第一个"性价比判据"**，比前半句重要。

**【机制 / 为什么】** 讲义给了判据（能否得到有效反馈），**没解释"为什么没有反馈时多花计算无效"**。
⚠️ **缺口：未给机制。** 【外部补充】可用"盲目重试 vs 带校验的重试"来类比——但必须标为外部补充。

**【前置】** S4

**【标准范例】** —— 用他自己调 FOC 的经历，这是最有说服力的
```
情况 A（有有效反馈）：
    电流环波形不对 → 改一个参数 → 看波形 → 还是不对 → 再改
    ✅ 每一步都有"对不对"的信号（示波器 / 串口数据）
    → 多试几次确实能收敛

情况 B（没有有效反馈）：
    波形不对，但你不知道看哪个量、也没有测量手段
    → 只能瞎改参数
    ❌ 试一百次也不会更接近正确答案，只会浪费时间
```
> ⭐ **"多花计算是否值得，取决于有没有反馈"** —— 这在你的调试经验里是常识，
> 在 LLM 上只是换了个对象。

**【常见误解】**
1. 「想得越久越准」——不成立。**没有反馈时，多算只是多花钱**
2. 「贵 = 强」——价格和是否解决了你的问题没有必然关系
3. 「反馈 = 用户的评价」——不全是。讲义在 S18 会展开：**测试、持续集成、独立检查器都是反馈**

**【适用边界】**
- 判据是"**能不能得到有效反馈**"。**什么算"有效"？** 讲义在 S18 给了线索（可执行的检查），
  但本讲**没有给完整清单**。⚠️ **缺口**

**【预考题】**
1. 花更多计算让模型多想一会儿，什么时候是浪费？
2. 你在调试时，什么情况下"多试几次"是有意义的？

**【练习题 + 答案】**
- Q1（识别）：test-time scaling 的收益取决于什么？
  A1：取决于**这些额外尝试能不能得到有效反馈**。没有反馈，多算无效。
- Q2（应用）：下面两种任务，哪个更值得多花计算？
  (a) 让模型解一道有标准答案、能自动验证的数学题
  (b) 让模型评价"这段代码是否优雅"
  A2：**(a)**。因为 (a) **有独立可验证的判据**（答案对不对），模型的多步尝试能被检验；
  (b) 的评价标准模糊、没有可执行的检验，多花计算也难说更接近正确答案。
- Q3（迁移）：你测速度环时，"多试几组 PID 参数"什么时候有意义？
  A3：当你能**读到明确的性能指标**（超调、响应时间、稳态误差）时。若连指标都没定义，
  试参数只是碰运气。

**【迁移题】**
把"多花计算是否值得，要看能否得到有效反馈"改写成一个你能用在日常工作里的判断句。

**【掌握判定】**
- 能说清：能说出判据是"有效反馈"，并解释没有反馈时为何无效
- 能应用：给定两个任务，能判断哪个更值得投入更多推理计算
- 能回忆：隔一天能说出这句判据

### S6 Agent = 模型 + 工具 + 环境（反馈循环）

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§从语言模型到能够行动的 Agent
- 要点：「Agent 又向前走了一步。它**可以调用工具**：读文件、执行命令、查询网页，
  **观察操作结果，再决定下一步做什么**。语言模型与运行它的程序、工具和环境共同形成一个**反馈循环**。」

**【机制 / 为什么】** 材料给了定义和机制（调用→观察→决定）。

**【前置】** S1、S3

**【标准范例】**
```
一次对话：   你问"怎么装 Debian" → 它给你步骤 → 你自己动手
一个 Agent： 你说"帮我装上" → 它执行命令 → 报错 → 它读报错 → 换一条命令
                        → 再报错 → 再排查 → 直到系统能启动
```
> 讲义的原话：「一次对话可以告诉你怎样安装系统，一个 Agent 则可能真的开始安装，
> 遇到报错后继续排查，直到拿到可以验收的结果。」

⚠️ **注意"读文件/执行命令/查询网页"** —— 这三件事都涉及操作系统概念。
他**没学过操作系统**，需要展开：文件 = 存储数据的地方；命令 = 让系统做事的指令；
网页查询 = 通过网络取回信息。**不要假设他知道 shell。**

**【常见误解】**
1. 「Agent = 更聪明的聊天机器人」——差别不在"聪明"，在**能不能动手 + 能不能看到结果**
2. 「Agent 就是插件多」——不是。核心是**反馈循环**（S11 会补上"插件多 ≠ 质量好"）
3. 「它调用工具后就知道结果了」——**必须"观察"**。调用和观察是两步，缺一不可

**【适用边界】**
- 讲义强调重点是**反馈循环**，而不是模型多聪明。但**没有说明这种循环在什么条件下会失效**
- ⚠️ **缺口：讲义未给"Agent 何时不可靠"的清单。** 只在 S11 提了"一个环节误解结果会放大错误"

**【预考题】**
1. "会聊天的 AI" 和 "Agent" 的**关键差别**是什么？
2. 一个 Agent 想修好一个报错，它必须能做到哪两件事？

**【练习题 + 答案】**
- Q1（识别）：构成 Agent 的三部分是什么？
  A1：**语言模型 + 工具（和运行它的程序）+ 环境**，三者形成反馈循环。
- Q2（应用）：一个只会"生成代码但不能运行"的助手，是 Agent 吗？
  A2：**不是完整意义上的 Agent**。它缺少"执行并观察结果"这一环——**没有反馈循环，就只有生成**。
- Q3（迁移）：你在 FOC 里"开环 → 闭环"的演进，和"对话 → Agent"的演进像在哪？
  A3：**都是从"没有反馈"走到"有反馈"**。开环靠预先设定，遇到扰动无法纠正；
  闭环读回输出、与目标比较、再修正。Agent 就是给 LLM 装上了闭环。

**【迁移题】**
用"有没有闭环"这条判据，判断你日常用的几个 AI 工具，哪些更接近 Agent。

**【掌握判定】**
- 能说清：能说出三部分 + 反馈循环，并指出"调用"与"观察"是两步
- 能应用：给定一个工具，能判断它是否形成闭环
- 能回忆：隔一天能说出"Agent 的关键是闭环，不是聪明"

### S7 harness：承载循环的外围系统

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§从语言模型到能够行动的 Agent
- 要点：「**承载这个循环的外围系统，常被称为 harness。**」

⚠️ 讲义只给了一句话定义，**没有展开 harness 的组成**。

**【机制 / 为什么】** ⚠️ **缺口：讲义只给定义，未给机制（harness 里有哪些部件、各自作用）。**

**【前置】** S6

**【标准范例】** —— 用他熟的话说
```
模型本体    =  一个"算下一个 token"的函数
harness     =  围着它搭的一圈装置，负责：
                把工具递到它手上       （工具接口）
                把它想做的动作真的做出来 （执行）
                把结果读回来给它看     （观察）
                决定什么时候停         （终止条件）
```
> 用你的话说：**模型是芯片，harness 是那圈外设和驱动。**
> 芯片本身只会算，是外设让它能"碰到"世界。
> ⚠️ 这个类比是【外部补充】，讲义没有这样说。

**【常见误解】**
1. 「harness = 界面」——不是。界面是给人看的；harness 是**给模型用的**（接工具、执行、回读结果）
2. 「模型自己会调工具」——模型只输出"我要调用 X"这样的文本，**真正执行的是 harness**

**【适用边界】**
- 讲义对 harness 只有一句定义。**不要求掌握其组成**（本讲列为了解即可的边缘点）
- 若学习者深入追问，标【待查证】并说明讲义未展开

**【预考题】**
1. 模型说"我要读取 a.txt"，是谁真的去读了那个文件？
2. 如果 harness 出了 bug，模型会表现成什么样？

**【练习题 + 答案】**
- Q1（识别）：harness 是什么？
  A1：**承载"模型—工具—环境"这个反馈循环的外围系统**。
- Q2（应用）：同一个模型，换一个 harness，能力表现会变吗？为什么？
  A2：**会**。因为模型能"看到什么、操作什么、能否知道自己做对了"由 harness 决定，
  而这些正是 S8 说的能力来源。
- Q3（迁移）：同一个单片机芯片，换一套外设电路，能做的事一样吗？类比说明 harness 的作用。
  A3：不一样。**芯片能力相同，但"能感知什么、能驱动什么"由外围电路（harness）决定。**

**【迁移题】**
为什么说"同一个模型，在不同产品里表现差别很大"是正常的？

**【掌握判定】**
- 能说清：能说出 harness 是"承载循环的外围系统"
- 能应用：能用"芯片 + 外设"的类比解释 harness 的作用
- 能回忆：隔一天能说出这个词和它管什么

### S8 ★ 判断 Agent 能力的三问

**原子性**：只考一件事 ✓（三个问题是**同一个判断框架**，不是三件事）

**【讲义原话】**
- 出处：§从语言模型到能够行动的 Agent
- 要点：「理解 Agent **不能只看模型答题有多聪明**，还要看它
  **能观察什么**、**能操作什么**，以及**操作以后能否知道自己做对了没有**。」

**【机制 / 为什么】** 材料给了框架。**⚠️ 缺口：未解释为什么是这三项**（可从 S6 的反馈循环推出：
观察 = 传感器，操作 = 执行器，自检 = 反馈信号）。

**【前置】** S6

**【标准范例】** —— 用他最熟的控制系统语言重写
```
把 Agent 看成一个控制系统：

    能观察什么   ←→  传感器（我能测到什么？）
    能操作什么   ←→  执行器（我能驱动什么？）
    能否自检     ←→  反馈信号（我怎么知道我做对了？）

⭐ 这三项决定"闭环能不能闭上"。
  缺了第三项，就是开环 —— 无论模型多聪明，都没法自我纠正。
```
> ⭐ 这是把"AI 话题"翻译回他母语领域的最有效一步：
> **Agent 的三问 = 控制系统的三要素。**

**【常见误解】**
1. 「模型越强，Agent 越好用」——三问里**没有一项是"模型多聪明"**
2. 「能操作就够了」——**没有观察和自检，操作再多也是开环**，可能越做越错
3. 「自检 = 模型自己说'我做对了'」——不是。**要有独立于模型的判据**（S18 会给方法）

**【适用边界】**
- 三个问题给的是**评估框架**，不是"合格线"。**每个问题"够不够"取决于具体任务**
- ⚠️ **缺口：讲义未给"什么样的自检算有效"**（→ S18、S19 部分回答）

**【预考题】**
1. 评价一个 Agent 好不好用，你会看什么？
2. 如果只能给 Agent 增加一项能力，你会加哪个？为什么？

**【练习题 + 答案】**
- Q1（识别）：三个问题分别是什么？
  A1：**能观察什么 / 能操作什么 / 操作后能否知道自己做对了没有。**
- Q2（应用）：一个 Agent 能改代码、能跑测试、能读测试输出。三问都满足了吗？
  A2：满足。**改（操作）、跑测试并读输出（观察）、测试通过与否（自检）**，
  三项齐全，是闭环。
- Q3（迁移）：一台只能输出 PWM 但不能读回电流的单片机系统，三问缺哪一项？后果？
  A3：缺"**能观察什么**"（没有电流反馈）→ 无法判断是否达到目标 → **开环，无法自我纠正**。

**【迁移题】**
拿你正在用的一个 AI 编程工具，逐项回答这三问，并指出它最弱的一项是哪个。

**【掌握判定】**
- 能说清：能说出三问，并说明三者构成闭环
- 能应用：给一个具体 Agent，能逐项评估并指出缺口
- 能回忆：隔一天能凭记忆复述三问（顺序可不同）

### S9 先用好，再理解原理

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§先用好，再理解原理
- 要点：「很多人第一次使用 Agent，仍然把它当成一个更会聊天的搜索框。
  **真正有意思的变化，发生在你开始把日常任务交给它的时候。**」
  「过去，这些任务常常意味着翻教程、记配置项、搜索报错，**光是准备开始就让人失去耐心**。
  现在，我们可以**先得到一个能用的环境，再围绕实际遇到的问题理解原理**。」

**【机制 / 为什么】** 材料给了主张和理由（降低起步成本）。

⭐⭐ **这一节和他的先验假设直接冲突**，是本课对他最有价值的一处：
> 他（在某处）说过：「**学 AI 一定要先学软件工程和计算机方面的知识**」。
> 讲义的主张是：**先用好，再理解原理。**
> ⚠️ 按 备课铁律「不直接否定学习者的先验假设」，不能直接否定他 —— **这是他自己的预考素材，让他自己发现冲突。**

**【前置】** 无（独立主张）

**【标准范例】** —— 用他自己学单片机的经历，这是最有力的
```
你第一天学 STM32 的时候，是先读完《Cortex-M4 权威指南》再点灯，
还是先跑通点灯例程、再回头理解时钟树？

答案显然是后者。

现在把"装一个 Debian 系统"换到那个位置：
    过去：翻教程 → 记配置项 → 搜报错 → 光是准备就耗光了耐心
    现在：先让 Agent 装出一个能用的环境 → 再围绕真实问题理解原理
```
> ⭐ 关键不是"AI 让你偷懒"，而是**学习入口的位置变了**：
> 从"我不会所以不能做"，变成"先做出一个能观察、能检查的结果"。

**【常见误解】**
1. 「先用好 = 不用理解原理」——**讲义紧接着说：先用好仍然包含验收**（S10）
2. 「这只是给懒人找借口」——讲义说的是**顺序**：不是不学，是**先有可观察的结果再学**
3. 「所有东西都该先用好再做」——⚠️ **讲义没说这个主张的边界**。若任务**没有可观察的验收标准**，
   "先用好"就会退化成"看起来能跑就行"。⚠️ **缺口**

**【适用边界】**
- 讲义明确保留了一件事：**判断结果的工作还在**（S10）
- ⚠️ **缺口：什么类型的任务不适合"先用好"** —— 讲义未给

**【预考题】**（⭐ 这组题的设计意图是暴露他自己的假设）
1. 要学一个全新的工具，你会先读完文档再用，还是先用起来？
2. 你之前说"学 AI 必须先学软件工程和计算机基础"——如果这个前提不成立，你的学习计划会怎么变？

**【练习题 + 答案】**
- Q1（识别）：讲义主张的学习顺序是什么？
  A1：**先用起来拿到一个能观察、能检查的结果，再围绕实际遇到的问题理解原理。**
- Q2（应用）：「我不会，所以不能做」和「先让工具帮我做出一个能观察的结果」——
  这两句在**学习入口**上有什么不同？
  A2：前者把"先懂"当作起点，**没有懂就无法开始**；后者把"能观察的结果"当作起点，
  **有了结果就有了提问的对象**。后者把学习起点从"懂"移到了"看到"。
- Q3（迁移）：你学 FOC 时，"先跑通开环再理解原理"和这条主张一致吗？
  A3：一致。**先让电机转起来（可观察），再回头理解坐标变换和环路（原理）。**

**【迁移题】**
举一个你**曾经因为"想先完全搞懂"而迟迟没开始**的事，用这条主张重新安排一次顺序。

**【掌握判定】**
- 能说清：能说出"先用好再理解原理"的含义，并说出它为什么有效
- 能应用：能判断一个具体任务适不适合这条策略
- 能回忆：隔一天能复述主张

### S10 "先用好"仍然包含验收

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§先用好，再理解原理
- 要点：「但先用好**仍然包含验收**：系统到底能不能启动，快捷键是否符合预期，
  数据是否保存正确，**都需要证据**。学习曲线被改写了，**判断结果的工作还在**。」

**【机制 / 为什么】** 材料给了理由（需要证据）。这一节是 S9 的**配套约束**，缺了它 S9 会失真。

**【前置】** S9

**【标准范例】**
```
"我先用起来" 的错误版本：
    Agent 说装好了 → 我信了 → 之后发现问题

"我先用起来" 的正确版本：
    Agent 说装好了 → 我重启一次看它能不能起来（证据）
                  → 我按几个快捷键看是否符合预期（证据）
                  → 我存一个文件再读回来（证据）
```
> 用你的话：**这就是"先点灯，但必须真的看到灯亮"。**
> 不是"例程编译通过就算成功"。

**【常见误解】**
1. 「Agent 说完成了 = 完成了」——**必须自己拿到证据**
2. 「验收 = 跑一遍看看」——要看的是**具体断言**：能不能启动、是否符合预期、数据是否正确
3. 「先用好就不用验收了」——**恰恰相反，"先用好"的前提就是有验收**

**【适用边界】**
- 讲义只举了三个验收维度（能否启动 / 是否符合预期 / 数据是否正确），**不是完整清单**

**【预考题】**
1. 让 Agent 装好系统后，你怎么确认它真的可用？
2. "它说装好了"和"我知道装好了"，差别在哪？

**【练习题 + 答案】**
- Q1（识别）："先用好"为什么仍需要验收？
  A1：因为**需要证据**才能知道结果是否真的可用；讲义原文：「判断结果的工作还在」。
- Q2（应用）：Agent 改完你的代码，给出三种确认方式，哪种最像"验收"？
  (a) 读它的修改说明 (b) 编译通过 (c) 跑一遍测试并看到具体断言通过
  A2：**(c)**。它给出**可核对的证据**（哪些断言、是否通过），而 (a) 是自述、(b) 只证明语法正确。
- Q3（迁移）：你发 B站视频前怎么验收？和这一条有什么关系？
  A3：导出后自己完整看一遍/听一遍音频是否正常 —— 同样"需要证据"，而不是"渲染完成就算好了"。

**【迁移题】**
把你的某件日常工作，拆成"先用好"+"必须拿到什么证据"两列。

**【掌握判定】**
- 能说清：能说出"先用好"为什么必须配验收
- 能应用：能为一个任务列出具体的验收证据
- 能回忆：隔一天能复述"判断结果的工作还在"

### S11 工具组合 = 分解 + 组合，但错误会沿链放大

**原子性**：只考一件事 ✓（"能组合"与"会放大错误"是同一件事的两面，不拆）

**【讲义原话】**
- 出处：§工具可以组合，成功经验可以复用
- 要点：「网页、视频、论文可以作为**信息源**；检索、分类、总结可以作为**处理过程**；
  文档、提醒、文件上传可以作为**输出动作**。只要接口接得起来，它们就不再是孤立的功能。
  这也是软件工程很早就有的思想：**分解问题，再通过组合获得比单个部件更大的能力**。」
  「当然，**插件数量并不等于系统质量**。一个环节误解了结果，下一个环节可能继续**放大错误**。」

**【机制 / 为什么】**
- 材料给了"组合带来能力"和"错误会放大"两个断言
- ⚠️ **缺口：未给"为什么接口接得起来就能组合"的机制**。
  【外部补充】这正是他**已经学过**的模块化/耦合语言（见 知识地图 P0–P7）——
  **接口 = 契约**。★ 这是本讲与他已有知识的第一处正面衔接。

**【前置】** 无（但强烈建议在学 P0–P7 之后学本点）

**【标准范例】** —— 用他已经建立的语言
```
你在单片机里做的事：

    ADC 模块   →  输出一个数    →  滤波模块   →  输出一个数  →  PID 模块

每个模块只有"输入—输出契约"，内部怎么实现的对方不需要知道。
所以你能换一个滤波算法，而不动 PID。

讲义说的"工具组合"是同一件事：
    网页/视频/论文  →  检索/分类/总结  →  文档/提醒/上传
    （信息源）         （处理过程）        （输出动作）

⚠️ 但链变长以后：
    第一级把"A"误解成"B" → 后面每一级都在错误的输入上继续算
    → 错误被逐级放大，最后的结果看不出错在哪
```
> ⭐ **"一个环节误解结果，下一个环节继续放大错误"** ——
> 这就是你已经学过的「**依赖**」带来的「**改动放大 / 认知负荷**」的另一种面孔。

**【常见误解】**
1. 「工具越多能力越强」——**数量与质量无关**；链越长，失败的传播路径越多
2. 「组合 = 把工具列出来」——真正的组合前提是**接口说得清**（输入什么、输出什么、失败怎么办）
3. 「组合是 AI 时代的新思想」——讲义明确说这是**软件工程很早就有的思想**

**【适用边界】**
- ⚠️ **缺口：讲义未给"怎么判断一条链可靠"的方法**。S18/S19 给了一部分（独立检查、可观测性）

**【预考题】**
1. 把三个 AI 工具串起来用，能力一定比用一个强吗？
2. 一条流水线里，第一个环节出错了，你多久能发现？

**【练习题 + 答案】**
- Q1（识别）：讲义说"组合"背后的软件工程思想是什么？
  A1：**分解问题，再通过组合获得比单个部件更大的能力。**
- Q2（应用）：为什么"插件数量不等于系统质量"？
  A2：因为**每个环节都可能误解上一个环节的结果**，并把错误继续传下去。
  链越长，错误被放大的机会越多。质量取决于**接口是否可靠**，而不是数量。
- Q3（迁移）：你在 FOC 里把电流环、速度环串起来时，如果编码器读数错了，最后会怎样？
  A3：速度环基于错误的速度计算 → 输出错误电流指令 → 电流环忠实地执行这个错误指令
  → **每一级都没"出错"，但整体结果错**。这正是讲义说的"继续放大错误"。

**【迁移题】**
找出你目前使用的某个"多工具串联"流程，指出最容易误解上游结果的那一环。

**【掌握判定】**
- 能说清：能说出组合的价值和风险各是什么，并知道这是软件工程的老思想
- 能应用：能指出一条链上最容易出错/放大错误的环节
- 能回忆：隔一天能说出"分解 + 组合"与"错误会放大"这两句

### S12 ★★ Intent / Spec / Impl 三层与缺口

**原子性**：只考一件事 ✓（三层是一个模型，不拆）

**【讲义原话】**
- 出处：§Intent、Spec 与 Impl 之间的缺口
- 要点：
  - 「**Intent 是你真正想达成的目标。** 它往往连提出者自己也没有完全想清楚」
  - 「**Spec 是把意图具体化以后，能够描述行为与约束的规格。**」
  - 「**Impl 则是程序实际执行的计算。** 计算机必须在每一个执行分支上做出确定的动作，
    不能留一句'到时候看着办'。」
  - 「**从 Intent 到 Spec，需要做产品判断；从 Spec 到 Impl，需要做设计与实现判断。**
    同一个意图允许许多规格，同一个规格又允许许多实现。」

⭐⭐ **本讲主线**。而且它和他已学的「抽象 / 接口」直接相通。

**【机制 / 为什么】** 材料给了三层定义、两种判断、以及"一对多"关系。

**【前置】** 建议先有 P0–P7（模块/接口）基础

**【标准范例】** —— 用他自己的项目
```
Intent （他真正想要的）：
    "做一个速度环闭环的 FOC 控制"

Spec （可以被检验的规格）：
    空载下，给定 1000 rpm 目标，稳态误差 < 1%，超调 < 5%，响应时间 < 0.5s

Impl （实际执行的计算）：
    具体的 Clarke/Park 变换、PID 参数、采样频率、中断优先级……

⭐ 注意"同一个意图允许许多规格"：
    Intent 不变，但 Spec 可以改成"超调 < 2%"或"响应 < 0.2s"
⭐ "同一个规格允许许多实现"：
    Spec 不变，但你可以用 SMO 或 EKF 做无感，也可以用霍尔
    —— 两者都能满足同一个 Spec
```
> ⚠️ **关键**：Spec 里的每一项都是**可以被检验的**。
> "做一个好用的工具" 不是 Spec，因为**没人能检验它达成没有**。

**【常见误解】**
1. 「Intent 就是需求文档」——不是。Intent 常常**连提出者自己都没想清楚**
2. 「Spec 就是详细设计」——不是。Spec 说"要满足什么"，不说"怎么实现"
3. 「通过了测试 = 满足了 Intent」——讲义明确否定：
   「即使程序通过了现有测试，也只能说明它满足了这些检查，
   **不能自动推出规格忠实表达了真实意图**」
4. ⚠️ 「三层是流水线，走一遍就完」——**缺口**：讲义未说清三层是**迭代**还是**线性**（S14/S15 有线索）

**【适用边界】**
- 讲义强调缺口**不会因为 AI 变强而消失**：「AI 可以加速实现，这些问题却不会随着代码自动生成而自动消失」
- ⚠️ **缺口：讲义未给"如何把 Intent 变成 Spec"的操作步骤**（S14 给了部分线索）

**【预考题】**
1. "帮我做一个好用的工具" —— 这是 Intent 还是 Spec？为什么？
2. 程序通过了所有测试，是否说明它做到了用户真正想要的？

**【练习题 + 答案】**
- Q1（识别）：三层分别是什么？两层边界上各需要什么判断？
  A1：**Intent（真正想达成的目标）/ Spec（可描述行为与约束的规格）/ Impl（实际执行的计算）**。
  Intent→Spec 需要**产品判断**；Spec→Impl 需要**设计与实现判断**。
- Q2（应用）：判断下列各属于哪一层：
  (a) "希望能自动处理我的邮件" (b) "收到新邮件后，按发件人归档，草稿要符合我的语气"
  (c) "调用 IMAP 接口拉取未读邮件并写入 SQLite"
  A2：(a) **Intent**（没有可检验标准）(b) **Spec**（描述了行为与约束）(c) **Impl**（具体执行的计算）
- Q3（迁移）：你在 FOC 项目里，"让电机转得稳"属于哪一层？要补什么才能变成 Spec？
  A3：**Intent**。要补**可检验的量**：目标转速、稳态误差、超调、响应时间、负载条件。
- Q4（★ 关键）：为什么"同一个 Spec 允许许多实现"这件事对工程很重要？
  A4：因为它意味着**实现可以替换而规格不变**。这就是模块化的价值：
  接口（Spec）稳定，内部（Impl）可换。**他已在 P0–P7 学过这一层。**

**【迁移题】**
给你手上的一个真实任务，写出它的 Intent，再写出至少两条**可检验**的 Spec。

**【掌握判定】**
- 能说清：能解释三层各是什么、两种判断的分界
- 能应用：给若干句子，能正确归层；能把一个 Intent 改写成可检验的 Spec
- 能回忆：隔一天能说出三层名称 + 两种判断 + "一对多"

### S13 同一意图多规格、同一规格多实现

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§Intent、Spec 与 Impl 之间的缺口
- 要点：「同一个意图允许许多规格，同一个规格又允许许多实现。
  **每一步看似合理，最终仍然可能离用户想要的东西很远。**」

**【机制 / 为什么】** 材料给了"一对多"和"误差可累积"。

**【前置】** S12

**【标准范例】**
```
Intent: "让这个网页打开得快一点"

Spec 版本 A：首屏 1 秒内可见            → Impl：懒加载
Spec 版本 B：总加载体积 < 500KB         → Impl：图片压缩
Spec 版本 C：首屏 1 秒内可见 且 体积 < 500KB → 两个都要

⭐ 三条 Spec 出自同一个 Intent，都是"合理"的
⭐ 但如果用户真正在意的是"手机上打开快"，
   那么 B（压体积）可能比 A 更对 —— **每一步都合理，合起来却可能跑偏**
```

**【常见误解】**
1. 「Spec 只有一种正确写法」——不，**同一个 Intent 允许许多 Spec**
2. 「只要每步都对，结果就对」——讲义明确说：**每一步看似合理，最终仍可能离目标很远**
3. 「所以应该一次把 Spec 写全」——⚠️ 讲义没这么说（S14/S15 会说：要小步验证）

**【适用边界】**
- ⚠️ **缺口：讲义未给"如何在多个 Spec 中选出对的那个"的方法**

**【预考题】**
1. 同一个意图，能不能写出两种都合理的规格？举例。
2. 每一步都做对了，最终会不会还是错的？

**【练习题 + 答案】**
- Q1（识别）："同一个意图允许许多规格"——这句话的直接后果是什么？
  A1：**规格的选择本身是一个需要判断的决定**，不能从意图唯一推出。
  所以 Intent→Spec 需要**产品判断**。
- Q2（应用）：写同一个 Intent 的两条不同的 Spec。
  例 Intent："让配置文件更好维护"
  A2：Spec A：**配置文件不超过 50 行**；Spec B：**改一个参数只需改一处**。
  两者都合理，关心的点不同（前者是规模，后者是修改局部性）。
- Q3（迁移）：你在两台不同的板子上实现同一个速度环 Spec，Impl 会一样吗？
  A3：**不一样**（时钟频率、外设不同），但 Spec 相同。这正是"同一规格多实现"。

**【迁移题】**
找一个"看起来完成了但其实跑偏了"的真实经历，指出是 Intent→Spec 的偏差还是 Spec→Impl 的偏差。

**【掌握判定】**
- 能说清：能解释"一对多"为什么让规格选择成为判断问题
- 能应用：能为同一 Intent 写出两条合理的 Spec
- 能回忆：隔一天能说出"每一步看似合理，仍可能离目标很远"

### S14 模型靠猜填补空白（猜错代价分级）

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§Intent、Spec 与 Impl 之间的缺口
- 要点：「模型怎样填补这些空白？**很大程度上靠猜。**
  总不能每选一种颜色、每命名一个变量都询问用户；
  **但在架构、数据表示和验收标准上猜错，代价就大得多。**
  我们要研究的，是**哪些决定可以先做再验证，哪些决定值得先讨论或做一个小实验**。」

⭐ 这是本讲给出的**第二个操作性判据**（第一个是 S5 的"有效反馈"）。

**【机制 / 为什么】** 材料给了机制（靠猜）和代价分级（颜色/命名 < 架构/数据表示/验收标准）。

**【前置】** S12

**【标准范例】** —— 用他自己的调参经验
```
猜错的代价，用你调 FOC 的经验看最清楚：

    低代价的猜测：函数取什么名字、注释怎么写
        → 猜错了随手改，不牵连别人            ← 相当于"改一个增益"

    高代价的猜测：整个控制结构怎么划分（几个环、谁调谁）
        → 猜错了要重写一遍                    ← 相当于"换了控制架构"

⭐ 讲义的原话就是这条经验的一般化：
   「哪些决定可以先做再验证，哪些决定值得先讨论或做一个小实验」
```
> ⚠️ 「数据表示」需要展开：**数据在程序里用什么形式存放**。
> 用他的语言：就像**定点还是浮点、用 Q15 还是 float** —— 选错了，后面全要改。

**【常见误解】**
1. 「所有细节都该先问清楚」——讲义明确否定了（「总不能每选一种颜色、每命名一个变量都询问用户」）
2. 「所有决定都可以先做」——也不行，**架构 / 数据表示 / 验收标准的猜错代价大**
3. 「代价大小是固定的」——不，**取决于"改它要动多少地方"**（这正是 S15 的局部性）

**【适用边界】**
- ⚠️ **缺口：讲义给了三类"代价大"的决定（架构、数据表示、验收标准），但没给完整清单**

**【预考题】**
1. 让 AI 从零做一个项目，它会有很多地方不问你直接决定。哪些决定你不希望它自己定？
2. 为什么“颜色”猜错没关系，“数据表示”猜错就有关系？
3. 【讲义原话·课堂提问】「我们要研究的，是**哪些决定可以先做再验证，
   哪些决定值得先讨论或做一个小实验**。」——你怎么分这两类？

**【练习题 + 答案】**
- Q1（识别）：模型如何填补 Intent/Spec 里的空白？哪些地方的猜测代价大？
  A1：**主要靠猜**。代价大的是**架构、数据表示、验收标准**。
- Q2（应用）：下列哪些决定值得先讨论/先做小实验？
  (a) 变量命名 (b) 用链表还是数组存数据 (c) 按钮颜色 (d) 怎么判断"做完了"
  A2：**(b) 和 (d)**。数据表示和验收标准都属于"代价大"的一类；
  命名和颜色属于"先做再验证"。
- Q3（迁移）：你在选 PID 的实现方式（定点/浮点）时，会先讨论还是先做？
  A3：**先讨论或先做小实验**。因为它属于"数据表示"，选错后改动面很大。

**【迁移题】**
列出你当前项目里"猜错代价最大"的三个决定。

**【掌握判定】**
- 能说清：能说出模型靠猜，并指出哪三类决定代价大

### S16 硬编码 vs 可复用模板：演示通过 ≠ 需求实现

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§二维码 Excel 为什么掉进了泥潭
- 要点：「**硬编码尤其说明问题。用户需要的是一个对不同输入都成立的计算过程，
  模型却可能交出一个只让当前输入看起来正确的结果。演示成功和需求实现之间，
  隔着一个很大的差别。**」

**【机制 / 为什么】** 材料给了现象和区分（演示 vs 需求），**没给"怎么发现硬编码"的方法**。
⚠️ **缺口。** 【外部补充】可用"换一组输入试一次"作为检查手段——**必须标为外部补充**。

**【前置】** S12（Spec 要可检验）、S15（局部性）

**【标准范例】** —— 用他的单片机经验，一句话就能落地
```
硬编码的样子（你一定见过）：
    #define TARGET_RPM  1000          ← 目标转速写死了
    ...
    if (rpm > 1000) { ... }           ← 又在另一处写了一遍

    "只让当前输入看起来正确"：
    把目标改成 1500，程序就行为异常 —— 因为有个地方还写着 1000

可复用的样子：
    int target_rpm;                   ← 目标是个变量
    void set_target(int rpm) { ... }  ← 只在一处管理它

⭐ 验证手法：**换一组输入再试一次**。
   如果只有原来的输入能跑通 → 是硬编码
```

**【常见误解】**
1. 「能跑通就是完成了」——讲义明确否定：**演示成功和需求实现隔着一个很大的差别**
2. 「硬编码只是风格问题」——不是。它让"对不同输入都成立"这一**需求本身**没被满足
3. 「AI 写了 6 小时所以应该不错」——讲义记录的一次尝试**花了 6 小时仍交出了硬编码版本**

**【适用边界】**
- ⚠️ **缺口：讲义未给"如何系统性地发现硬编码"的方法**
- 【外部补充】最小检查：**换输入**。但要判断"换多少组、换多极端"仍需经验

**【预考题】**
1. AI 交给你一个能运行的程序，你怎么判断它是真的实现了需求，还是只是“让当前输入看起来正确”？
2. 硬编码最本质的坏处是什么？（不是“丑”）
3. 【讲义原话·课堂提问】「**一台严格管控文件流出的机器，如果仍然能够显示画面，
   信息真的“只进不出”吗？**」——这个问题的有趣之处是“重新认识现有部件”，
   它和硬编码有什么关系？

**【练习题 + 答案】**
- Q1（识别）：为什么讲义说"演示成功和需求实现之间隔着一个很大的差别"？
  A1：因为**需求要求"对不同输入都成立"**，而演示只需要**当前那一个输入看起来对**。
  只满足当前输入的程序，没有实现需求。
- Q2（应用）：给你一段 AI 生成的代码，你只允许做一个测试来判断是否硬编码，做什么？
  A2：**换一组（尤其是更极端/不同规模的）输入再跑一次**。如果失败或行为异常，
  说明关键值被写死在计算结构里。
- Q3（迁移）：你写的速度环，如果把电机换成另一个参数的型号，要改几处？
  A3：如果电流环参数、限幅、编码器分辨率散落在多个文件 → 要改多处（硬编码/耦合重）；
  如果有统一的配置入口 → 改一处。（与 S15 的局部性一致）

**【迁移题】**
写一条"验收清单"，用来判断 AI 给的实现是"演示"还是"实现"。

**【掌握判定】**

- 能回忆：隔一天能说出这个区分

### S18 拆解 / 验证 / 迭代：缩短"做决定"与"知道对不对"的距离

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§让大工程获得及时的反馈
- 要点：「**拆解、验证和迭代因此仍然有用。**
  拆解让一个大问题变成能看清因果的小问题；
  测试与持续集成让已发现的错误不再轻易回流；
  小步修改让新的失败尽早出现，便于定位和回退。
  这些动作共同**缩短了'做了一个决定'与'知道决定是否正确'之间的距离**。」

⭐ 讲义还给了二维码 Excel 的**正确拆法**（这是本点的标准范例）：

「可以先拿一个短字符串，完成单帧二维码，并让独立解码器真实读回原文。这一步验证最核心的计算。
随后扩展到不同输入、Base64 编码和分片，再验证多帧的顺序与拼接，最后处理刷新、兼容性和性能。
每一步都留下可执行的检查；**每一步都在消除一种具体的不确定性**，
而不是等整个文件写完才看它能不能用。」

**【机制 / 为什么】** ✅ 材料给了机制（缩短决定与知道之间的距离），而且给了完整范例。

**【前置】** S17

**【标准范例】** —— 讲义原文，直接用
```
❌ 一次性做法：把需求全丢给 AI，等它写完一个 Excel，再看能不能用
   → 反馈来得极晚，且出问题时不知道错在哪

✅ 讲义给的拆法：
   第1步  短字符串 → 单帧二维码 → **独立解码器真实读回原文**
          ★ 一次只验证"最核心的计算"这一件事
   第2步  扩展到不同输入、Base64 编码
   第3步  分片，验证多帧的**顺序与拼接**
   第4步  刷新、兼容性、性能

⭐ 每一步都留下**可执行的检查**
```
> 用你的话：**这和你在 FOC 里"先开环跑通，再加电流环，再加速度环"是同一种做法。**
> 你不会一次性写完所有环路再上电 —— 因为那样出问题时不知道是哪一环。

**【常见误解】**
1. 「拆解就是把任务列成清单」——不是。拆解的标准是**每一步能独立验证**
2. 「小步 = 慢」——恰恰相反：**小步让失败尽早暴露**，避免走到底才发现方向错
3. 「测试是额外成本」——讲义把"独立检查器、测试"列为**新工程工作的核心**（S19）

**【适用边界】**
- 讲义给的是"能验证的任务"的拆法。⚠️ **缺口：对"难以验证"的任务怎么办**，未给方法

**【预考题】**
1. 让 AI 做一个复杂工具，你会一次性给完整需求，还是分步？为什么？
2. 你学 FOC 时，是一次性把三个环都调好，还是一环一环来？这个习惯说明什么？

**【练习题 + 答案】**
- Q1（识别）：拆解、验证、迭代各自的作用是什么？
  A1：**拆解**——把大问题变成能看清因果的小问题；
  **测试与持续集成**——让已发现的错误不再回流；
  **小步修改**——让新的失败尽早出现，便于定位与回退。
  三者共同**缩短"做决定"与"知道对不对"之间的距离**。
- Q2（应用）：把"做一个自动整理邮件的工具"拆成 3 步，每步给出一个可执行的检查。
  A2（示例）：①只读一封邮件并正确解析出标题/发件人 → 检查：打印结果与原文一致；
  ②按发件人归档 5 封邮件 → 检查：文件确实出现在预期位置；
  ③生成一封草稿 → 检查：语气/事实与原邮件一致（需人工读一遍）。
- Q3（迁移）：你在 FOC 项目里"先开环 → 再加电流环 → 再加速度环"，
  每一步的"可执行检查"分别是什么？
  A3：开环：电机是否按预期转动（看转速/方向）；
  电流环：给定 Id/Iq 指令，实测电流是否跟随（看采样值）；
  速度环：给定目标转速，稳态误差与超调是否达标（看曲线）。

**【迁移题】**
把一个你正打算"一次性做完"的任务，改写成 3-4 个"每步都有可执行检查"的步骤。

### S19 生产变便宜后，瓶颈转移到"判断"

**原子性**：只考一件事 ✓

**【讲义原话】**

- 要点：「假设生成能力提高一千倍，**即使只有百分之一的垃圾，垃圾的绝对量也达到旧时代全部产量的十倍**。」

**【标准范例】** —— 讲义的一千倍算式，用他自己的场景重算一遍
```
假设你现在的产出是 1 份/天，其中 1% 是垃圾 → 垃圾 0.01 份/天

生成能力 ×1000：
    产出 1000 份/天，仍有 1% 是垃圾 → 垃圾 10 份/天
    ← 10 份垃圾 = 旧时代全部产量（1 份）的 10 倍
```
> ⭐ 讲义原话：「**错误率很小和维护负担很小，并不是一回事。**」
> 用你的话：**不良率没变，但绝对不良数爆了。**
> —— 这和你熟悉的**通信误码率**是一个道理：误码率不变，速率翻倍，单位时间的错码数就翻倍。

**【常见误解】**
1. 「错误率低就没问题」——讲义明确：**错误率小 ≠ 维护负担小**
2. 「产出快了，人就轻松了」——讲义说：**逐行阅读难以同样加速**，判断成了瓶颈
3. 「那就不看，全交给 AI」——讲义的主张相反：**让判断跟上生产**，把注意力放在最值得判断的地方

**【适用边界】**
- 一千倍是**假设**（讲义原文："这是一个假设计算"），**不是事实预测**
- ⚠️ **缺口：讲义未给"如何让判断跟上生产"的完整方法来**（给了五个方向：好规格、独立检查器、
  测试、可观测性、清晰接口）

**【预考题】**
1. 如果 AI 生成代码快 1000 倍，但错误率不变，会出什么问题？
2. 生产变快之后，什么会变成新的瓶颈？

**【练习题 + 答案】**
- Q1（识别）：讲义用一千倍算式想说明什么？
  A1：**错误率很小和维护负担很小，并不是一回事**——生产量剧增会放大**垃圾的绝对量**。
- Q2（应用）：为什么"逐行阅读"会成为瓶颈？
  A2：因为**生成可以越来越快，人的逐行阅读难以同样加速**。
  判断的速度跟不上生产的速度，判断就成了瓶颈。
- Q3（迁移）：通信里速率提高 1000 倍、误码率不变，会发生什么？和这里像在哪？
  A3：单位时间错码数增加 1000 倍。**同样的道理**：比率不变，绝对量随总量放大。
- Q4（★）：讲义说新工程工作依赖哪五样东西？
  A4：**好的规格、独立检查器、测试、可观测性、清晰接口。**
  共同目的：**让判断也能跟上生产。**

**【迁移题】**
如果你每天能用 AI 产出 10 倍的东西，你的"判断"环节打算怎么改造？

**【掌握判定】**
- 能说清：能说出"错误率小 ≠ 维护负担小"，并解释瓶颈为何转移到判断
- 能应用：能复述五个方向，并说明它们共同服务于"让判断跟上生产"
- 能回忆：隔一天能说出一千倍算式的结论
