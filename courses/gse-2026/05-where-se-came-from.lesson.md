### W1 能力边界不断移动

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§不断移动的能力边界
- 要点：
  - 「课堂还讨论了 Noam Brown 关于工作和 taste 的访谈。
    ⭐ **Taste 可以理解为"对接下来该做什么的直觉"**：面对许多可能的方向，
    哪一个问题值得问，哪一个实验值得做。**如果 AI 能完成一个人工作中的 90%，
    这个人的注意力自然会转向剩下的 10%。但剩下的部分并不因此成为永久属于人的领地。**」
  - ⭐⭐ 「他预测，再过一两代模型，模型在这种判断上也会超过自己。
    **这个预测提醒我们，不要把今天模型的短板当作人类的永恒优势。**」

**【机制 / 为什么】** 材料给了定义（taste）和一个明确的提醒。

**【前置】** L1 S19（生产变便宜后瓶颈转移）

**【标准范例】** —— 用他自己的领域
```
⭐ "把今天的短板当永恒优势"的例子：

    "AI 调不出电机的味道"        ← 可能是今天的短板
    "AI 不懂硬件手感"            ← 也可能是今天的短板
    "AI 不能做真正有创造性的工作"  ← 每一次说这句话，边界都往后退了一格

⭐ 讲义的态度不是"人会输"，而是：
    **不要把"现在做不到"当成"永远做不到"**，
    也不要把"现在做得到"当成"永远安全"
```
> ⚠️ 讲义明确：**这是一个预测（Noam Brown 的），不是已经发生的事实**。
> 教学时必须保留"预测"这个身份。

**【常见误解】**
1. 「AI 做不了 X，所以 X 永远是人的优势」——⚠️ 讲义明确提醒不要这么想
2. 「所以人没用了」——讲义**没有**说这个。它说的是**边界在移动**，需要持续重新判断
3. 「taste 是审美」——讲义的定义更具体：**对"接下来该做什么"的直觉**

**【适用边界】**
- ⚠️ Noam Brown 的访谈内容与预测**未核对原文** → `【待查证·引注未核】`
- ⚠️ 讲义自己也把它标为**预测**

**【预考题】**
1. 你觉得有哪些工作"AI 永远做不了"？说出理由。
2. "taste"在你的领域里指什么？

**【练习题 + 答案】**
- Q1（识别）：讲义怎么定义 taste？
  A1：**"对接下来该做什么的直觉"**——面对许多可能的方向，
  **哪一个问题值得问，哪一个实验值得做**。
- Q2（★ 应用）：如果 AI 能完成一个人工作中的 90%，会发生什么？
  A2：**这个人的注意力会自然转向剩下的 10%**；
  但 ⚠️ **剩下的部分并不因此成为永久属于人的领地**。
- Q3（迁移）：你说过哪些"AI 做不了"的话？现在回头看，哪些已经变了？
  A3（开放）。

**【迁移题】**
写下三条你认为"AI 短期内做不了"的工作，各附一句"如果它做得到了，会怎样"。

**【掌握判定】**
- 能说清：能说出 taste 的定义和那条提醒
- 能应用：能识别"把今天短板当永恒优势"的推理
- 能回忆：隔一天能复述"不要把今天模型的短板当作人类的永恒优势"

### W2 ★ 能否获得可靠反馈 + 独立验证

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§不断移动的能力边界
- 要点：
  - ⭐ 【课堂提问】「一个相关的问题是：**某种能力能不能获得可靠的反馈？**
    写程序至少可以**运行测试**，数学证明可以**检查推导**；
    **选择研究方向、澄清需求、管理长期记忆，看起来更难评价。**」
  - ⭐⭐ 「但'**难以评价**'也未必意味着**永远无法训练**。
    研究方向可以通过**后续实验**检验，需求澄清可以通过**最终交付是否符合用户意图**来评价。
    **反馈可能更晚、更贵、更有噪声，这些都是工程问题。**」
  - ⭐ 「更强的模型又能参与寻找新领域、构建训练环境和验证器、调整数据分布……
    **递归自我改进，也就是 RSI，关心的正是能力生产过程本身能否被持续改进。**
    ⭐⭐ **这个循环能不能转起来，要看每一轮是否带来经过独立验证的净收益。
    模型给自己打了更高的分，并不等于能力真的提高了。**」

⭐⭐ **"难评价" ≠ "无法训练"** 是本讲一个重要判断；**"独立验证"** 是它的配套要求。

**【机制 / 为什么】** 材料给了机制（反馈可以更晚更贵更有噪声）和一条硬要求（独立验证）。

**【前置】** L1 S5（有效反馈）

**【标准范例】** —— 用他的经验
```
⭐ "反馈更晚、更贵、更有噪声，但仍是工程问题"——

    在单片机里，有些指标是**立刻可测的**：
      波形对不对、转速达没达到
    有些是**很久才知道的**：
      这个电路在高温高湿下能不能扛三年
      这个参数在带载后还稳不稳

    ⚠️ 你不会因为"三年后才知道"就说"没法验证"
       → 你会设计**加速老化试验**、**工况覆盖**、**独立测量**
    ⭐ 这就是讲义说的：**反馈更晚更贵更有噪声，但仍是工程问题**
```

**【常见误解】**
1. 「难评价 = 无法训练」——❌ 讲义明确否定
2. 「模型说自己变强了就是变强了」——❌ **"模型给自己打了更高的分，并不等于能力真的提高了"**
3. 「有反馈就够」——还要**独立**验证

**【适用边界】**
- ⚠️ RSI（递归自我改进）是**设想**，讲义用"能不能转起来"的口气讨论 → **不是已实现的事实**

**【预考题】** ⭐ 用课堂原话
1. 【讲义原话·课堂提问】「某种能力能不能获得可靠的反馈？」
2. 模型给自己打的分，能作为"能力提高"的证据吗？

**【练习题 + 答案】**
- Q1（识别）：讲义举了哪些"容易评价"和"难评价"的能力？
  A1：**容易评价**：写程序（可以运行测试）、数学证明（可以检查推导）；
  **难评价**：选择研究方向、澄清需求、管理长期记忆。
- Q2（★ 关键）："难评价"是否意味着不能训练？为什么？
  A2：**不意味着**。研究方向可以通过**后续实验**检验，
  需求澄清可以通过**最终交付是否符合用户意图**来评价。
  ⭐ **反馈可能更晚、更贵、更有噪声——这些都是工程问题**（可以被设计）。
- Q3（关键）：RSI 的循环能不能转起来，取决于什么？
  A3：**要看每一轮是否带来经过"独立验证"的净收益。**
  ⚠️ **模型给自己打了更高的分，并不等于能力真的提高了。**

**【迁移题】**
找一个你"觉得难验证"的事情，设计一个"更晚、更贵、但可行"的验证方式。

**【掌握判定】**
- 能说清：能说出"难评价≠无法训练"和独立验证的要求
- 能应用：能为一件难评价的事设计验证方式
- 能回忆：隔一天能复述"模型给自己打了更高的分，并不等于能力真的提高了"

### W3 从空项目出发：AI 补全了什么

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§从空项目出发，AI 补全了什么
- 要点：
  - 「面对一句'我想要一个办公助手'，今天可以**先生成一个最小可行产品，也就是 MVP**，
    让人实际使用，再继续修正。⭐ **原型把抽象的想象变成了可以点击、可以批评的对象。**」
  - ⭐⭐ 「这个过程之所以快，是因为**模型替我们补齐了大量没有说出口的决定**：
    界面如何组织，数据如何保存，操作失败时如何反馈。
    ⚠️ **第一次演示很顺利，只能说明这些决定在演示场景下能够组成一个可运行的系统。
    它们是否符合用户真正的需要，还要继续检验。**」
  - 「在大语言模型出现以前，**补齐这些细节需要昂贵的人力**。接到任务就立即安排所有程序员写代码，
    往往会让**不同的人沿着不同的理解前进**。等代码拼在一起，
    大家才发现'**同一个需求'在每个人脑海里根本不是同一件事**。」

**【机制 / 为什么】** ✅ 材料给了机制（补齐未说出口的决定）和一条明确限定。

**【前置】** L1 S14（模型靠猜填补空白）、L2 T4（写清"完成"）

**【标准范例】** —— 直接复用他的场景
```
你说"帮我做一个速度环"，AI 生成了一个能跑的版本：

⭐ 它替你补齐的"没说出口的决定"：
    目标转速默认多少？    → 可能填了 1000
    超调要求？            → 没提，它不设
    采样频率？            → 可能填了 1kHz（但你的硬件是 10kHz）
    死区要不要补？        → 它不知道有死区
    上位机怎么显示？      → 它自己定了一个

⚠️ 讲义的关键限定：
   "**第一次演示很顺利，只能说明这些决定在演示场景下能够组成一个可运行的系统**"
   → 你的电机空载能转 ≠ 带载能稳

⭐⭐ "同一个需求在每个人脑海里根本不是同一件事"
   → 这正是 Intent/Spec 缺口的**历史来源**（W4）
```

**【常见误解】**
1. 「演示顺利 = 符合需要」——❌ 讲义明确否定
2. 「AI 补齐了细节，所以不用管了」——⚠️ **它补齐的恰好是"决定"**，
   而**决定是否符合需要还要检验**
3. 「多人写代码只是效率问题」——❌ 真正的问题是**各自沿着不同理解前进**

**【适用边界】**
- ⚠️ **缺口：讲义未给"如何发现 AI 补了哪些未说出口的决定"的方法**
  （L1 S14 给了方向：高代价的决定值得先讨论）

**【预考题】**
1. 你让 AI 生成一个东西，它"替你决定"了哪些事？
2. 演示能跑通，说明它符合你的需要了吗？

**【练习题 + 答案】**
- Q1（识别）：AI 让"从空项目出发"变快，是因为它做了什么？
  A1：**替我们补齐了大量没有说出口的决定**：界面如何组织、数据如何保存、
  操作失败时如何反馈。
- Q2（★ 关键）："第一次演示很顺利"能说明什么？不能说明什么？
  A2：**能说明**这些决定在演示场景下**能组成一个可运行的系统**；
  **不能说明**它们**符合用户真正的需要**——那还要继续检验。
- Q3（迁移）：你让 AI 写一段 FOC 代码，它替你决定了哪些关键参数？哪些必须由你定？
  A3（开放，引导）：采样频率、限幅、死区、PI 初值等——
  **其中"数据表示"和"验收标准"属于 L1 S14 说的高代价决定**。

**【迁移题】**
让 AI 生成一个小东西，然后列出"它替你做的决定"清单（至少 5 条）。

### W13 ★★ 契约：前置 / 后置 / 不变量 = 接口的语义

**原子性**：只考一件事 ✓

> ⚠️ **本点已全量改写。** 讲义原文用 **Eiffel（面向对象语言）** 举例，
> 而学习者**不懂类与对象**。以下全部改为 **C 的函数契约**。

**【讲义原话】**
- 出处：§契约：调用者与实现者各自承诺什么
- 要点：
  - 「Bertrand Meyer 在 Applying "Design by Contract" 中讨论了**契约式设计**。
    它的出发点很朴素：**一个组件调用另一个组件时，双方应该明确各自的责任。**」
  - ⭐⭐ 「**前置条件**规定**调用者**需要保证什么；**在前置条件成立的情况下**，
    **后置条件**规定**实现者**需要保证什么。**不变量**则描述……
    在对外可用的稳定状态下应当满足的条件。
    ⭐ **它们一起构成了接口的语义，而不只是参数和返回值的类型。**」
  - ⭐ 例子（讲义原例为**不允许透支的账户**，此处改写）：
    「可以把取款的前置条件设为'金额为正，且不超过当前余额'，
    后置条件设为'新余额等于旧余额减去取款金额'……
    ⭐ **具体实现怎样存储余额，调用者不必知道；
    但只要满足前置条件，就有权依赖后置条件。**」
  - ⭐⭐ 「这份契约也明确划出了边界：**余额不足的请求没有满足它的前置条件。**
    如果产品要求把'余额不足'作为一种**正常业务结果**返回，就应该另行设计契约……
    **不能一边接受任意取款请求，一边在余额不足时用'调用者不该这样调用'逃避业务要求。
    契约描述的是双方真正同意的责任。**」

⭐⭐⭐ **本点的关键教学动作**：让他在**自己写过的 C 函数**里认出契约。

**【机制 / 为什么】** ✅ 材料给了完整机制和一条重要的边界。

**【前置】** L1 S12（Spec）、W4

**【标准范例】** —— ⭐ 全部改写成 C（他每天在写的东西）
```
⭐ 前置条件 / 后置条件 / 不变量，其实就是你写 C 函数时该写清楚的三件事：

/* 取款：不允许透支
 *
 * 前置条件（调用者必须保证）：
 *      amount > 0  且  amount <= balance
 * 后置条件（实现者保证）：
 *      balance == old_balance - amount
 * 模块不变量（始终成立）：
 *      balance >= 0
 */
int withdraw(int amount)
{
    assert(amount > 0);                 /* 前置 */
    assert(amount <= balance);          /* 前置 */
    int old = balance;
    balance -= amount;
    assert(balance == old - amount);    /* 后置 */
    assert(balance >= 0);               /* 不变量 */
    return 0;
}

⭐⭐ 讲义的那句关键：
    "**具体实现怎样存储余额，调用者不必知道；
      但只要满足前置条件，就有权依赖后置条件**"

    ← 用你的话说：
      balance 存在哪儿、用什么类型、有没有加锁 —— **调用者不用管**
      **只要我保证 amount > 0 且不超过余额，我就有权相信余额会被正确扣减**
      ⭐ 这正是你在 P0–P7 学过的「接口即契约」的**完整形式**
```

**【常见误解】**
1. 「契约就是文档注释」——⚠️ 它可以被**工具检查**（运行时的 `assert`，或静态验证）
2. 「前置条件只是"建议"」——❌ **"只要满足前置条件，就有权依赖后置条件"**，
   这是**双方的权利义务**
3. ⭐⭐ 「余额不足就说明调用者用错了」——**讲义明确反对**：
   如果产品要求把"余额不足"当**正常业务结果**，
   **就该另行设计契约**（如返回失败状态且余额不变），
   **不能一边接受任意请求，一边用"你不该这样调用"逃避业务要求**

**【适用边界】**
- ⚠️ Bertrand Meyer 原文与 Eiffel 文档**未核对** → `【待查证·引注未核】`
- ⚠️ 讲义提到 Dafny / Verus（把规约与实现联系起来的形式化工具）→ **降级为了解即可**

**【预考题】**
1. 你写一个函数时，会在哪里说明"调用者必须保证什么"？
2. 如果调用者传了一个不满足前提的参数，责任在谁？

**【练习题 + 答案】**
- Q1（识别）：前置条件、后置条件、不变量各规定谁的责任？
  A1：**前置条件**规定**调用者**需要保证什么；
  **后置条件**在前置条件成立的前提下规定**实现者**需要保证什么；
  **不变量**描述稳定状态下应当满足的条件。
- Q2（★ 关键）：它们合起来构成了什么？
  A2：**接口的语义**——**而不只是参数和返回值的类型**。
- Q3（★ 应用）："只要满足前置条件，就有权依赖后置条件"——这对"实现自由"意味着什么？
  A3：**具体实现（怎么存、用什么类型）调用者不必知道**；
  他可以**依赖承诺**。→ 这就是**局部性 / 可替换性**（接 L1 S15、L4 V13）。
- Q4（★★ 关键）：讲义说"不能一边接受任意取款请求，一边在余额不足时用
  '调用者不该这样调用'逃避业务要求"——为什么？
  A4：因为如果产品要求把"余额不足"当**正常业务结果**返回，
  **就应该另行设计契约**（例如规定失败时返回失败状态且余额不变）。
  ⭐ **契约描述的是双方真正同意的责任**，不是实现者单方面用来甩锅的借口。
- Q5（迁移）：给你写的一个 C 函数补上"前置/后置/不变量"三行注释。

### W15 ★ 「留白也是一种决定」

**原子性**：只考一件事 ✓

> ⚠️ 讲义原例用"子类可替代父类"（OO 概念），**已改为"同一个操作的两版实现"**。

**【讲义原话】**
- 出处：§留白也是一种决定 / §契约与实现
- 要点：
  - ⭐ 「第三件事是承认**模型可以有意不把一切说完**。……
    UML 的交互语义区分**合法执行轨迹**和**非法执行轨迹**……
    **这两个集合不一定覆盖所有可能的轨迹，因此还可以存在模型尚未表态的行为。**」
  - ⭐⭐ 以支付为例：
    - 「**合法**：用户确认支付，系统扣款成功，再返回成功结果。」
    - 「**非法**：用户没有确认，系统已经扣款。」
    - 「⭐ **尚未规定**：用户确认后请求超时，系统是否自动重试。」
  - ⭐⭐ 「第三类**不能直接当成已经获得业务认可的行为**。
    **它说明还有决定没做。如果实现者自行选择自动重试，就必须进一步回答：
    一次超时是否可能意味着扣款已经完成？怎样保证再次请求不会重复扣款？**」
  - ⭐ 「**形式化有成本，可以把成本花在歧义大、违反代价高、或者需要机器继续推导的地方。**
    早期业务草图只要足以支持评审，就已经有价值；需要执行或验证时，再补足相关语义。
    **明确哪些地方还没有决定，能让这种渐进过程更可控。**」

⭐⭐ **"尚未规定"是第三种状态**——这也是 L2 T5「完成的语义包括失败」的同类结构。

**【机制 / 为什么】** ✅ 材料给了三分类和成本的分配原则。

**【前置】** W13、L2 T5

**【标准范例】** —— ⭐ 用支付例子，但映射到他的场景
```
⭐ 三分类（讲义原话结构）：
    ✅ 合法      ：已经决定、允许发生的行为
    ❌ 非法      ：已经决定、禁止发生的行为
    ❓ 尚未规定  ：**还没有做的决定**

⭐ 用你的场景对照（一种通信协议）：
    ✅ 合法：收到校验正确的帧 → 回复 ACK
    ❌ 非法：校验错误却回复 ACK
    ❓ 尚未规定：**收到重复帧怎么办？超时重发几次？**

    ⚠️ 讲义的关键提醒：
      "**第三类不能直接当成已经获得业务认可的行为。
        它说明还有决定没做。**"

    ⭐ 如果你（或 AI）自己选了"重发 3 次"
      → 那就是**替你做了一个业务决定**
      → 而且这个决定可能和上位机的期望不一致
```

**【常见误解】**
1. 「没写的就是允许的」——❌ **"尚未规定"是第三类，不等于允许**

3. 「形式化越全面越好」——⚠️ 讲义明确：**有成本**，要花在**歧义大、违反代价高、
   需要机器继续推导**的地方

**【适用边界】**
- ⚠️ UML 规范具体节号**未核对** → `【待查证·引注未核】`

**【预考题】**
1. 模型里没规定的行为，是"允许"还是"禁止"？
2. 形式化该花在哪些地方？

**【练习题 + 答案】**
- Q1（识别）：UML 的交互语义区分哪三类？（结构）
  A1：**合法执行轨迹 / 非法执行轨迹 / 模型尚未表态的行为**（第三类）。
- Q2（★ 关键）：第三类能不能当成"已经获得业务认可的行为"？
  A2：**不能**。它**说明还有决定没做**。
  如果实现者自行选择一种处理方式，**就必须继续回答由此产生的问题**
  （讲义例：超时是否意味着扣款已完成？怎样保证不重复扣款？）。
- Q3（★ 应用）：形式化成本该花在哪里？
  A3：**歧义大、违反代价高、或者需要机器继续推导的地方**；
  早期草图只要能支持评审就有价值，需要执行或验证时再补足语义。
- Q4（★ 迁移）：你项目里有哪些"尚未规定"的行为？AI 替你选了哪一种？
  A4（开放，⭐ 引导）。

**【迁移题】**
为你的一个操作列出"合法 / 非法 / 尚未规定"三栏。

**【掌握判定】**
- 能说清：能说出三分类，并说明"尚未规定"不等于允许
- 能应用：能为一个操作写出三栏
- 能回忆：隔一天能复述"它说明还有决定没做"

### W16 ★ 不同含义需要不同表达 + 模型本身也要检查

**原子性**：只考一件事 ✓（"语义维度要分开"与"模型可被检查"是同一主张的两面）

> ⚠️ 讲义原例用 OO 的聚合/关联端所有权，**已改为 C 的结构体与内存归属**。

**【讲义原话】**
- 出处：§不同的含义，需要不同的表达 / §模型本身也需要检查
- 要点：
  - ⭐ 「自然语言和随手画的图，**经常让一个记号同时承担多种没有说清楚的含义**。」
  - 例：「**两条记录当前具有相同的属性值，并不说明它们是同一个对象；
    修改其中一个，另一个是否跟着改变，取决于身份和共享关系。**」
  - ⭐ 「在选课系统里，**从学生对象能找到课程，首先回答的是访问关系；
    关联端的属性归谁拥有，回答的是模型结构；对象是否随另一个对象一起销毁，
    又涉及生命周期。**……**删除一个学生的选课信息，显然不应该顺手删除整门课程。**」
  - ⭐ 「时间顺序也一样。**交互图上的上下位置，不能总被解释为全局串行执行。**
    UML 的 `seq` 表示**弱顺序**：保留各片段内部的顺序，
    也保留同一生命线上前后片段的事件顺序；
    **来自不同生命线、不同片段的事件仍可能交错。**」
  - ⭐⭐ 「因此，**短信通知的行为画在仓库备货行为上方，并不自动要求短信必须全部发送完，
    仓库才能开始工作。**如果业务确实要求两者严格有先后，就需要**明确的约束**，
    或者使用相应的严格顺序表达。
    **顺序、并发、失败路径和责任归属，都值得分别说明。**」
  - ⭐ 「**模型本身也需要检查。**OCL（对象约束语言）……可以像检查程序的类型一样，
    检查模型是否满足结构上的规则。」
  - ⚠️⚠️ 「**通过模型的良构性检查，只说明它符合被检查的建模规则，
    并不自动证明所有实现都符合业务需要。
    一个语法完全正确的支付模型，仍然可能遗漏重复扣款问题。**」

⭐⭐ **"画在图上的顺序不等于执行顺序"** 这一条，在嵌入式里极其常见（时序图歧义）。

**【机制 / 为什么】** ✅ 材料给了完整的四类"被混在一起的含义"。

**【前置】** W13、W14

**【标准范例】** —— ⭐ 用他的项目
```
⭐ 讲义说的"一个记号承担多种含义"，在嵌入式里天天发生：

    你画一条线："ADC 完成 → 处理 → 输出 PWM"
    ❓ 这条线至少混了四件事：
       ① **依赖**：处理需要 ADC 的值
       ② **顺序**：是先处理完再输出，还是并行？
       ③ **生命周期**：ADC 的缓冲区谁分配、谁释放？
       ④ **失败路径**：ADC 超时怎么办？

    ⭐ 讲义的原话：
      "**顺序、并发、失败路径和责任归属，都值得分别说明**"

⭐⭐ 关于"上下位置 ≠ 执行顺序"（弱顺序）：
    你画的时序图里，"通信发送"画在"控制计算"上面
    ⚠️ 这**不自动**要求通信发完才能开始计算
      → 它可能只是"先提到"，实际是**并发**的
      → 要严格顺序，**必须显式写约束**

≥≥ 关于"模型检查"的边界（讲义主动澄清的）：
    "**良构性检查只说明它符合被检查的建模规则，
      并不自动证明所有实现都符合业务需要。**"
```

**【常见误解】**
1. 「画在图上就是顺序」——❌ **弱顺序不等于全局串行**
2. 「两个对象属性相同就是同一个对象」——❌ **取决于身份和共享关系**
3. 「模型检查通过 = 业务正确」——❌ 讲义明确否定

**【适用边界】**
- ⚠️ UML 规范节号、OCL / MOF / Profile 细节**未核对** → `【待查证·引注未核】`
- ⚠️ 讲义也指出 UML 规范**没有把全部语义都化为 OCL**（有些约束标注"无法用 OCL 表达"）

**【预考题】**
1. 时序图里上下排列的两个动作，一定是先后执行吗？
2. 语法完全正确的模型，能保证业务正确吗？

**【练习题 + 答案】**
- Q1（★ 关键）：交互图上的上下位置表示什么？
  A1：**弱顺序**（`seq`）：**保留片段内部顺序，以及同一生命线上前后片段的事件顺序**；
  ⚠️ **来自不同生命线、不同片段的事件仍可能交错**。
  因此"画在上面"**不自动要求**"必须先全部完成"。
- Q2（识别）：讲义说要"分别说明"哪四件事？
  A2：**顺序、并发、失败路径和责任归属。**
- Q3（应用）："两个记录属性相同"能说明它们是一个对象吗？
  A3：**不能**。是否同一对象**取决于身份和共享关系**；
  **修改其中一个，另一个是否跟着变，也取决于它们的关系**。
- Q4（★★ 关键）：模型检查通过说明了什么？没说明什么？
  A4：**说明**它符合**被检查的建模规则**；
  ⚠️ **不自动证明所有实现都符合业务需要**——
  "**一个语法完全正确的支付模型，仍然可能遗漏重复扣款问题**"。
- Q5（迁移）：你的时序图里，"画在上面"的动作，实际是严格先后还是可能交错？
  A5（开放，引导他检查是否显式写了约束）。

**【迁移题】**
把你项目里的一张时序/流程说明，补上"顺序 / 并发 / 失败路径 / 责任归属"四项。

- 能应用：能识别一张图里被混在一起的含义
- 能回忆：隔一天能复述"良构性检查并不自动证明所有实现都符合业务需要"

### W17 ★★ LLM 时代，差距移到了哪里

**原子性**：只考一件事 ✓

**【讲义原话】**
- 出处：§LLM 时代，差距移到了哪里
- 要点：
  - ⭐ 「UML 试图通过共同的语言，把意图整理成明确的结构和约束。
    大语言模型让另一条路径变得可行：**直接从自然语言生成程序。
    以前需要人工补齐的中间步骤，现在经常可以一跃而过。**」
  - ⭐ 「但**规约与实现之间的差距仍然存在**。……
    一个**并发实现本身也会有多种执行轨迹**，所有相关行为都应当落在承诺的边界内。」
  - ⭐⭐⭐ 「当用户没有说明'**支付超时后怎么办**'，模型为了完成程序，往往会选一种处理方式。
    **第一次可能等待，第二次可能自动重试，第三次可能直接返回失败。
    三份代码都能运行，接口看起来相同，正常路径的测试甚至全部通过，
    但它们已经包含了不同的业务决定。**」
  - ⭐⭐ 「这就需要有人持续维护三类信息：**已经决定的行为，明确禁止的行为，
    以及尚未决定的行为。**」
  - ⭐ 「对支付系统，我们可以要求**扣款前必须获得相应确认**；
    规定**同一订单的累计扣款不能超过应付金额，并明确把重试和并发回调纳入这个要求**。
    至于内部采用什么存储结构、如何组织请求，只要满足这些承诺，**就可以保留实现自由。**」
  - ⭐ 「承诺可以先写在自然语言里，再根据问题的代价和工具能力，
    落实为**接口契约、状态机、断言、测试或验证条件**。
    ⭐⭐ **它们需要能独立于某次聊天和某份实现被保存、检查，并在需求变化时一起更新。**」
  - ⭐⭐⭐ 「AI 越能快速生产代码，这个接口就越值得认真设计：
    **哪些事已经决定，哪些行为绝不能发生，哪些细节可以交给实现者选择。**
    给已决定的事一个**显式、类型化、机器可检查的表达**，
    我们才更有可能在快速改写实现时，**继续保有对软件行为的控制。**」

⭐⭐⭐ **本讲的收束**，也是全课程关于"AI 时代什么最值得做"的回答。

**【机制 / 为什么】** ✅ 材料给了完整机制和三分类。

**【前置】** W15（三类行为）、W13（契约）、L2 T4（写清完成）

**【标准范例】** —— ⭐ 用他的场景，一次讲透
```
⭐⭐ 讲义那个"三份代码都能运行"的例子，换成你的场景：

    你说"做一个速度环"，没说"堵转时怎么办"
    → AI 为了把代码写完，**必然要选一种**
      版本 A：堵转 → 直接停机
      版本 B：堵转 → 限流继续试
      版本 C：堵转 → 报错返回

    ⚠️ 三份代码**都能编译、都能跑、正常路径测试全过**
    ⚠️ 但它们**包含不同的业务决定**（可能损害硬件 vs 可能忽略故障）

⭐⭐ 所以讲义说"要持续维护三类信息"：
    ✅ 已经决定的行为：转速跟随、超调 < 5%
    ❌ 明确禁止的行为：**任何情况下不得持续超过 5A**
    ❓ 尚未决定的行为：**堵转时是停机还是限流**（这类要显式列出来）

    ⭐ 然后"内部用什么存储结构、怎么组织请求" → **保留实现自由**

⭐⭐⭐ 最重要的一句：
    "**它们需要能独立于某次聊天和某份实现被保存、检查，
      并在需求变化时一起更新。**"
    → 写在哪？
       L1 的 Spec / L3 的提交与原子变更 / L4 的可追踪性 / W13 的契约
       ——**前四讲的东西在这里合上了**
```

**【常见误解】**
1. 「三份代码都能跑，所以等价」——❌ **"已经包含了不同的业务决定"**
2. 「正常路径测试全过就安全」——❌ 讲义明确把这个当作反例
3. 「把承诺写在聊天里就行」——❌ **必须能独立于某次聊天和某份实现被保存、检查**

**【适用边界】**
- ⚠️ **缺口：讲义未给"如何选择把承诺落实成哪种形式"（契约/状态机/断言/测试/验证）的具体判据**
  （只给了方向：根据**问题的代价和工具能力**）

**【预考题】**
1. 两个 AI 分别生成同一个功能的代码，都测试通过。它们等价吗？
2. 你要维护"三类信息"，分别是哪三类？

**【练习题 + 答案】**
- Q1（★ 关键）：为什么"三份代码都能运行、接口看起来相同、正常路径测试全部通过"，
  仍然可能不等价？
  A1：因为它们**已经包含了不同的业务决定**——
  在"用户没有说明"的地方，**模型为了完成程序，往往会自行选一种处理方式**
  （讲义例：超时后可能等待、可能自动重试、可能直接返回失败）。
- Q2（识别）：需要持续维护的三类信息是哪三类？
  A2：**已经决定的行为 / 明确禁止的行为 / 尚未决定的行为。**
- Q3（★ 应用）：支付系统里，哪些是"已决定"，哪些是"留白"？
  A3：**已决定**：扣款前必须获得相应确认；**同一订单累计扣款不能超过应付金额**
  （且明确把重试和并发回调纳入）；**留白**：内部用什么存储结构、如何组织请求
  —— **只要满足承诺就保留实现自由**。
- Q4（★★ 关键）：这些承诺必须满足什么条件？
  A4：**需要能独立于某次聊天和某份实现被保存、检查，并在需求变化时一起更新。**
- Q5（★ 迁移）：为什么说"AI 越能快速生产代码，这个接口就越值得认真设计"？
  A5：因为实现随时可以被快速改写；**只有承诺被显式表达，才可能在改写实现时
  继续保有对软件行为的控制**。

**【迁移题】**
给你项目写一份"三类信息"清单，并说明每类保存在哪里、怎样检查。

**【掌握判定】**
- 能说清：能说出三份代码为何不等价、三类信息、以及承诺的保存要求
- 能应用：能为一个功能写出三类信息
- 能回忆：隔一天能复述"它们需要能独立于某次聊天和某份实现被保存、检查"
