## 第一部分：复杂度的本质（Ch 2）

### A0 全书的公理：一切设计都是为了降低复杂度

**原子性**：只考一件事 ✓

**【原话】**（Ch 1；Ch 2 开篇）
> 这本书讲的是**如何设计软件系统以最小化其复杂度**。"第一步是理解敌人。"

**【外部补充】** 这是全书所有原则的**唯一裁判**。后面每一条"应该这样设计"，理由最终都归结到"这样做复杂度更低"。
→ **记住这一条，后面 40 个点都不需要死记，可以自己推。**

**【前置】** 无（本书起点）

**【标准范例】**
两个设计方案之争，判据只有一个：
> **哪个方案让"下一个改代码的人"更省力？**

**【常见误解】**
1. 「设计的目标是让代码能跑」——见 A6，这是战术编程
2. 「设计的目标是代码短」——见 A2 认知负荷部分，原书明确反驳：**短不一定简单**
3. 「设计的目标是功能强大」——功能是收益，接口是成本，见 A11

**【预考题】**
1. 你觉得"把代码写好看"到底是为了什么？给一个不是"老板要求"的理由。

**【练习题 + 答案】**
- Q：原书说复杂度"与系统的整体规模或功能多少不一定相关"。一个 500 行的小程序，可能很复杂吗？
  A：可能。复杂度取决于开发者**理解和修改的难度**，不取决于规模。

**【掌握判定】**
- 能说清：说出"设计的目的是降低复杂度"，并解释复杂度指的是"理解与修改的难度"
- 能应用：给定两个方案，能用"哪个让后来者更省力"做判断

### A1 复杂度的定义（实用定义）

**原子性**：只考一件事 ✓

**【原话】**（§2.1）
> 复杂度是**任何与软件系统的结构有关、使得系统难以理解和修改的东西**。

**【原话】** 两种等价说法：
- 如果系统难以理解和修改 → 复杂；容易 → 简单
- 用成本/收益说：复杂系统里，即使做很小的改进也要花很多力气

**【原话】三条重要限定**（这三条最容易被忽略）：
1. **复杂度是开发者在特定时刻、为达成特定目标时体验到的**——它不必然与系统规模相关
2. **复杂度由最常发生的活动决定**：系统里有一小部分极其复杂，但几乎没人碰，那它对整体复杂度影响很小
3. **复杂度对读者比对作者更明显**：你觉得简单，别人觉得复杂，那它就是复杂的

**【原话】** 作者给的粗略量化公式：
> 整体复杂度 C = Σ（各部分 p 的复杂度 c_p × 开发者在该部分花费的时间比例 t_p）

**【前置】** A0

**【标准范例】**
一个单片机项目里有一段 800 行的、没人敢动的电机换相表生成代码。
- 它很复杂
- 但它**三个月才被碰一次**
- → 按第 2 条限定，它对项目整体复杂度的贡献**很小**

反过来：一个 30 行的 `delay_ms()` 被全项目 60 处调用，里面用了一个全局的时钟频率变量——**它很简单，但贡献的复杂度很高**。

**【常见误解】**
1. 「复杂 = 大 / 功能多」——明确错，见限定 1
2. 「我觉得简单就行」——明确错，见限定 3
3. 「复杂的地方藏起来就没事了」——**部分对**（限定 2），但前提是它真的一直不被碰

**【适用边界】**
- ⚠️ 缺口：公式只是"粗略的数学描述"，作者自己说明它不可精确计算

**【预考题】**
1. 一个函数只有 3 行，却很"复杂"。这可能吗？在什么情况下？

**【练习题 + 答案】**
- Q：按 A1 的限定 3，"复杂度由读者判断"。如果你是作者，别人说你的代码复杂但你不同意，原书建议怎么做？
  A：不要争辩，去**问对方为什么觉得复杂**——因为你的目标不是写你能用的代码，而是写别人也能用的代码。
- Q：为什么"我理解的复杂度"和"团队理解的复杂度"可能不一致，且这个不一致有价值？
  A：它是发现"未知的未知"的线索。

**【迁移题】**
你的项目里有 `main.c`，2000 行，你天天改，觉得挺顺手。同事每次改都抱怨。按 A1，谁说了算？

**【掌握判定】**
- 能说清：给出复杂度定义 + 至少复述两条限定
- 能应用：判断一段代码"对项目整体复杂度"贡献大不大（用"被碰的频率"）
- 能回忆：不看材料说出三条限定

### A2 复杂度的三大症状

**原子性**：⚠️ 本点含 3 个术语，**建议单独一次会话**（负荷偏高）

**【原话】**（§2.2）复杂度通过三种方式显现：

| 症状 | 原文含义 |
|---|---|
| **改动放大**（Change amplification） | 一个看起来简单的改动，需要在很多不同地方改代码 |
| **认知负荷**（Cognitive load） | 开发者为了完成任务**需要知道多少东西** |
| **未知的未知**（Unknown unknowns） | **不清楚**哪些代码需要改，或者需要什么信息 |

**【原话】关键判断**：
> **三者中，"未知的未知"最糟。**

理由：改动放大虽然烦，但只要**知道**要改哪些地方，改完就能工作；认知负荷高会加成本，但只要**知道**该读哪些信息，改动大概率还是对的。
**而未知的未知，你连"要去找什么"都不知道**，只能读遍全部代码——大系统里这不可能。

**【原话】作者给的经典范例**（网站 banner 颜色）：
- (a) 每个页面各自写死背景色 → 改一次颜色要改所有页面 → **改动放大**
- (b) 抽出中心变量 → 改一处即可
- (c) **但有几个页面用了"更深的同色系"做强调，且颜色是各自写死的** → 改中心变量时，**没人会想到还要改那几个强调色** → **未知的未知**

**【原话】关于认知负荷的补充**（原书特意反驳"行数越少越简单"）：
> 作者见过只用几行就能写应用的框架，但**极难搞清那几行该写什么**。
> **有时代码多几行反而更简单，因为它降低了认知负荷。**

**【前置】** A1

**【标准范例】**（C 语境）

```c
/* 改动放大：这个项目里，电机最大转速在 3 个地方各写一遍 */
#define MAX_RPM_A   3000   /* motor.c   */
#define MAX_RPM_B   3000   /* ctrl.c    */
#define MAX_RPM_C   3000   /* ui.c      */

/* 改规格为 4000 时，你得知道有这三处 —— 这就是认知负荷 */
```

```c
/* 未知的未知：更阴险的版本 */
#define MAX_RPM     3000            /* 中心定义，看着很好 */

/* 但在 ui.c 里，为了把转速条画成渐变，写死了颜色阈值： */
if (rpm > 2700) { set_color(RED); }  /* 2700 ≈ 0.9 * 3000，写死的 */
```
改 `MAX_RPM` 为 4000 后，报警阈值不会跟着变——**而且没有任何东西提示你它存在**。

**【常见误解】**
1. 「三种症状严重程度差不多」——明确错，未知的未知最糟
2. 「改动放大最严重，因为最累」——错。只要**可发现**，它就不算最糟
3. 「代码写短一点就能降低认知负荷」——原书明确反驳

**【适用边界】**
- ⚠️ 缺口：原书没给"如何度量认知负荷"的方法

**【预考题】**
1. 三种症状里，你觉得哪个最可怕？为什么？
2. 如果一段代码在 5 个地方重复，但**有个脚本能自动找出所有 5 处**——它还可怕吗？

**【练习题 + 答案】**
- Q：把这个例子归类：你在 `motor.c` 改了 PWM 频率，同事在 `led.c` 里假设了 PWM 频率是 1kHz 来算闪烁周期。这是哪种症状？
  A：**未知的未知**。`led.c` 依赖了 `motor.c` 的实现细节，但**没有任何机制提示这个依赖存在**。
- Q：改动放大和认知负荷，哪个更容易被修复？为什么？
  A：改动放大。因为它**可发现**——你能数出有几处。认知负荷需要你先知道"该读什么"。

**【迁移题】**
你的 `main.c` 里有 200 行，其中 30 处直接操作寄存器。把它封装成 `motor_set_rpm()`。用 A2 的三个症状分别说明：这个重构各改善了哪一项？（提示：有一项可能**没改善甚至变差**）

**【掌握判定】**
- 能说清：三症状名称 + 为什么未知的未知最糟
- 能应用：给一个真实 bug 场景，正确归类
- 能回忆：不看材料列出三个症状

### A3 复杂度的两大成因：依赖 + 晦涩

**原子性**：只考一件事 ✓

**【原话】**（§2.3）
> 复杂度由两样东西引起：**依赖（dependencies）** 和 **晦涩（obscurity）**。

**【原话】依赖的定义**（★ 与上一课直接对应）
> **当一段代码无法被孤立地理解和修改时，就存在依赖**；这段代码与其他代码相关，如果改了它，其他代码就必须被考虑和/或修改。

**【原话】晦涩的定义**
> **重要信息不明显**时，就产生晦涩。
> 例：变量名太笼统（如 `time`）；文档没说单位，只能翻代码猜。
> **晦涩常常和依赖一起出现**——依赖存在，但不明显。

**【原话】两者的对应关系**：
> 依赖导致 **改动放大** 和 **高认知负荷**；
> 晦涩造成 **未知的未知**，也助长认知负荷。

**【原话】依赖不可消除**（★ 再次印证上一课的结论）
> **依赖是软件的根本组成部分，不可能完全消除。**
> 事实上我们是**故意**引入依赖的——每写一个新函数就围绕它的接口产生依赖。
> **设计的目标是减少依赖的数量，并让剩下的依赖尽可能简单、明显。**

**【原话】这个转换技巧很关键**（网站例子的总结）：
> 新版网站消灭了页面之间的依赖，但**创造了一个围绕"取背景色"这个 API 的新依赖**。
> 幸运的是**新依赖更明显**：能通过搜索变量名找到所有使用处，编译器也会帮忙报错。
> **它用一个不明显、难管理的依赖，替换成了一个更简单、更明显的依赖。**

**【前置】** A1, A2

**【标准范例】**
```c
/* 不明显的依赖 + 晦涩 */
int timeout;   /* 单位是什么？谁在改它？ */

/* 更明显的依赖 */
int timeout_ms;   /* 单位写在名字里 —— 晦涩降低 */
```
按原书：**目标不是"消灭依赖"，而是"让依赖可见"**。

**【常见误解】**
1. 「好的设计就是没有依赖」——**明确错**，原书说依赖不可消除、且是故意引入的
2. 「只要封装好，依赖就消失了」——封装只是让依赖**更明显/受限**，不是消失
3. 「晦涩就是文档不够」——**部分对**。原书说：**晦涩也是设计问题**；"需要大量文档"本身就是设计不对的危险信号

**【适用边界】**
- ⚠️ 缺口：没有给出"依赖数量"的可计算方法

**【预考题】**
1. 上一课我们说"耦合不能消除，只能降低"。这里原书说"依赖不能消除"。**这两个是同一件事吗？**

**【练习题 + 答案】**
- Q：把"全局变量 `mode` 被 5 个文件读写"改成"通过 `set_mode()` 设置，通过 `get_mode()` 读取"。依赖消失了吗？改善了哪一项？
  A：**没消失，只是变得明显**——依赖现在集中在两个函数上，可以通过函数名搜索到，编译器也能检查。
- Q：为什么原书说"需要大量文档"是设计问题的危险信号？
  A：因为大量文档往往在弥补**晦涩**；而晦涩的根因常常是设计不够清晰。

**【迁移题】**
你的 `motor.c` 和 `encoder.c` 都各自实现了一遍"把霍尔计数转成角度"的逻辑。按 A3：这里是什么问题？是依赖还是晦涩？改起来会怎样？

**【掌握判定】**
- 能说清：说出两成因 + 它们分别对应哪些症状
- 能应用：给一个代码场景，判断是依赖问题还是晦涩问题
- 能回忆：说出"依赖不可消除，目标是让依赖更明显"

### A4 复杂度是渐进的（零容忍）

**原子性**：只考一件事 ✓

**【原话】**（§2.4）
> 复杂度**不是由一次灾难性错误造成的，而是由许多小块累积起来的。**
> 单独一个依赖或一处晦涩，几乎不会显著影响系统的可维护性。复杂度来自成百上千个小问题的积累。

**【原话】** 为什么难以控制：
> 你很容易说服自己："我这次改动引入的一点点复杂度没什么大不了。"
> **但如果每个开发者对每次改动都这么想，复杂度会迅速累积。**
> 一旦累积起来就很难消除——因为**修好单独一个依赖或晦涩，本身并不会带来多大差别**。

**【原话】结论**
> 要减缓复杂度的增长，必须采取 **"零容忍"（zero tolerance）** 的态度。

**【前置】** A1

**【标准范例】**
单次改动的诱惑：
```c
/* "就这一次，图省事" */
motor_speed = 3000;   /* 直接写全局变量，不走 set 函数 */
```
一次无害。但 50 次之后，这个全局变量就被 12 个文件读写，谁也不知道它的合法范围。

**【常见误解】**
1. 「这次赶工期，以后再清理」——见 A6，这就是战术编程的滑坡
2. 「小事不用管，等出问题再重构」——原书说等到那时成本已不可承受
3. 「零容忍 = 追求完美」——不是。零容忍针对的是**不必要的复杂度**，不是禁止任何取舍

**【适用边界】**
- ⚠️ 缺口：没有给出"什么时候可以容忍"的量化标准

**【预考题】**
1. "我这次先图快，下个迭代再重构" —— 这句话有什么问题？（提示：想想它会发生几次）

**【练习题 + 答案】**
- Q：为什么"修好一个依赖"对整体复杂度几乎没有帮助？
  A：因为复杂度是累积的，单个问题在总量里占比极小。

**【掌握判定】**
- 能说清：说出"复杂度是累积的"+"零容忍"
- 能应用：识别出"就这一次"式的妥协

### A5 战术编程 vs 战略编程 ★

**原子性**：只考一件事 ✓

**【原话】**（Ch 3）
> **战术编程**：主要目标是"把它弄跑起来"。看起来完全合理，但它**使好的系统设计几乎不可能**。
> 你是短视的：不为未来做规划，不花时间找最好的设计，"加一点点复杂度、塞一两个小补丁没关系"。

**【原话】滑坡怎么发生的**：
> 复杂度累积 → 开始出问题 → 你想"现在更重要的是做下一个功能，而不是回头重构" → 于是打补丁 → **补丁创造更多复杂度，又需要更多补丁** → 很快代码一团糟 →
> 此时清理要花几个月，**进度根本不允许**，而"修一两个问题看起来也没什么用" → **于是你继续战术编程。**

**【原话】战略编程的定义**
> **第一步是意识到"能跑的代码是不够的"。**
> 最重要的东西是系统的**长期结构**。
> 系统里大部分代码都是通过**扩展已有代码**写出来的，所以你最重要的工作是**让未来的扩展变得容易**。
> → 你的首要目标必须是**产生伟大的设计**，而它**顺便也能跑**。

**【原话】两种投资**
- **主动**：为每个新模块多花一点时间找简单设计；**不要用第一个想到的方案**，试两三个再挑最干净的
- **被动**：设计错误不可避免；发现后**不要绕过它**，花点额外时间修掉它

**【原话】投资多少**：**总开发时间的 10–20%**
- 不建议一次大投入（那是瀑布模型，已知无效）
- 理想设计是**随着你对系统的了解一点点浮现出来的**
- 短期慢 10–20%，但几个月内就会开始回本；**之后投资变成免费的**

**【原话】关于战术龙卷风（Tactical Tornado）**
> 每个组织几乎都有一个：**产出代码比别人快得多，但完全是战术式的**。
> 有些组织把这种人当英雄。**但他们留下一条毁灭的尾巴。**
> 将来必须接手他们代码的工程师，几乎不会把他们当英雄——而且清理烂摊子会让那些（真正的）工程师**看起来**进度更慢。

**【原话】反面案例**：Facebook 的 "Move fast and break things"——公司极成功，但代码库因战术风格受损；后来改口为 "Move fast with solid infrastructure"。**Google 和 VMware 同期采用更战略的方式，也成功了。**

**【前置】** A0, A4

### A6 模块 = 接口 + 实现

**原子性**：只考一件事 ✓

**【原话】**（§4.1）
> 为了管理依赖，我们把每个模块看成两部分：**接口**和**实现**。
> - **接口** = 在别的模块里工作的开发者**为了使用这个模块所必须知道的一切**
> - **实现** = 履行接口所承诺之事的代码

**【原话】关键规则**
> 在某个模块里工作的开发者，必须理解**这个模块的接口和实现**，加上**它所调用的其他模块的接口**。
> **他不需要理解其他模块的实现。**

**【原话】模块的定义**（★ 对 C 背景很友好）
> 本书中，**模块 = 任何有接口和实现的代码单元**。
> 面向对象语言里的每个类是一个模块。
> **类中的方法，或者非面向对象语言里的函数，也可以被看作模块**——它们同样有接口和实现。
> 更高层的子系统和服务的接口可以是内核调用或 HTTP 请求。

**【原话】最好的模块**
> **接口比实现简单得多。** 两个好处：
> 1. 简单接口**最小化了这个模块加给系统其余部分的复杂度**
> 2. 如果模块的修改**不改变接口**，就不会影响其他模块

**【原话】接口包含两类信息**
- **正式的（formal）**：代码里明确写出的，语言能检查的。函数的正式接口 = 它的签名（参数名与类型、返回类型、异常）
- **非正式的（informal）**：语言**无法**理解和检查的。包括**高层行为**（如"这个函数会删除参数指定的文件"）、**使用约束**（如"必须先调 A 再调 B"）
> **一般规则：如果开发者为了使用一个模块需要知道某信息，那它就是接口的一部分。**
> **对大多数接口，非正式部分比正式部分更大、更复杂。**

**【前置】** 上一课的 P0（什么是模块）

**【标准范例】**

```c
/* ---- 接口（放在 .h 里）---- */

/**
 * 设置电机目标转速。
 *
 * @param rpm  目标转速，单位 rpm；超出 [0, MOTOR_MAX_RPM] 会被钳到边界
 * @return     实际生效的转速
 *
 * 注意：必须先调用 motor_init()，否则返回 0 且不产生效果。
 */
int motor_set_speed(int rpm);

/* ---- 实现（放在 .c 里，外面看不到）---- */
static int s_current_rpm;
static int s_pwm_duty;
void pwm_reconfigure(int duty) { /* ... */ }
```
- **正式接口** = `int motor_set_speed(int rpm)` 这一行
- **非正式接口** = 单位、钳位规则、必须先 init、返回值含义 → **这一部分比签名本身大三倍**

**【常见误解】**
1. 「接口 = 函数签名」——**不完整**。签名只是正式部分，**非正式部分通常更大**
2. 「实现就是"怎么写的"，跟使用者无关」——对，但**未文档化的非正式接口**会造成未知的未知
3. 「私有变量 = 信息隐藏」——**明确错**，见 A14

**【适用边界】**
- 【原话】⚠️ 作者脚注：确实存在用形式化规格语言描述行为的语言，可以自动校验接口与实现一致。但作者**个人意见**是：**用自然语言描述的接口，对开发者来说可能比形式化规格更直观易懂**

**【预考题】**
1. 一个函数的"接口"就是它的参数列表吗？还有什么？
2. 你写 `.h` 的时候，通常会写多少注释？这够吗？

**【练习题 + 答案】**
- Q：`void motor_init(void);` 这个签名，正式接口是什么？有哪些可能的**非正式**接口没写出来？
  A：正式 = 无参无返回。非正式可能包括：必须在时钟初始化之后调用；只能调用一次；调用后外设进入某状态；耗时约 X ms。
- Q：为什么"不使用其他模块的实现"很重要？
  A：因为一旦依赖别的模块的实现细节，那个模块内部一改，你就得跟着改——这正是上一课的耦合。

**【迁移题】**
你的 `motor.h` 现在只有函数声明。按 A6，哪些东西**应该**写进 `.h` 的注释里，才是完整的接口？

**【掌握判定】**
- 能说清：说出接口/实现的分工 + 接口含正式与非正式两部分
- 能应用：给定一个 `.h`，指出它缺失了哪些非正式接口

### A7 抽象：两种失败模式

**原子性**：只考一件事 ✓

**【原话】**（§4.3）
> **抽象 = 一个实体的简化视图，它省略了不重要的细节。**
> 定义里"**不重要**"这个词至关重要：**省略越多的不重要细节越好，但一个细节只有真的不重要才可被省略。**

**【原话】抽象会以两种方式出错**（★ 本点的核心）：
1. **包含了其实不重要的细节** → 让抽象**比必要的更复杂**，增加使用者的认知负荷
2. **省略了其实很重要的细节** → 造成**晦涩**。只看抽象的人**得不到正确使用所需的全部信息**。
   > **这种省略了重要细节的抽象，是一个「假抽象」（false abstraction）：看起来简单，实际上不是。**
   作者给的例子：一个 6 行的函数，文档写了 10 行——说明这个抽象没省掉什么。

**【原话】设计抽象的关键**
> 理解**什么是重要的**，并寻找**把"重要信息"的数量降到最少**的设计。

**【原话】作者特意为"行数少 ≠ 简单"辩护**
> 短 ≠ 简单。有些接口看起来参数极少，但**你必须知道很多隐含规则才能正确使用**——那是假抽象。

**【前置】** A6

**【标准范例】**
```c
/* ---- 失败模式 2：假抽象（省略了重要细节）---- */
void motor_set_speed(int v);
/* 问题：v 是什么单位？rpm？rad/s？PWM 占空比？0-100 还是 0-32767？
   不知道这些，调用者没法用。文档省掉了"重要"的细节。 */

/* ---- 失败模式 1：包含不重要细节（抽象不够简）---- */
void motor_set_speed(int rpm, int pwm_freq_hz, int dead_time_ns, uint8_t phase_order);
/* 问题：后三个是内部实现细节，绝大多数调用者不关心。
   把它们暴露出来，增加认知负荷。 */
```

**【常见误解】**
1. 「抽象就是把复杂的藏起来」——**不完整**。藏错了就变成"省略了重要细节"，是假抽象
2. 「参数越少越抽象」——错，见 A7 的失败模式 2
3. 「文档越少越简洁」——错，省略重要信息是缺陷不是简洁

**【适用边界】**
- ⚠️ 缺口：没有给出"如何判断某细节是否重要"的通用方法

**【预考题】**
1. 一个函数只有 2 个参数，但要正确调用它你需要知道 5 条隐含规则。这是好的抽象吗？

**【练习题 + 答案】**
- Q：区分两种失败模式：`void init(int mode);`（`mode` 的合法取值文档里没写）属于哪种？
  A：**失败模式 2（假抽象）**——省略了重要细节。
- Q：`void set_speed(int rpm, int pwm_freq);`（PWM 频率是内部实现），属于哪种？
  A：**失败模式 1**——包含了不重要的细节。

**【迁移题】**
找一个你写过的 `.h`，检查：
（a）有没有哪个参数是"不该暴露的内部细节"？
（b）有没有哪条"调用者必须知道"的规则没写进注释？

**【掌握判定】**
- 能说清：说出两种失败模式，并能举例
- 能应用：判断一个接口属于哪种失败
- 能回忆：不看材料说出"假抽象"的含义

### A8 深模块 vs 浅模块 ★ 核心

**原子性**：只考一件事 ✓

**【原话】**（§4.4）
> **最好的模块提供强大的功能，但接口简单。我用「深」（deep）来描述这种模块。**
> 想象每个模块是一个矩形：矩形**面积** ∝ 模块实现的功能；**顶边** = 接口，顶边长度 = 接口的复杂度。
> **最好的模块是深的**：大量功能藏在简单接口后面。

**【原话】成本收益视角**
> - 模块的**收益** = 它提供的功能
> - 模块的**成本**（就系统复杂度而言）= 它的**接口**
> > **接口是好东西，但更多、更大的接口不一定更好！**

**【原话】浅模块（§4.5）**
> 浅模块是**接口相对其提供的功能而言比较复杂**的模块。
> 例：实现链表的类就是浅的——操作链表本来就没几行代码，接口的复杂度几乎等于实现的复杂度。
> **小模块往往是浅的。**

**【原话】浅模块的极端例子**（原书从软件设计课项目里取的）
```java
private void addNullValueForAttribute(String attribute) {
    data.put(attribute, null);
}
```
> 从管理复杂度的角度，这个方法**让事情变糟了，而不是变好**：
> - 它**没有提供抽象**——它全部功能都从接口可见
> - 调用者大概还需要知道"属性会被存进 `data` 变量里"
> - 想这个接口并不比想完整实现更简单
> - 如果认真写文档，**文档会比代码还长**
> - 调用它比直接操作 `data` 变量**还要多敲几个字符**
> → **它增加了复杂度（多一个接口要学），却没有补偿性的收益。**

**【原话】Unix I/O 的例子（深模块典范）**
只有五个基本系统调用：`open / read / write / lseek / close`
> 现代实现需要**几十万行代码**，处理磁盘表示、目录存储、权限、并发调度、缓存、多种存储设备……
> **这些对调用系统调用的程序员完全不可见。**
> **Unix I/O 接口的实现多年来经历了剧变，但五个基本内核调用没变过。**

**【原话】垃圾回收器的例子**
> 它**根本没有接口**——在幕后不可见地回收内存。
> 加进垃圾回收实际上**缩小了系统的整体接口**，因为它消除了"释放对象"的那个接口。

**【前置】** A6, A7

**【标准范例】**（C 语境）

```c
/* ---------- 浅模块 ---------- */
int motor_get_pwm_duty(void);       /* 只是读一个内部变量 */
void motor_set_pwm_duty(int d);     /* 只是写一个内部变量 */
/* 调用者需要知道 duty 的合法范围、它和转速的关系、什么时候该改它
   → 接口不比实现简单，且把实现细节暴露了 */

/* ---------- 深模块 ---------- */
int motor_set_speed(int rpm);
/* 调用者只需要知道"给目标转速"
   内部的 PID、PWM 重配置、死区补偿、编码器换算全部隐藏
   → 大量功能，一个参数 */
```

**【常见误解】**
1. ★ **「模块越小越好」**——**明确错**。原书说小模块往往是**浅**的，反而增加系统级复杂度。见 A9
2. 「接口多 = 功能强」——错。接口是成本
3. 「深度 = 代码行数多」——是"功能/接口"的比例，不是绝对行数

**【适用边界】**
- ⚠️ 缺口：没有数值化"深度"的方法，作者用的是矩形面积/边长的定性比喻

**【预考题】**
1. 两种写法，哪个是深模块？
   - 甲：`void pid_set_kp(float)`, `void pid_set_ki(float)`, `void pid_set_kd(float)`, `void pid_update(void)`
   - 乙：`int motor_set_speed(int rpm)`

**【练习题 + 答案】**
- Q：为什么"垃圾回收器"被认为能**缩小**系统接口？
  A：因为它消除了"手动释放内存"这个接口——接口数量净减少，而功能增加。
- Q：链表类为什么是浅模块？
  A：操作链表的实现本来就没几行代码，接口复杂度≈实现复杂度，没藏住什么。
- Q：`int motor_set_speed(int rpm)` 是深还是浅？判断依据是什么？
  A：深。判断依据是**接口复杂度 vs 隐藏功能的比值**——一个 int 参数背后藏着 PID、PWM、换算、限幅、保护等。

- 能应用：给两个接口，判断哪个更深
- 能回忆：不看材料说出"接口是成本，功能是收益"

### A9 Classitis：拆得越小越好是错的 ★★ 直接回答上一课留下的问题

**原子性**：只考一件事 ✓
**为什么重要**：这就是你上次没答出来的 Q3 的**官方答案**。

**【原话】**（§4.6）
> 不幸的是，深模块的价值今天**没有被广泛认识**。
> 编程界的**传统智慧是"类应该小，而不是深"**。学生常被教导：类设计中最重要的就是把大类拆成小类。
> 对方法也有同样建议："**任何超过 N 行的方法都应该拆成多个方法**"（N 可以小到 10）。
> > **这种做法导致大量浅的类和方法，它们增加了系统的整体复杂度。**

**【原话】Classitis 的定义**（★ 全书针对你那个问题最直接的一段）
> "类应该小"这种做法的极端，是我称之为 **classitis（类炎）** 的综合征。
> 它源于一个**错误的观点："类是好的，所以类越多越好。"**
>
> 在患有 classitis 的系统中，开发者被鼓励把每个新类的功能降到最少：
> **如果你想要更多功能，就引入更多类。**
>
> > **Classitis 可能让每个类单独看都很简单，但它增加了整个系统的复杂度。**
> > 小类贡献的功能不多，所以必须有很多个，**每个都有自己的接口**。
> > **这些接口累积起来，在系统层面造成巨大的复杂度。**
> > 小类还会因为每个类都要写样板代码，导致冗长的编程风格。

**【原话】Java 类库是 classitis 最明显的例子之一**
> 打开一个文件读取序列化对象，要创建**三个**对象（`FileInputStream` → `BufferedInputStream` → `ObjectInputStream`）。
> 前两个对象在文件打开后就再也用不到了。
> 特别烦人（且容易出错）的是：**缓冲必须显式创建**——忘了创建就没有缓冲，I/O 会变慢。
> > **提供选择是好的，但接口应该让最常见的用法尽可能简单。**
> > 几乎所有文件 I/O 使用者都需要缓冲，所以它应该默认提供。

**【原话】Unix I/O 的对照**
> Unix 系统调用的设计者**让常见情况变简单**：他们认识到顺序 I/O 最常见，就把它设为默认。
> 随机访问仍然容易（用 `lseek`），但只做顺序访问的开发者**根本不需要知道它的存在**。
> > **如果一个接口有很多功能，但大多数开发者只需要知道其中几个，那么这个接口的"有效复杂度"只是那些常用功能的复杂度。**

**【原话】由此得出的一条原则**
> **接口应该被设计成让最常见的用法尽可能简单。**（书末原则汇总，p.27）

**【前置】** A6, A7, A8

**【标准范例】**（C 语境）

```c
/* ---------- Classitis 风格：拆得很细，每块都很"简单" ---------- */
/* motor_raw.h     */ int  motor_raw_write_reg(uint8_t addr, uint16_t v);
/* motor_clamp.h   */ int  motor_clamp_rpm(int rpm);
/* motor_convert.h */ int  motor_rpm_to_duty(int rpm);
/* motor_apply.h   */ void motor_apply_duty(int duty);
/* motor_state.h   */ int  motor_get_state(void);

/* 调用者为了"设置转速"要依次调用 4 个：
   clamp → convert → apply → （再用 state 检查）
   ⚠️ 而且必须知道调用顺序 —— 这就是 classitis 的代价 */

/* ---------- 深模块风格 ---------- */
/* motor.h */ int motor_set_speed(int rpm);
/* 内部把 clamp / convert / apply / 状态更新全做了 */
```

**【常见误解】**
1. ★★ **「类/模块越小越好」** —— **这是 classitis，原书明确判为错误**
2. ★ **「有硬性的行数上限，超过就拆」** —— 原书明确反对："任何超过 N 行的方法都应拆分（N 可小到 10）"是导致 classitis 的做法
3. 「拆得细 = 职责单一 = 好设计」——**职责单一的方向没错，但"拆成更多单元"不是达成的唯一手段**，而且常常反效果
4. 「抽象越多越好」——错。**每个新接口都是净成本**

**【适用边界】**
- ⚠️ **重要**：原书**不是**说"应该做大类"。
  §5.5 明确说："信息隐藏常常可以通过**让一个类稍大一点**来改善"——但 §5.5 同时说"当然，也可能把'更大的类'这个想法做得过头（比如整个应用一个类）"。
  → **判据不是大小，是"这个结构让整体复杂度变低还是变高"。** 见 A17（拆分的四种代价）

**【预考题】**
1. 有人把一个模块拆成 8 个各司其职的小模块，每个都比原来简单。整体设计一定更好吗？为什么？
2. 如果"类越小越好"是错的，那"什么"才是对的判据？

**【练习题 + 答案】**
- Q：为什么 classitis 会让每个类"看起来简单"但系统"实际更复杂"？
  A：因为**每个类都贡献了一个新接口**；接口是净成本。单元简单度的提升，被接口数量的增长抵消并反超。
- Q：Java 的 `FileInputStream` + `BufferedInputStream` 设计，问题出在哪？Unix 是怎么处理的？
  A：缓冲必须显式创建，且忘了会静默变慢（把常见情况搞复杂了）；Unix 把最常见的情况（顺序 I/O）设为默认，不常用的 `lseek` 不干扰普通人。

### A10 让最常见的用法尽可能简单

**原子性**：只考一件事 ✓

**【原话】**（§4.7；书末原则汇总 p.27）
> **接口应该被设计成让最常见的用法尽可能简单。**

**【原话】"有效复杂度"的概念**（★ 很实用）
> **如果一个接口有很多功能，但大多数开发者只需要知道其中几个，那么这个接口的有效复杂度只是那些常用功能的复杂度。**

**【原话】具体手法**（从 Unix vs Java 的对比中提炼）
- 把**最常见的情况设为默认**（顺序 I/O 是默认）
- 不常用的能力**仍然容易做到**，但**不干扰**普通用户（`lseek` 存在，但顺序访问者无需知道它）
- 如果某些场景不需要默认行为，**提供干净的关闭/替换机制**，并且把它**从主接口中分离出去**（例如用另一个构造函数），让大多数人**根本不需要意识到它的存在**

**【前置】** A8, A9

**【标准范例】**

```c
/* 常见情况：一行搞定 */
int motor_set_speed(int rpm);

/* 不常见情况：换个函数，不污染上面的接口 */
int motor_set_speed_ex(int rpm, const MotorOpts *opts);
/* opts 里可以关掉限幅、指定加速度等 —— 99% 的人永远不碰 */
```

反例（把不常见的塞进常见路径）：
```c
int motor_set_speed(int rpm, int accel, bool clamp_enable, int pwm_mode, bool log_enable);
/* 每次调用都要想 5 个参数，其中 4 个我永远用默认值 */
```

**【常见误解】**
1. 「参数都给上，用户自己选」——这是 classitis 的接口版，把选择成本推给所有人
2. 「默认值就是设个默认参数」——不够；**关键是把不常用能力从主接口里移出去**，不是只给默认值

**【适用边界】**
- ⚠️ 缺口：原书没说"最常见的用法"如何统计；实践中靠观察和直觉

**【预考题】**
1. 你的项目里，有哪些函数调用时你每次都要填一堆你根本不在乎的参数？

**【练习题 + 答案】**

  A：接口有很多能力，但常用路径上只需要知道少数几个 → 有效复杂度低。
- Q：给"最常见的用法最简单"设计一条可操作的检查方法。

## 第三部分：信息隐藏（Ch 5）

### A11 信息隐藏

**原子性**：只考一件事 ✓

**【原话】**（§5.1）
> 实现深模块最重要的技术是**信息隐藏**。这个技术最早由 **David Parnas** 描述。
> 基本思想：**每个模块应该封装少量知识，这些知识代表设计决策。**
> 这些知识**嵌在模块的实现里，但不出现在接口里**，所以对其他模块不可见。

**【原话】隐藏的通常是什么**：实现某个机制的细节。例子包括：
> - 如何在 B 树里存信息、如何高效访问
> - 文件里每个逻辑块对应哪个物理磁盘块
> - 如何实现 TCP 协议
> - 如何调度多核处理器上的线程
> - 如何解析 JSON
> 可以是数据结构与算法，也可以是**低层细节**（如页大小），或**高层概念**（如"假设大多数文件很小"这种假设）。

**【原话】信息隐藏降低复杂度的两条路径**：
> 1. **简化接口** → 降低使用者的认知负荷
> 2. **让系统更容易演进** → 如果某个信息被隐藏了，模块外就没有对它的依赖，**与该信息相关的设计变更只会影响这一个模块**

**【原话】★ 一条重要澄清（对 C 背景尤其重要）**
> **把类里的变量和方法声明为 private，并不等于信息隐藏。**
> private 元素**有助于**信息隐藏，因为外面不能直接访问它们。
> **但是私有信息仍然可能通过 public 方法暴露出去，比如 getter 和 setter。**
> **当这种情况发生时，这些变量的性质与用法就和它们是 public 一样被暴露了。**

**【原话】隐藏的程度**：
> 最好是完全隐藏（对使用者无关且不可见）。
> 但**部分隐藏也有价值**：如果某信息只有少数使用者需要，而且通过**独立的方法**访问、不出现在最常见的用法里，那它**基本上是被隐藏的**，产生的依赖更少。

**【前置】** A6, A8

**【标准范例】**

```c
/* ---------- 假的信息隐藏（private + getter/setter = 没隐藏）---------- */
static int s_pwm_duty;
int  motor_get_pwm_duty(void) { return s_pwm_duty; }   /* 内部细节全暴露 */
void motor_set_pwm_duty(int d) { s_pwm_duty = d; }
/* 名字里有 private 的意味，但"PWM 占空比"这个设计决策
   现在被所有使用者依赖了 —— 和 public 变量效果一样 */

/* ---------- 真正的信息隐藏 ---------- */
int motor_set_speed(int rpm);   /* PWM 这个设计决策被藏在实现里 */
```

**C 语言里的对应物**：`static` 函数/变量 + **不在 `.h` 里声明**。一旦你把内部状态通过 `.h` 暴露出去，就等于写了 getter/setter。

**【常见误解】**
1. ★ **「private / static = 信息隐藏」** —— **明确错**，原书专门澄清：getter/setter 会把私有信息重新暴露
2. 「封装 = 信息隐藏」——接近但不等于；封装的边界在哪、暴露了什么，才是关键
3. 「隐藏得越多越好」——基本对，但**不能隐藏重要信息**（否则是 A7 的假抽象）

**【适用边界】**
- ⚠️ 缺口：原书没给"应该如何划分隐藏边界"的算法

**【预考题】**
1. 你把一个变量声明成 `static`，然后写了 `get_x()` / `set_x()` 两个函数。这样算隐藏了吗？

**【练习题 + 答案】**
- Q：为什么 getter/setter 会破坏信息隐藏？
  A：因为它们把变量的**存在、类型、取值范围、更新时机**都放进了接口——与直接把变量做成 public 的暴露程度是一样的。
- Q：C 里怎样才能做到真正的信息隐藏？
  A：`static` + **不在 `.h` 中声明**；需要跨文件共享的只暴露高层行为，不暴露内部状态。

### A12 信息泄漏（Information Leakage）

**原子性**：只考一件事 ✓

**【原话】**（§5.2）
> 信息隐藏的反面是**信息泄漏**：**当一个设计决策反映在多个模块里时，就发生了信息泄漏。**
> 这在模块之间制造了依赖：**该设计决策的任何变更都需要修改所有涉及的模块。**

**【原话】两种泄漏**：
- **通过接口泄漏**：如果某个信息出现在模块的接口里，那它**按定义就已经泄漏了** → **更简单的接口往往对应更好的信息隐藏**
- **后门泄漏（back-door leakage）**：**即使信息不出现在接口里也可能泄漏。**
  例：两个类都知道某种文件格式（一个读、一个写）。**即使谁都没在接口里暴露格式信息，它们都依赖这个格式**——格式一变，两个类都要改。
  > **这种后门泄漏比通过接口的泄漏更阴险，因为它不明显。**

**【原话】★ 这是本书最重要的危险信号之一**
> **信息泄漏是软件设计中最重要的危险信号之一。作为软件设计者，你能学到的最好技能之一，就是对信息泄漏有高度敏感。**
> 遇到信息泄漏时，问自己："**我如何重组这些类，让这个特定的知识只影响一个类？**"
>
> 两个可选做法：
> - 如果涉及的类**相对小且与泄漏信息紧密绑定** → 可以**合并成一个类**
> - 或者把信息从所有受影响的类里**抽出来，新建一个封装该信息的类** ——
>   ⚠️ **但这个做法只有在你能为它找到简单接口时才有效**；如果新类通过接口把大部分知识又暴露出去，那它就没价值（**你只是把后门泄漏换成了通过接口的泄漏**）

**【前置】** A11

**【标准范例】**（C 语境 —— 非常贴近嵌入式）

```c
/* ---------- 后门泄漏：两个文件都知道"霍尔计数 ↔ 角度"的换算 ---------- */
/* motor.c   */
float angle = hall_count * (360.0f / (POLE_PAIRS * 6));   /* 换算写在这 */

/* encoder.c */
int hall = (int)(angle * (POLE_PAIRS * 6) / 360.0f);       /* 同一换算又写一遍 */

/* 问题：谁也没在 .h 里暴露这个公式，但它出现在两个文件里。
   哪天改成 12 极对，两处都得改 —— 而且没有任何提示。 */
```

```c
/* ---------- 修法 A：抽出封装该知识的模块 ---------- */
/* angle.h */
float angle_from_hall(int hall_count);
int   hall_from_angle(float angle);
/* motor.c 和 encoder.c 都调它 —— 换算只存在一处 */
```

**【常见误解】**
1. 「只要接口里没有，就不算泄漏」——**明确错**，后门泄漏更阴险
2. 「把泄漏的信息抽成新类就解决了」——**不一定**。原书警告：如果新类的接口把知识又暴露了，等于没解决
3. 「信息泄漏 = 数据重复」——不等同。**泄漏的关键是"同一个设计决策"被多个模块知道**

**【适用边界】**
- ⚠️ 缺口：没有自动检测工具（作者说这需要"敏感性"，是人的技能）

**【预考题】**
1. 两个模块谁都没在接口里暴露某个公式，但各自实现了一遍。这算不算"泄漏"？

**【练习题 + 答案】**
- Q：为什么"通过接口泄漏"比"后门泄漏"好一些？
  A：因为它**可见、可搜索、编译器能检查**；后门泄漏看不见。
- Q：把公共知识抽成一个新模块，什么情况下白做了？
  A：当新模块的接口又把这份知识暴露出去时（后门泄漏换成了接口泄漏）。

### A13 时间分解（Temporal Decomposition）

**原子性**：只考一件事 ✓

**【原话】**（§5.3）
> 信息泄漏的一个常见成因是我称为**时间分解**的设计风格。
> **在时间分解里，系统结构与操作发生的时间顺序相对应。**

**【原话】例子**：一个按某格式读文件、修改、再写回的应用。用时间分解会被拆成三个类：读、改、写。
> **读和写两个步骤都知道文件格式 → 造成信息泄漏。**
> **解法是把读写的核心机制合并到一个类里**，这个类在读取阶段和写入阶段都会被用到。

**【原话】为什么容易掉进去**
> 很容易掉进时间分解的陷阱，因为**写代码时"操作必须发生的顺序"常常就在你脑子里**。
> 但**大多数设计决策会在应用的整个生命周期里、在多个时间点显现出来**，所以时间分解常常导致信息泄漏。

**【原话】正确的做法**
> 顺序确实重要，所以它会在应用的**某处**体现出来。**但它不应该体现在模块结构里**——除非那个结构与信息隐藏一致（也许不同阶段确实用到完全不同的信息）。
> **设计模块时，关注每个任务需要什么知识，而不是任务发生的顺序。**

**【原话】危险信号定义**
> 时间分解：执行顺序反映在代码结构里——在不同时间发生的操作被放进不同方法/类里。
> 如果同一份知识在不同执行点被使用，它就会被编码在多个地方，造成信息泄漏。

**【前置】** A12

**【标准范例】**（★ 直接对应他的 FOC 项目）

```c
/* ---------- 时间分解：按"上电时做什么、运行时做什么"切 ---------- */
/* init.c */
void system_init(void) {
    /* 读电机参数表、算极对数换算、初始化 PWM 频率 */
    g_hall_to_deg = 360.0f / (params.pole_pairs * 6);   /* 换算知识在这 */
    pwm_set_freq(params.pwm_khz * 1000);
}

/* loop.c */
void control_loop(void) {
    float deg = hall_count * (360.0f / (params.pole_pairs * 6));  /* 又写一遍 */
}
```
**问题**：`init.c` 和 `loop.c` 因为"发生在不同时间"被分开，结果**都掌握了"极对数换算"这份知识** → 信息泄漏。

```c
/* ---------- 按"知识"切 ---------- */
/* encoder.h —— 谁需要换算都来找它，与调用时机无关 */
float encoder_hall_to_deg(int hall_count);
```
`init.c` 和 `loop.c` 都调用它，换算只存在一处。

**⚠️ 关键提醒**：**不要按"初始化阶段 / 运行阶段"或"中断里 / 主循环里"来切模块。** 那是按时间切，不是按知识切。

**【常见误解】**
1. ★ **「按执行顺序/生命周期阶段划分模块」** —— 这是时间分解，原书判为信息泄漏的常见成因
2. 「初始化代码就该单独放一个文件」 —— **不必然**。要看它是否与运行时共享知识
3. 「中断服务程序和主循环必须分开」 —— **执行上要分开，但那不等于要把知识切碎放进两个模块**

**【适用边界】**
- 【原话】顺序有时确实应该体现在结构里——**当不同阶段确实用到完全不同的信息时**
- ⚠️ 缺口：没有给出判别"不同阶段是否共享知识"的机械方法

**【预考题】**
1. 按"上电初始化"和"运行时"把代码分成两个文件，有什么问题？
2. 你的中断服务程序和主循环，有没有共享某个换算公式或常量？

**【练习题 + 答案】**
- Q：一个应用"先读配置、再运行、最后存日志"，按这三个阶段分三个模块。有什么风险？
  A：如果三个模块都要知道配置的格式/结构，就产生了信息泄漏。
- Q：时间分解"有时"是对的。什么情况下对？
  A：当不同阶段确实使用**完全不同的信息**时（此时按时间切与按知识切是一致的）。

**【迁移题】**
列出你项目里"在不止一个地方出现的同一个常量或公式"。判断：它们是因为**时间分解**被分开的吗？如果是，怎么按知识重组？

**【掌握判定】**
- 能说清：说出时间分解的定义 + 为什么它导致泄漏
- 能应用：给一个项目结构，指出哪些切法是时间分解
- 能回忆：说出"关注任务需要什么知识，而不是任务发生的顺序"

## 第四部分：拆分还是合并（Ch 9）★ 直接回答上一课留下的问题

### A14 拆分的四种代价

**原子性**：只考一件事 ✓

**【原话】**（Ch 9 开篇）
> 软件设计里最基本的问题之一：**两块功能，应该放在一起实现，还是分开实现？**
> 这个问题适用于所有层级：函数、方法、类、服务。

**【原话】先破除一个直觉**
> 看起来实现"降低复杂度"最好的办法是把系统拆成大量小组件——组件越小，每个组件就越简单。
> **然而，细分这个动作本身创造出了细分之前不存在的新复杂度：**

**【原话】细分的四种代价**：

| # | 代价 | 原文要点 |
|---|---|---|
| 1 | **组件数量本身** | 组件越多，越难全部记住、越难在其中找到想要的那个。**细分通常导致更多接口，而每个新接口都增加复杂度。** |
| 2 | **管理组件的额外代码** | 原来用一个对象，细分后可能要管理多个对象 |
| 3 | **分离（separation）** | 细分后的组件距离更远了（可能在不同文件）。**如果组件之间真有依赖，分离就是坏的**——开发者要在组件间来回翻；**更糟的是，他们可能没意识到依赖存在，从而导致 bug** |
| 4 | **重复（duplication）** | 原本只有一份的代码，细分后可能每个组件里都要有一份 |

**【原话】关键权衡**
> **如果组件真正独立，分离是好的**——能让开发者一次只专注一个组件。
> **但如果有依赖，分离就是坏的。**

**【前置】** A8, A9, A12

**【标准范例】**
把一个 400 行的 `motor.c` 拆成 5 个文件，每个 80 行：
- ✅ 每个文件更好读
- ❌ 多出 4 组 `.h`/`.c` 和接口
- ❌ 谁调用谁需要理清（代价 1、2）
- ❌ 本来在同文件能一眼看到的依赖，现在要跨文件翻（代价 3）
- ❌ 原来共用的换算函数现在要么重复、要么再抽一层（代价 4）

**【常见误解】**
1. 「拆得越小，每个部分越简单，所以整体越简单」——**明确错**，这是 Ch 9 开篇要破除的直觉
2. 「只要每个模块职责清晰，拆分就没代价」——错，**接口数量和分离本身就是代价**
3. 「有依赖就该合并」——不完整，见 A15 的三条判据

**【适用边界】**
- ⚠️ 缺口：四种代价之间如何加权，原书未给方法

**【预考题】**
1. 把一个大文件拆成 10 个小文件，会带来哪些**新增的**成本？（至少说 3 个）

**【练习题 + 答案】**
- Q：四种代价里，哪一种"最坏"？为什么？
  A：代价 3 中的"**没意识到依赖存在**"——它会直接导致 bug，其余三种主要是增加成本。
- Q：为什么"组件真正独立时，分离是好的"？
  A：因为此时没有来回翻的负担，分离让注意力集中（这正是拆分想要的效果）。

**【掌握判定】**
- 能说清：说出拆分的四种代价
- 能应用：给一个拆分提案，列出它会产生的具体代价

### A15 何时合并 ★

**原子性**：只考一件事 ✓

**【原话】**（Ch 9）
> **把代码放在一起，在它们紧密相关时最有益。如果它们不相关，大概还是分开好。**

**【原话】四条"相关"的迹象**：
| 迹象 | 原文 |
|---|---|
| 1. **共享信息** | 两者都依赖某种文档的语法 |
| 2. **被一起使用** | 用其中一个的人很可能也用另一个。**这种关系只有是双向的才有说服力** |
| 3. **概念上重叠** | 存在一个简单的更高层类别同时包含两者 |
| 4. **离开另一个就看不懂** | 不看另一个就没法理解这一个 |

> ⚠️ **关于第 2 条的反例**（原书特意给）：
> 磁盘块缓存几乎总会用到哈希表，**但哈希表能用在很多跟块缓存无关的场景**；
> → **所以这两个模块应该分开。**（关系必须是双向的）

**【原话】三条合并规则**：

**9.1 共享信息 → 合并**
> HTTP 服务器例子：一个方法读请求、另一个解析请求，结果**两个方法都掌握了 HTTP 请求格式的很多知识**（因为不解析就无法知道请求到哪结束）。
> **因为共享信息，最好把读和解析放在同一个地方；合并后代码更短更简单。**

**9.2 能简化接口 → 合并**
> 合并后可能定义出比原接口**更简单、更好用**的接口。
> 通常发生在原来每个模块只解决问题的一部分时。
> **而且合并后可能让某些功能自动完成，使大多数用户不必意识到它们的存在**（Java I/O 的缓冲就是这个机会）。

**9.3 消除重复 → 合并**
> 发现同一段模式反复出现，就看能不能重组代码消除重复。
> 注意：**如果片段只有一两行，提取成方法可能没什么收益**；**如果片段与环境交互复杂（比如访问很多局部变量），替换方法可能需要复杂的签名，收益也会降低。**

**【原话】相关的危险信号**
> **重复（Repetition）**：同一段（或几乎相同的）代码反复出现，是"你还没找到正确抽象"的危险信号。
> **通用-专用混合（Special-General Mixture）**：通用机制里还包含为特定用途专门写的代码，使机制变复杂，并在机制与用途之间制造信息泄漏。

**【前置】** A12, A14

**【标准范例】**（C 语境）

```c
/* ---------- 命中"共享信息"，应该合并 ---------- */
/* can_rx.c */  void can_receive_packet(void);   /* 读一帧 CAN 报文 */
/* can_parse.c */ void can_parse_packet(void);   /* 解析这帧 */

/* 问题：要判断帧到没到齐，必须解析帧头里的长度字段
   → 接收方也得懂协议格式 → 共享信息 → 应合并 */
```

```c
/* ---------- 命中"重复"，应该合并 ---------- */
/* motor.c   */ if (err == 0x11) { log_write("overcurrent"); }
/* heater.c  */ if (err == 0x11) { log_write("overcurrent"); }
/* → 错误码到文本的映射应该只有一份 */
```

```c
/* ---------- 反例：看似相关，其实该分开 ---------- */
/* 用了哈希表 —— 不能因此就把"块缓存"和"哈希表"合并 */
```

**【常见误解】**
1. 「两个模块互相调用就该合并」——**错**。要满足上面四条之一，而且第 2 条必须**双向**
2. 「重复一两行也值得抽函数」——**原书说未必**，短片段抽出来可能没收益
3. 「共享信息 = 共享变量」——不等同。共享的是**知识**（格式、协议、换算规则）

**【适用边界】**
- ⚠️ 缺口：四条迹象冲突时如何取舍，原书未给优先级

**【预考题】**
1. 两个模块都用到同一个哈希表工具函数，它们该合并吗？

**【练习题 + 答案】**
- Q：为什么"被一起使用"必须是**双向**的才算相关？
  A：单向的"总是用到"（如块缓存总是用哈希表）只是使用关系，不是概念关系；合并会把无关的东西绑在一起。
- Q：什么时候"消除重复"反而不值得做？
  A：当片段很短（一两行），或它与环境耦合太深、替换方法需要复杂签名时。

**【迁移题】**
在你项目里找一组"总是先调 A 再调 B"的函数。判断：它们是双向相关（该合并）还是单向依赖（该保留）？

**【掌握判定】**
- 能说清：说出四条相关迹象 + 三条合并规则
- 能应用：给一组模块，判断是否该合并
- 能回忆：说出"被一起使用必须双向"

### A16 何时拆分：通用 vs 专用

**原子性**：只考一件事 ✓

**【原话】**（§9.4）
> 如果一个模块包含一个可用于多种用途的**机制**，那么它应该**只提供那一个通用机制**。
> **它不应该包含把这个机制专门化的代码，也不应该包含其他通用机制。**
> 与通用机制相关的**专用代码通常应该放在另一个模块里**（通常是和那个特定用途相关的模块）。

**【原话】分层规律**
> **一般地，系统的低层更通用，高层更专用。**
> 例：应用最顶层完全由该应用特有的功能组成。
> **分离专用代码与通用代码的方法是：把专用代码往上提，提到更高的层，让低层保持通用。**

**【原话】具体做法**
> 当遇到一个类同时包含同一抽象的通用特性和专用特性时，看它能否拆成两个类：
> **一个装通用特性，另一个叠在它上面提供专用特性。**

**【原话】重要澄清**（防止过度解读）
> 这条建议针对的是**与同一个机制相关**的代码。
> 例：**特定用途的 undo 代码**（比如"撤销一次文本插入"）应该与**通用 undo 代码**（比如管理历史列表）分开。
> **但是，把"某个机制的专用代码"与"另一个机制的通用代码"放在一起，通常是合理的。**
> 文本类就是例子：它实现一个通用的文本管理机制，但也包含与撤销相关的专用代码。
> 这段撤销代码是专用的（只处理文本修改的撤销），**把它和 `History` 类里的通用撤销基础设施合并没道理**，但**把它放进文本类是合理的**——因为它与其他文本功能紧密相关。

**【前置】** A15

**【标准范例】**（C 语境）

```c
/* ---------- 通用机制（底层）---------- */
/* crc.h */
uint16_t crc16(const uint8_t *buf, int len);   /* 纯计算，不知道业务 */

/* ---------- 专用代码（上层）---------- */
/* motor_proto.c —— 与电机协议相关，调用 crc16 */
uint16_t motor_frame_crc(const MotorFrame *f);
/* ⚠️ 不要把"电机帧的校验规则"塞进 crc.c —— 那会让通用机制变专用 */
```

**【常见误解】**
1. 「通用越好」——**错**。原书说"应该**稍微**通用"（§6.1），过度通用也是问题（接口难用）
2. 「凡是专用代码都要抽出去」——**错**。要区分它属于哪个机制（见上面的重要澄清）
3. 「低层代码不该知道业务」——方向对，但**低层可以为多个业务服务，高层才绑定单一业务**

**【适用边界】**
- ⚠️ 缺口：如何判断"稍微通用"和"过度通用"的界线，原书只给了自问清单（§6.5），无量化标准

**【预考题】**
1. 一个 `crc16()` 函数里写了"如果是电机帧就……"的分支。有什么问题？

**【练习题 + 答案】**
- Q：为什么"专用代码往上提"能改善设计？
  A：让低层保持通用 → 低层可被复用、且不会因某个用途变化而被迫改动（减少信息泄漏）。
- Q：文本类里包含"撤销文本修改"的专用代码，为什么不违反"通用与专用分离"？
  A：因为这条原则针对**同一个机制**；撤销文本修改是"文本机制"的专用代码，与通用撤销基础设施（另一个机制）合并才是不合理的。

**【迁移题】**
你的 `delay.c` 里有没有"专为某个外设写的"延时分支？按 A16 应该怎么处理？

**【掌握判定】**
- 能说清：说出"低层通用、高层专用" + 那条重要澄清
- 能应用：判断一段专用代码该放在哪一层

### A17 拆分方法（以及"长方法不一定是坏的"）★

**原子性**：只考一件事 ✓

**【原话】**（§9.8）
> **光凭长度很少是拆分方法的好理由。**
> 一般地，**开发者拆分方法拆得太多了**。拆分方法会引入额外接口（增加复杂度），还会把原本相关的片段分开，**使代码更难读**。
> > **除非它让整体系统更简单，否则不应拆分方法。**

**【原话】长方法不总是坏的**
> 假设一个方法包含五个按顺序执行的 20 行代码块。**如果这些块相对独立**，那这个方法可以一块一块读，**把每块挪进单独的方法没什么收益**。
> **如果这些块之间有复杂的交互**，那就更该把它们放在一起，让读者一次看到全部代码；否则读者要在分散的方法之间来回翻。
> > **包含几百行代码的方法，只要签名简单、容易读，就没问题。这些方法是深的（功能多、接口简单），是好的。**

**【原话】拆方法只有在"整体上产生更干净的抽象"时才有意义**，两种拆法：

| 拆法 | 做法 | 何时成立 | 危险 |
|---|---|---|---|
| **(b) 提取子任务**（最好） | 子任务进子方法，父方法调它；**父方法的接口不变** | 子任务**能被干净地分离**：(a) 读子方法不需要知道父方法；(b) 读父方法不需要懂子方法实现。**通常意味着子方法比较通用，可能被别处复用** | 若你在父子之间来回翻 → 危险信号 **Conjoined Methods** |
| **(c) 拆成两个各自对外的方法** | 原方法做了多件不紧密相关的事，接口过于复杂 | **每个新方法接口都比原来简单**；理想情况下**大多数调用者只需要调其中一个** | 若调用者必须调**两个**、还要来回传状态 → 会变成 **A8 的浅方法** |

**【原话】反向操作：有时合并方法更简单**
> 可能把两个浅方法换成一个深方法；可能消除重复；可能消除方法间的依赖或中间数据结构；可能改善封装（原先散在多个地方的知识现在集中在一处）；或简化接口。

**【原话】危险信号定义**
> **Conjoined Methods**：两个方法依赖太多，**不理解其中一个的实现就无法理解另一个**。
> 这也适用于其他情形：**如果两段代码物理上分离，但都必须看另一段才能理解，那就是危险信号。**

**【前置】** A8（深浅模块）, A14

**【标准范例】**

```c
/* ---------- 拆过头了（浅方法）---------- */
static int  rpm_to_duty_clamp(int rpm) { /* 1 行 */ }
static void duty_write(int d)          { /* 1 行 */ }
static void flag_update(void)          { /* 2 行 */ }
/* 三个浅方法，调用者要连着调三个 —— 没省认知负荷 */

/* ---------- 一个深方法就够 ---------- */
int motor_set_speed(int rpm);   /* 内部做同样三件事，接口一个 */
```

**【常见误解】**
1. ★ **「方法超过 N 行就必须拆」** —— **明确错**，原书点名批评这类硬性规则
2. 「方法越短越好」——错，见"长方法不总是坏的"
3. 「拆出子方法总是无害的」——错，可能造成 conjoined methods

**【适用边界】**
- ⚠️ 缺口：没有给出"多长算长"的数值；原书的判据是**抽象是否更干净**

**【预考题】**
1. 一个 200 行的方法，一定该拆吗？
2. 拆出子方法之后，你发现自己要来回翻看父子两处才能理解。这说明什么？

**【练习题 + 答案】**
- Q：两种拆法（b）和（c），哪种更常成立？为什么？
  A：**(b)**。因为 (c) 会让调用者面对多个方法、需要来回传状态，容易退化成浅方法。原书说 (c) 不常成立。
- Q：什么情况下"几百行的方法"是好的？
  A：当它**签名简单、容易读**、块之间独立（或紧密相关需要一起看）时——此时它是深方法。

**【迁移题】**
你项目里最长的方法是什么？按 A17 判断：它是"该拆的"还是"深方法，不该拆"？给出理由。

**【掌握判定】**
- 能说清：说出"长度不是拆分的理由" + 两种拆法的区别
- 能应用：给一个长方法，判断该不该拆、怎么拆
- 能回忆：说出 Conjoined Methods 这个危险信号

### 原书自带的"危险信号"清单（可直接用作练习素材）

| 危险信号 | 一句话 |
|---|---|
| Shallow Module | 接口不比实现简单多少 |
| Information Leakage | 同一个设计决策反映在多个模块里 |
| Temporal Decomposition | 代码结构按执行顺序而非按信息隐藏来切 |
| Overexposure | 为了用常用功能，调用者被迫知道罕见功能 |
| Pass-Through Method | 方法几乎只把参数转给另一个签名相似的方法 |
| Repetition | 非平凡代码反复出现 |
| Special-General Mixture | 专用代码没和通用代码干净分开 |
| Conjoined Methods | 两个方法互相依赖到不理解一个就无法理解另一个 |
| Comment Repeats Code | 注释里的信息从旁边的代码一眼就能看出 |
| Implementation Doc Contaminates Interface | 接口注释里写了使用者不需要的实现细节 |
| Vague Name | 名字模糊到传达不了有用信息 |
| Hard to Pick Name | 给一个实体起不出精确直观的名字 |
| Hard to Describe | 为了说完整，变量/方法的文档必须写得很长 |
| Nonobvious Code | 代码行为或含义不容易理解 |

| 点 | 缺口 |

| A0–A1 | 复杂度只有"粗略数学描述"，**不可精确计算** |
